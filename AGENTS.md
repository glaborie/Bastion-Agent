# AGENTS.md — Working Instructions for OpenCode

## What this repository is

Bastion-Agent is a maintained control plane, not a scaffold. The build plan in
`HANDOVER_SPEC.md` is delivered and every guardrail it names has tests, so do not
rebuild an existing component and do not restate a decision `docs/adr/` already
records. Change one thing at a time, through the backlog, and prove it with the
gate.

Where things live: `HANDOVER_SPEC.md` is the design, `docs/adr/` the decisions,
`backlog/items/` the work queue, `THREAT_MODEL.md` and `COMPLIANCE.md` the claims
the policy checks enforce, `docs/TROUBLESHOOTING.md` the local failure modes.

## Technology Stack & Constraints

- **Python**: 3.11+ using `uv` for package management (`pyproject.toml`).
- **Frameworks**: FastAPI, ARQ (asyncio Redis worker), SQLAlchemy 2.0 (asyncpg), Pydantic v2.
- **Security & DLP**: Microsoft Presidio (`presidio-analyzer`, `presidio-anonymizer`), `cryptography` (AES-256-GCM), `onnxruntime` for distilled local classification.
- **Inference & Routing**: OmniRoute client (OpenAI-compatible) routing to local `llama.cpp` container (RTX 3060 Ti CUDA) or OpenRouter API.
- **Observability**: OpenTelemetry Python SDK exporting to `otel-collector-contrib` (dispatches to Langfuse/Arize).
- **Evaluation**: DeepEval (`deepeval`) + Pytest for deterministic golden dataset gating (zero-tolerance threshold).
- **Containerization**: `docker-compose.yml` with 14 services — `gateway`, `worker`, `db` (Postgres 16), `pgadmin`, `redis` (Redis 7), `redis-ui`, `keycloak`, `omniroute`, `llama-cpp`, `otel-collector`, `minio` and `minio-init` (the audit witness), `trivy-scan`, `falco` — plus the `docker-compose.gpu.yml` and `docker-compose.pki.yml` overlays. `pgadmin`, `redis-ui` and the witness/scanner sit behind profiles, so the default stack stays small.

## What moves with a change

Each row is a merge-blocking check in `scripts/gate.sh`: a change that lands
without its document fails CI, not review.

| Change | Must move with it |
|---|---|
| A tool or its role | `docs/tools/v1.json`, `config/keycloak/realm-export.json` — `validate_tool_catalog.py`, `validate_rbac.py` |
| A control or a threat | `THREAT_MODEL.md` — `check_threat_model.py`, `recalculate_dread.py` |
| A decision | the ADR that records it, new or superseding — `check_adrs.py`, the `adr` skill |
| A service, image pin or scanner | `docker-compose.yml`, `trivy.yaml`, `COMPLIANCE.md` (ADR-016) |
| DLP, routing or egress behaviour | the golden corpus and eval gates — the `dlp-invariants` skill, `scripts/run_evals.py` |
| A backlog item | its own file under `backlog/items/` — `check_backlog.py` |

## Quality Standards

- Strict type hints: `mypy strict` is set in `pyproject.toml`.
- Clean logging with structured context.
- Zero mock shortcuts in core security validation — every guardrail must be active and tested. The enforceable form of this rule is the gate.

## Entry points

- `/next` works one ready item end to end; `/idea <text>` captures one without
  implementing it; `/gate` runs the gates; `/handoff` summarises the session.
- Skills: `adr`, `backlog-intake`, `dlp-invariants`, `stack`, `secrets`,
  `fake-name-generator-ch`.

## Backlog & Idea Intake

`backlog/items/` is the only work queue: one Markdown file per item.
`docs/adr/` records decisions; `HANDOVER_SPEC.md` records the design;
`backlog/items/` records what someone wants and nobody has decided yet.
`BACKLOG.md` is a rendered index of those files — generated by
`scripts/check_backlog.py --write`, untracked, and never edited by hand.
`backlog/config.toml` holds the phase governance.

- At session start, read `backlog/items/` and run
  `uv run python scripts/check_backlog.py --next`.
- Work one `ready` item at a time. Never start an `inbox`, `blocked`, or
  later-phase item on your own initiative.
- A new idea goes through `/idea <text>` and is captured, not implemented. Never
  implement an idea in the turn that produced it.
- Finishing an item means: run the verification gates, tick every acceptance box,
  set `status: done` and `updated`, then
  `uv run python scripts/check_backlog.py --write`.
- Capture with `uv run python scripts/check_backlog.py --new "<title>"`: it
  allocates the next id from the highest existing one and creates the file
  exclusively, so concurrent captures cannot overwrite each other or reuse an id.
  Never hand-pick an id.
- A branch edits only the item file it is working on. Do not touch another item,
  `backlog/config.toml`, or `BACKLOG.md`.
- Two branches can still allocate the same id, because each worktree sees its own
  items. The validator names the duplicate at merge: rename one file with
  `git mv` and update any `depends-on`.

## Worktree & PR discipline

- **Create the worktree before touching a backlog item.** Never implement an
  item in the main checkout. `scripts/dev/worktree.sh start IDEA-NNN` does the
  whole start-up: worktree from `origin/master`, branch `idea-nnn-slug`, `.env`
  symlink, `uv sync`, `status: active` committed, and the branch pushed. It
  prints the path; move the session there next.
- **The pushed branch is the claim, and `worktree.sh start` enforces it.** It
  refuses an id that already has a worktree, a local branch, or a remote
  `idea-nnn-*` branch, so two agents cannot start the same item. Before picking
  work, `uv run python scripts/check_backlog.py --list active` shows claims that
  have merged and `git ls-remote --heads origin 'refs/heads/idea-*'` shows the
  ones that have not. If an item is claimed, take another or ask; do not start it
  anyway.
- **The item must be on the base before it can be started.** Capturing is not
  starting: commit and merge the item first, or `worktree.sh start` stops with
  "is not on origin/master". A worktree created from a base without the item has
  nothing to mark active, and the board then shows no claim at all.
- One worktree per item, branched from `origin/master`, named after the item.
  The worktree tool takes only a name, so branch explicitly afterwards; never
  assume the base.
- Do not stack pull requests. Merge the base first, then open the next one, or
  the second PR carries the first PR's commits.
- Run `gh pr list --head <branch>` before `gh pr create`; a backgrounded
  create plus a retry produces "already exists".
- At merge time, run `scripts/dev/cleanup.sh` (dry-run first): it removes the
  worktree and deletes local and remote branches only where the pull request is
  merged, and reports the rest.
  Certificate material under a worktree's `pki/` is owned by container uids;
  clear it through a throwaway container rather than `sudo`.
- Verify a claim about CI behaviour by reading `.github/workflows/ci.yml`
  first; do not describe a gate from memory.
- When a local run looks broken, read `docs/TROUBLESHOOTING.md` before
  debugging the client.
