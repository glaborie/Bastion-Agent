# ADR-021: A HashiCorp Vault Dev Overlay for Infra Credentials

**Status:** Accepted
**Date:** 2026-11-14
**Last modified:** 2026-11-19

## Context

The dev stack carried every credential in a hand-typed `.env` file: the Postgres
and Redis passwords, the Keycloak admin password and client secret, the MinIO
root password and the audit witness key. Nothing generated them, nothing rotated
them, and a value copied between a workstation and a compose file had no single
source. `docker-compose.vault.yml`, `vault/`, `README-Vault.md` and the
`make vault-*` targets closed that gap by running HashiCorp Vault inside the
stack, but the decision they encode was recorded nowhere: `docs/adr/` held
twenty ADRs and none named the storage backend, the auth model, the token, the
unseal material or what the overlay deliberately does not do. A fixed root token
plus on-disk unseal material is exactly the kind of choice that must not live
only in a compose file.

Two collisions forced the record early. The repository already has a "vault":
`agent/dlp/vault.py` `TokenVault` under ADR-002, AES-256-GCM over
`{{ENTITY:TYPE_N}}` PII tokens in Redis. That is a token vault — a data store for
reversible redaction — not a secret store, and an unqualified "the vault" is
ambiguous from here on. Separately `IDEA-020` plans OpenBao with AppRole auth,
KV reads at startup, audit logging and rotation for production at phase v0.5;
it owns three choices this overlay had to make for dev (dev mode versus Shamir
shares, SDK versus sidecar, whether `worker` gets its own identity). This ADR
fixes the dev answer and states its limits so the production plan is a successor
decision rather than a silent contradiction.

The constraint that shapes everything below is scope: the overlay is additive
and dev-shaped. `docker-compose.yml` is not edited by it, the default stack
starts without Vault, and secrets still reach the application containers through
the process environment — materialised from Vault into a gitignored `.env.vault`
by `make vault-export` and loaded as a second `env_file` — because the runtime
read path for application secrets (JWT signing, HMAC, OAuth, model API keys) is
not wired yet. This ADR therefore records a better source of truth for dev
credentials, not the fail-closed provider that `IDEA-020` designs.

## Decision

1. **One additive overlay, `docker-compose.vault.yml`, and no edit to any
   existing service.** It adds `vault` (server) and `vault-bootstrap` (one-shot
   init, unseal, policy write and seed) on `bastion-net`; the pre-existing
   services in `docker-compose.yml` are unchanged, so `docker compose -f
   docker-compose.yml up -d` is still the default stack and Vault is opt-in
   through `make vault-up`.

2. **HashiCorp Vault 1.17 on Raft integrated storage, single node, behind
   TLS.** `vault/Dockerfile` builds from `hashicorp/vault:1.17.0` pinned by
   digest and copies `vault/config.hcl`, the policies and the certificate in.
   `vault/config.hcl` declares `storage "raft"` at `/vault/data` with
   `node_id = "bastion-dev-1"`, a TLS listener on **8200** with the cluster
   listener on **8201**, `api_addr`/`cluster_addr` on the same ports, and the
   UI enabled. One raft node is the dev topology; the file's comments carry the
   multi-node shape for staging and production.

3. **One KV v2 mount, `bastion/`, and one ACL policy per service.**
   `vault/bootstrap.py` enables KV v2 at `bastion` and seeds randomised dev
   secrets on first run only — it checks for `bastion/db/postgres` before
   writing, so unsealing never rotates credentials a running stack already
   holds. `vault/policies/` holds six policies — `gateway`, `keycloak`, `minio`,
   `omniroute`, `postgres`, `redis` — each granting `read` on its own
   `bastion/data/...` path and nothing else.

4. **A hardened server container and a non-root user.** The `vault` service runs
   as `user: vault` rather than root, with `cap_drop: [ALL]` and
   `cap_add: [IPC_LOCK]` (mlock, so key material is not swapped), a read-only
   root filesystem with a `tmpfs` for `/tmp`, `no-new-privileges:true` and the
   API published only on `127.0.0.1:8200`. `vault-bootstrap` runs as the same
   user because it owns the data volume it writes to.

5. **Every credential is materialised into a gitignored `.env.vault`, not read
   at runtime.** `make vault-up` seeds the generated infra passwords and
   application secrets, and `make vault-import` copies the six externally-issued
   keys (OpenRouter, llama.cpp, Langfuse, Arize, Opik, Hugging Face) from `.env`
   once, writing an empty value when unset. `make vault-export` reads every key
   — the full list is in `README-Vault.md` — and composes the host
   `DATABASE_URL`/`REDIS_URL` from the Vault Postgres/Redis password plus the
   non-secret `POSTGRES_USER`, `POSTGRES_DB`, `POSTGRES_PORT` and `REDIS_PORT`
   in `.env`. It writes `.env.vault` mode `0600` and fails loudly — deleting the
   file — if a required value comes back empty. `make vault-check`
   (`scripts/check_env_vault.py`) refuses a stack start when the file is
   incomplete or has drifted from Vault; its `--check-plaintext` mode is a gate
   step that fails, naming only the key, when a secret or an embedded URL
   password is typed back into `.env`. `docker-compose.yml` loads `.env.vault`
   as a second `env_file`, the Makefile layers it as a later `--env-file`, and
   `settings.py` loads the ordered pair `(".env", ".env.vault")`, so host
   tooling sees the same values and a fresh clone without Vault still starts.

6. **The certificate is self-signed and generated per host.**
   `vault/certs/vault.{crt,key}` is gitignored and created by a `make vault-up`
   prerequisite (`openssl`, 825 days, SANs `DNS:vault`, `DNS:localhost`,
   `IP:127.0.0.1`), with the key `root:vault` mode `0640` inside the image. The
   client therefore sets `VAULT_SKIP_VERIFY`, which is a dev-only shortcut and
   not a trust model: no component verifies the Vault identity.

7. **Dev-only limits, stated rather than implied.** A fixed root token,
   `dev-root-token-bastion`, is created by the bootstrap and used by the
   overlay and the Makefile; the unseal key is written to
   `/vault/data/unseal.key` in the data volume so a restart can unseal
   unattended; the certificate is self-signed; and the Raft cluster is a single
   node with no retry-join peer. Each of these is dev-only. None of them is a
   production posture, and none of them is delivered by `IDEA-020`, whose
   AppRole identities, runtime KV reads, audit device and rotation supersede
   this record.

8. **This is not the PII token vault.** Nothing here stores or unwraps prompt
   tokens. `TokenVault` in `agent/dlp/vault.py` (ADR-002) remains the only
   component that maps `{{ENTITY:TYPE_N}}` placeholders back to values; it keeps
   its own key and its own Redis store. When a document or a comment says "the
   vault", it must qualify which one.

## Consequences

**Pros**

- One generated source of truth for every dev credential, with no hand-copied
  password or application secret in `.env` that only exists on one workstation.
- `make vault-check` fails the start when `.env.vault` is stale, so a rotation
  cannot silently leave the stack on an old value.
- The overlay is additive and opt-in: CI, a fresh clone and the default stack are
  unaffected, and `docker-compose.yml` stays readable as the baseline.
- The server container is non-root, capability-stripped and read-only, so the
  dev posture is visible in the compose file instead of assumed.
- `IDEA-020` now has a recorded baseline to extend; the word "vault" has a
  written disambiguation from ADR-002.

**Cons**

- The fixed root token, the unseal key on disk and the self-signed certificate
  make the overlay unusable as a production posture; every one of them has to be
  replaced by `IDEA-020`, not hardened in place.
- Secrets still reach the app containers through the environment, so
  `docker inspect` and a crash dump can still read them; the overlay moves the
  source of truth, not the exposure. `.env.vault` is still plaintext at mode
  `0600`, readable by every process the developer runs, exactly as `.env` was.
- Vault becomes an extra service to start, unseal after every restart and
  diagnose; a lost unseal key means resetting the dev data volume and re-running
  `make vault-export`.
- Two secret stores with one name invites confusion; every new document has to
  keep saying which vault it means.
