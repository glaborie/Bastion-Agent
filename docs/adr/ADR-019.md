# ADR-019: East-West Mutual TLS with an Internal Step-CA

**Status:** Accepted  
**Date:** 2026-11-12  
**Last modified:** 2026-11-12

## Context

ADR-001 fixed the deployment target as a single Docker Compose stack on one host, with "no service mesh or sidecar proxies", and accepted that Keycloak's JWKS is fetched "over the internal network" without saying over what. In practice that made `bastion-net` a flat trusted bridge: `DATABASE_URL` carried a password with no `sslmode`, `REDIS_URL` carried `REDIS_PASSWORD` against a server with no `--tls-port`, and the gateway reached Keycloak over plain HTTP. Every application container held all four of those passwords, so a compromised workload — or anyone reading a leaked `.env`, a host process, or a published loopback port — could replay them from anywhere on the bridge. `THREAT_MODEL.md` T8 recorded the transport half of this as PLANNED and concluded "treat Redis write access as equivalent to administrator access"; §2 assigned segmentation to the deployer and no ADR decided how.

The pressure is credential replay, not passive sniffing: the compose baseline already drops `CAP_NET_RAW`, so ARP or DNS spoofing from a container is awkward, but a password authenticates a *secret*, never a *workload*. A certificate authenticates the workload. The question this ADR answers is therefore narrow: does the stack attach an identity to its east-west connections, and what does it cost in operations?

Two constraints bound the answer. First, the item's own review found the alternatives: a service mesh contradicts ADR-001 decision 1 outright, and hand-issued certificates with long lifetimes recreate the shared-secret problem with extra steps. Second, the CA root key would live on the same host as every workload it certifies, so the control cannot defend against host or root compromise — `THREAT_MODEL.md` §2 already places that attacker out of scope. The decision is recorded with that limit stated, not hidden.

## Decision

1. **An opt-in `pki` profile, not a new default.** `docker-compose.pki.yml` adds `pki-init`, `ca` and `pki-issue` under the `pki` profile and overrides `db`, `redis`, `keycloak`, `gateway` and `worker`. The default `docker compose up -d` is unchanged: it still starts a plaintext, loopback-only stack for local development, and `README.md` and `SECURITY.md` say so explicitly. The profile name avoids `compliance`, which IDEA-019 already claims for the Trivy scanner.

2. **A local Step-CA, bootstrapped once, never regenerated.** `scripts/pki/bootstrap.sh` creates `secrets/ca_password` and `secrets/provisioner_password` (mode `0600`, random, gitignored) and the `pki/` tree. `pki-init` runs `step ca init` only when `pki/ca/config/ca.json` is absent, so a restart cannot orphan every issued leaf. The CA listens on `https://ca:9000` inside `bastion-net` and publishes no host port. It carries `cap_drop: ALL` plus `NET_BIND_SERVICE`, which the `step-ca` binary requires at exec time even though it binds an unprivileged port.

3. **Keys are generated where they are used.** `pki-issue` runs `step certificate create --csr` to produce the private key and a CSR locally, then `step ca sign` to have the CA return the leaf. The CA never sees a private key, and the issuance container never holds one after it writes the file. Leaves are ECDSA P-256 with a lifetime from `PKI_CERT_TTL` (default `24h`), and each service directory is owned by the uid that service runs as, `0600` for the key and `0644` for the certificate.

4. **PostgreSQL accepts certificate authentication only over TCP.** `config/pki/pg_hba.conf` is `hostssl … cert` for the app role and `hostnossl … reject` otherwise; the Unix socket keeps `trust` because it is unreachable from the bridge and is what the image's healthcheck uses. The certificate CN is the database role (`bastion`), which is how `cert` maps a leaf to a role, and the server certificate carries `db`, `localhost` and `127.0.0.1` as SANs so `sslmode=verify-full` has a name to check. A password with TLS but no client certificate is refused with "connection requires a valid client certificate"; a plaintext connection is refused with "pg_hba.conf rejects … no encryption". Both were run against this profile. The commands, verbatim:

```
psql "host=db port=5432 dbname=bastion user=bastion sslmode=verify-full \
      sslrootcert=/pki/trust/ca.crt sslcert=/pki/gateway/tls.crt \
      sslkey=/pki/gateway/tls.key" -tAc 'select 1'
# -> 1

psql "host=db port=5432 dbname=bastion user=bastion sslmode=verify-full \
      sslrootcert=/pki/trust/ca.crt" -tAc 'select 1'
# -> FATAL: connection requires a valid client certificate
```

`docs/PKI.md` carries the same pair plus the Redis, Keycloak and renewal checks.

5. **Redis speaks TLS and requires a client certificate.** Redis keeps the password but moves to `--tls-port 6379 --port 0 --tls-auth-clients yes`, so the port has no plaintext listener at all. `db/redis.py` derives the client identity from settings and exposes one `arq_redis_settings()` helper, so the gateway's enqueue pool and the worker's consumer pool carry the same certificate instead of each remembering to. A `rediss://` DSN implies TLS even when the boolean is off. The container healthcheck moves to `redis-cli --tls` with the CA and client pair, because the image's default probe speaks plaintext.

6. **Keycloak serves HTTPS on the back channel.** `start-dev` forces an HTTP listener on the same port, so the profile starts Keycloak with `start --https-port=8080 --http-enabled=false` and per-service certificate flags. The gateway trusts the internal CA for those calls through `OIDC_CA_CERT_PATH`, which `gateway/auth/oidc.py` applies to both the JWKS and token clients. A configured-but-missing bundle raises at client construction rather than falling back to the system store.

7. **Every client fails closed.** `database_ssl_context` and `redis_tls_kwargs` raise at engine or client creation when a non-disabled mode cannot find its CA or client identity. Only the internal CA is loaded; the system trust store is deliberately not mixed in, so a public CA cannot impersonate `db` or `redis`. `tests/test_db_tls.py` pins each failure, and the live half asserts refusal rather than a successful password or plaintext connection.

8. **Renewal is re-issuance plus the service's own reload path.** Re-running `pki-issue` overwrites each leaf with a fresh serial and `notAfter`; PostgreSQL picks it up on `SIGHUP` without a restart, which was verified by capturing the served serial before and after. Redis, Keycloak and the application processes read their certificate at connection or start time and need a restart, which the runbook states. The rotation is not rolling: the CA issues from one root, and there is no dual-key envelope.

9. **Secrets arrive as compose secret files, not inline `-e` values.** `secrets/ca_password` and `secrets/provisioner_password` are mounted read-only into the three PKI services. The CA root key exists only under `pki/ca/`, is mode `0600` inside a `0700` directory, and is mounted only into the CA container; `gateway` and `worker` mount `pki/trust` (public root) and their own leaf directory.

10. **The ADR-001 sentence is narrowed, not quietly ignored.** ADR-001's "no sidecar proxies" was about request-path proxies, and this ADR keeps that: issuance is a one-shot compose job and there is no proxy in the request path. The "flat trusted bridge" implication is what changes, and ADR-001 is amended in place to say so.

11. **Out of scope for this decision.** OmniRoute and the OTLP endpoint stay on plain HTTP: OmniRoute's upstream image has no TLS listener and putting one in front would introduce the request-path proxy ADR-001 rejects, while the collector's TLS would need certificate plumbing in the exporter that the current span path does not use. `pgadmin` and `redis-ui` are excluded from the PKI profile because they would need client certificates they cannot present. These are named in `THREAT_MODEL.md` T8 as remaining PLANNED lines rather than left implicit.

## Consequences

- **Pros**: A password alone no longer reaches PostgreSQL, and a certificate-less client no longer reaches Redis at all; the threshold for impersonating a workload moves from "read a shared secret" to "hold that workload's private key"; the CA is a first-class, inspectable component rather than a stack of `openssl` commands; identity is attached per service, so a compromised side car does not inherit the app tier's database identity; the default developer path is untouched.
- **Cons**: The profile adds three containers and a bootstrap step, so `docker compose up` is no longer the whole story; certificates expire, and an unavailable CA at issuance time is a startup hazard (services start from their last cached leaf, which the runbook requires); PostgreSQL key files must be owned by its container uid, which is why issuance runs as root with a narrow capability set; Keycloak's `start` mode is stricter about hostname than `start-dev` and needs `KC_HOSTNAME_STRICT=false` for the two-name back-channel; and the browser now needs the internal CA trusted to reach the Keycloak login page on `https://localhost:8080`.
- **Residual risk**: the CA root key lives on the host it protects, so host or root compromise defeats the whole control — the honest gain is against credential replay from another workload, not against an attacker who already owns the machine. A compromised `gateway` or `worker` still holds its own key and can authenticate as itself. OmniRoute and OTLP remain plaintext, and `pgadmin`/`redis-ui` are excluded. There is no revocation list and no short-lived token exchange (SPIFFE-style), so a stolen leaf is valid until `notAfter`. The `24h` default is a compromise between exposure and the availability hazard of frequent issuance, not a measured optimum.
