# ADR-017: Runtime Detection with Falco

**Status:** Accepted  
**Date:** 2026-11-11  
**Last modified:** 2026-11-11

## Context

The stack hardens containers at creation and then stops observing. `cap_drop: ALL`, `no-new-privileges`, a non-root uid and `init: true` limit what a process may do, but nothing records what it actually does after start. The audit ledger proves which guarded actions the application chose to report; it cannot see a shell spawned inside the gateway, a worker writing outside its workspace, or a connection the gateway opens to an address outside the documented routing path. The threat model's T10 is post-hoc chain verification and T11 is build-time supply chain, so a compromised or misbehaving container has no runtime witness.

Falco is the smallest control that closes that gap without changing application code. It observes syscalls from the host kernel and evaluates a rule set, so it sees the process tree, files opened for write and sockets connected, including activity that never reaches the application's audit path. The cost is a privilege carve-out: the modern eBPF probe needs `CAP_BPF` and `CAP_PERFMON`, which Docker does not grant through `cap_add`, so the service runs privileged. That is a larger grant than any other service in the stack, and it is why the control is opt-in and confined to one container.

The deployment target matters for verification. On a native Linux host the probe sees host-wide syscalls and `/proc` metadata. On Docker Desktop the kernel behaviour differs: the `/dev` mount is required, `pid: host` prevents event delivery, and `/proc` lookups for process parent and command line can return `<NA>`. The rule set is written for the native host; the Docker Desktop path verifies the syscall rules but not the `/proc`-dependent allowlist entries. The ADR records that boundary rather than claiming uniform behaviour.

## Decision

1. **One opt-in service, pinned by digest.** `docker-compose.yml` defines `falco` with `profiles: [security]`, image `falcosecurity/falco:0.45.2` pinned by manifest-list digest, `privileged: true`, `restart: unless-stopped` and no ports. `docker compose up -d` does not start it; `docker compose --profile security up -d falco` does. The modern eBPF engine is selected with `-o engine.kind=modern_ebpf`; the probe is embedded in the image, so no kernel module is built or loaded.

2. **Kernel visibility is read-only.** The service mounts the host `/proc`, `/etc`, `/dev` and `/sys/kernel/tracing`; only `/proc`, `/etc` and tracefs are read-only. `/dev` is required by the documented container invocation and is the difference between a probe that emits events and one that does not on Docker Desktop. `pid: host` is deliberately absent: it was tested and suppressed all events on this host. The privileged flag is the single documented carve-out from the `cap_drop: ALL` baseline.

3. **Container metadata comes from the engine socket, read-only.** The Docker socket is mounted at `/host/var/run/docker.sock:ro`, which is where the image's container-plugin configuration looks. This is the only service with the socket; the image scanner (ADR-016) deliberately has none. The trade-off is explicit: a socket is host-root-equivalent, but Falco is already privileged, and the alternative is `container.id` without a name, which makes an alert unactionable. Alert conditions match `container.name` prefixes (`bastion-agent-gateway`, `bastion-agent-worker`) and `container.image.repository`, never a compose-assigned `container_name` that the app tier does not set.

4. **Six rules cover the behaviours the design assumes.** `config/falco/bastion_rules.yaml` defines: a shell in an application container; a worker write outside the tool workspace (`/tmp` is scratch, `/dev`, `/proc`, `/sys` and `/run` are runtime paths); gateway egress outside the internal port allowlist (53, 4317, 4318, 5432, 6379, 8000, 8080, 20128); a shell or `nsenter` in `db`/`redis`; a write to `/etc/passwd`, `/etc/shadow` or `/etc/sudoers`; and a write under `/app` in the application image. `-o rule_matching=all` is set because Falco's default `first` would hide the second rule that matches one event.

5. **Alerts carry machine metadata only.** Output fields are `container.name`, `container.image.repository`, `proc.pid`, `proc.name`, `proc.pname`, `fd.name` and `fd.sport`. `proc.cmdline`, `proc.args`, `proc.env` and `evt.buffer` are excluded: a shell's command line can carry a tool argument or a secret, and a runtime detector must not become a second place where prompt or argument text lands. `tests/test_falco.py` asserts the exclusion on every rule.

6. **JSON to a mounted file, plus stdout.** `json_output=true`, `syslog_output.enabled=false`, and `file_output` writes `artifacts/falco/events.json`; the same JSON lines go to the container log. The file is gitignored with a tracked `.gitkeep`, like the eval, gate, threat-intel and compliance artifacts. The OTel collector is not used: it defines only a traces pipeline, and adding a `filelog` receiver plus a logs pipeline is a separate change with its own retention and privacy decision. Alerts do not become audit-ledger rows because `AuditEventType` is frozen (ADR-007 decision 7) and a detector's output is evidence, not a business event.

7. **Allowlist entries are reviewed, not implicit.** Baseline exceptions live under `exceptions:` and each one must appear in `config/falco/ALLOWLIST.md` with a one-line justification and a review date; a test fails when an entry is missing or its date has passed. The current entries are the `db`/`redis` `docker-entrypoint.sh` startup and their `pg_isready`/`redis-cli` healthcheck shells. The application healthcheck is the exec form (`CMD ["python", "-c", ...]`), so it spawns no shell and needs no entry.

8. **Verification is a command, not a badge.** `scripts/falco_smoke.sh` starts the profile, waits for the syscall source, triggers a shell, a worker write outside the workspace and a gateway egress, asserts each rule fired, then asserts that a workspace write and an allowed database connection stay silent and that no secret value or process-argument field reached the alert file. The script is the documented proof; the compose contract, rule set and allowlist are also pinned by `tests/test_falco.py`.

## Consequences

- **Pros**: Runtime behaviour is observable without application changes; the carve-out is one opt-in container instead of a host-wide agent; alert output is deliberately metadata-only; the allowlist cannot rot silently; the rules map to the stack's actual process, file and network expectations; the default stack and the unprivileged CI job are unchanged.
- **Cons**: A privileged container is a larger grant than any other service and can be disabled by a host-root attacker; the Docker socket is mounted read-only for one service; alerts are high-volume on a busy host and need tuning; the Docker Desktop path cannot resolve `/proc` metadata, so the entrypoint and healthcheck exceptions are ineffective there and the data-container rule is noisy at container start; event capture depends on kernel tracepoints/fentry that vary by host; and `artifacts/falco/events.json` has no rotation, so it grows until the operator rotates it.
- **Residual risk**: Falco detects and does not contain; there is no kill, quarantine or paging integration; no SIEM or alert routing; no host IDS covering the Docker host outside containers; the `/tmp` allowance in the worker rule means a write to `/tmp` outside `TOOL_WORKSPACE_ROOT` is not alerted (the tool layer is the primary control); and an attacker who can stop or reconfigure the Falco container removes the witness. `THREAT_MODEL.md` records the control as opt-in and `COMPLIANCE.md` no longer claims 24/7 monitoring that no component performs.
