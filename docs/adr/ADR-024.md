# ADR-024: A Scoped Completion Cache in Front of the Model Call

**Status:** Accepted
**Date:** 2026-11-18
**Last modified:** 2026-11-18

## Context

Every guarded turn ends in a model call: after DLP, classification and routing,
`gateway/routers/chat.py` asks `ModelRouter.complete` for an answer and nothing
can short-circuit it. The same question asked twice, or asked again in slightly
different words, pays full inference twice. On this host that means two turns
queue behind one GPU (ADR-004), and every duplicate `PUBLIC` conversation is a
billed cloud completion. The cost and latency are real and the fix looks simple:
remember the answer.

The repository's posture is against careless caching. `gateway/routers/audit.py`
records that responses containing PII markers are never cached, the token vault
under ADR-002 mints session-scoped `{{ENTITY:...}}` markers, and ADR-012 makes
egress — canary tripwire, fencing, marker restore — the stage that decides what
the caller actually receives. A cache bolted on before those stages would be a
second, unaudited answer path, and a similarity threshold is a false-positive
budget: a hit on a question that only looks the same serves a confident wrong
answer with no way for the caller to tell.

Three choices had to be made for this first slice. Similarity is computed
on-box and deterministically — no embedding call may carry prompt text off the
perimeter, and the component must work for `CONFIDENTIAL` prompts as well as
public ones. The store is the Redis instance the stack already runs, because a
per-process dict would silently stop saving anything the moment the gateway is
scaled to two replicas. And the cache ships off by default, because a wrong hit
is worse than a duplicate call and its behaviour has to be measured before it is
turned on.

## Decision

1. **A cache stage between routing and completion.**
   `gateway/routers/chat.py` looks up after
   `ROUTING_DECISION` and before `_complete`, so the alias and classification
   label are known and the DLP row for the turn is already written. A hit
   synthesises a `ChatCompletion` (`model: "semantic-cache"`) and continues
   through the normal egress and delivery stages.

2. **The scope is the key.** One Redis key per combination of tenant, model
   alias and classification label
   (`semantic_cache:v1:<tenant>:<alias>:<label>`). Identical prompt text stored
   under `cloud-primary`/`PUBLIC` is invisible to `local-llama`, to a
   `CONFIDENTIAL` turn and to every other tenant. The client cannot choose or
   widen the scope: `tenant_id` comes from the authenticated context and the
   alias/label from the router's own decision.

3. **A turn that minted DLP markers is never stored and never served.** Markers
   are session-scoped; a cached answer containing `{{ENTITY:PERSON_1}}` minted in
   another session would be delivered unresolved. The stage therefore skips the
   cache when the DLP stage found entities, refuses to store an answer that
   matches `TOKEN_PATTERN`, and re-checks a candidate before serving it. This is
   conservative on purpose: the turns with the most duplication are also the
   turns whose answers carry session state.

4. **A hit is still a full turn.** Egress runs on the cached text exactly as on
   a model answer — the canary tripwire still fires, the marker restore still
   runs, and `EGRESS_FILTERED` is still written. The only ledger difference is
   `cache_hit` in the `RESPONSE_SENT` metadata and `bastion.cache.hit` on the
   span. Nothing is answered without an `INPUT_RECEIVED`, `DLP_REDACTION`,
   `ROUTING_DECISION` and `EGRESS_FILTERED` row already in the chain.

5. **Similarity is injectable; the default is deterministic and on-box.** The
   default backend is Jaccard over lowercased word sets. It is a placeholder for
   a local embedder, not a semantic model: it catches retyped and re-ordered
   questions and misses true paraphrases, which keeps the false-positive budget
   tight. `SEMANTIC_CACHE_SIMILARITY_THRESHOLD` (default `0.9`),
   `SEMANTIC_CACHE_TTL_SECONDS` (default `300`) and
   `SEMANTIC_CACHE_MAX_ENTRIES` (default `50` per scope) are settings keys, and
   `SEMANTIC_CACHE_ENABLED` is `false` at the shipped default.

6. **The cache is not a control and fails open.** A Redis read or write error
   logs and falls through to a model call; it never fails a turn. What it must
   never do is serve across a boundary: tenant, alias, label and marker rules are
   enforced on every lookup, not only at store time.

7. **Measured on the shipped code path**
   (`uv run python scripts/benchmark_semantic_cache.py`, 10-prompt corpus replayed
   three times, 25 ms simulated model): cache off — 0 % hits, 30 model calls,
   p50 25.25 ms, p95 25.31 ms; cache on — 66.7 % hits, 10 model calls, p50
   0.04 ms, p95 25.40 ms. The p95 is a miss: the benchmark makes the trade-off
   explicit — duplicates get cheap, the slowest turn does not get faster.

## Consequences

**Pros**

- Duplicate and retyped questions cost a Redis read instead of an inference
  call; on this corpus that removes two thirds of the model calls.
- The scope and the marker rule make a cross-tenant or cross-classification
  answer impossible by construction, not by a filter applied afterwards.
- A hit remains fully audited and still passes egress, so the ledger and the
  canary keep the meaning they had.
- Everything is settings-driven and off by default; the similarity backend is an
  injected protocol, so a local embedder can replace token overlap without
  touching the stage.

**Cons**

- Word-set Jaccard is not semantics. A genuine paraphrase usually misses, and a
  short question that shares most of its words with another can hit; the
  threshold is a false-positive budget the operator has to accept, and the
  measured near-miss case is the one to watch, not the hit rate.
- A cache hit re-runs egress but never re-runs the model, so a change in the
  upstream model's behaviour is invisible to cached turns until the TTL expires.
- The scope never shares answers across principals inside a tenant, which is
  where most of the remaining saving would be and the largest leak surface; that
  decision is deliberately not taken here.
- The cache is a PII-adjacent store: post-redaction answers without markers,
  short TTL, bounded entries. It is not a PII store, but it is not nothing and
  the TTL is the only thing that removes an entry early.
- The lookup costs a Redis round trip on every enabled turn, so the median turn
  gets faster only on a hit and slightly slower on a miss.
