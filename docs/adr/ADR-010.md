# ADR-010: Guarded Tool Execution & Resume State Machine

**Status:** Accepted  
**Date:** 2026-11-09  
**Last modified:** 2026-11-09

## Context

Tool calls cross two processes with different trust and latency profiles. The gateway decides approvals in a browser session; the ARQ worker owns execution, because a mutating tool may be slow and must not run inside an HTTP request. A suspended call also outlives the request that created it: the initiating client is gone by the time a second operator approves.

The approval must therefore be durable and bound to the exact request. If the worker simply re-read the tool name and re-ran it after approval, the stored arguments could be swapped between decision and execution (TOCTOU), a crashed worker could lose an approval, and a retried job could run a write twice. The state machine and its audit trail are the mechanisms that make the handoff safe.

## Decision

1. **One state machine, two processes**: `agent/tools/execution.py` implements `request_tool_execution` (authorize, execute or suspend) and `resume_approved_tool` (execute an approved ticket). The gateway and the worker import the same functions, so policy and audit behaviour cannot drift.

2. **Declaration-time policy**: `@tool(name, description, read_only, required_role)` validates the handler is async, declares a `context: AgentContext`, and annotates every JSON argument as `str`, `int`, `float` or `bool`. Mutating tools must declare a `required_role`; that role is what a second operator must hold to approve. Role-denied tools are filtered out of `available_tools(roles)` rather than offered and then rejected.

3. **One identity namespace**: `PendingApproval.initiator_id` and `approver_id` are both the OIDC subject (`sub`). The dashboard derives `actor_id` from the validated token, and the agent must enqueue tool jobs with the same value. Usernames or emails are never used for the four-eyes comparison, because two different spellings of the same person would defeat it.

4. **Immutable request binding**: suspension stores a `PendingApproval` row whose `request_fingerprint` is a canonical SHA-256 of `(tool, arguments)`, plus an HMAC-SHA256 capability token over `(ticket id, fingerprint, expiry)`. Only the token hash is persisted. On resume the fingerprint is recomputed from the stored arguments and compared in constant time; a mismatch marks the ticket `FAILED`, records a `SECURITY_INCIDENT`, and executes nothing.

5. **Read-only fast path**: tools with `read_only=True` execute inside the worker job as soon as RBAC permits, with no ticket and no human in the loop. A read-only tool that declares no role is open to any authenticated principal holding at least one known role.

6. **Resume is locked and idempotent**: `resume_approved_tool` selects the ticket `FOR UPDATE`. Terminal states (`EXECUTED`, `REJECTED`, `EXPIRED`, `FAILED`) return without re-running; a pending ticket past its expiry is closed as `EXPIRED`; only `APPROVED` executes. The row stays `APPROVED` until the tool returns, so a worker crash re-runs the call on the next sweep (at-least-once; tools must tolerate retries). The approver must exist and differ from the initiator, re-checked at resume.

7. **Durable handoff with a safety net**: the approval route commits the decision, then enqueues `resume_tool_job` with the deterministic job id `resume:<ticket_id>`. If Redis is unavailable the approval still commits; the worker's `resume_approved_tickets_job` cron sweep (every 30 s) executes approved tickets that no job picked up. `expire_stale_approvals_job` closes lapsed tickets so the queue only lists actionable work; the ticket history remains in the audit ledger, and until the sweep runs the dashboard shows the ticket as expired and locked. `TOOL_RESUME_AUTO_ENQUEUE=false` disables the push path without changing decisions.

8. **Audit in the same transaction**: `TOOL_REQUESTED` (accepted or denied), `APPROVAL_REQUESTED`, `TOOL_EXECUTED` (ok or failed) and `SECURITY_INCIDENT` are appended alongside the state change. `metadata_json` carries tool name, outcome, duration, role, argument *keys* and identifiers; argument values are covered by `payload_hash` only. The audit ledger therefore outlives the DLP vault without retaining PII.

9. **Filesystem confinement**: built-in file tools resolve every path inside `TOOL_WORKSPACE_ROOT` using `Path.resolve()`, reject absolute and traversing paths and symlink escapes, cap reads and writes by size, and write atomically with `os.replace` at mode `0600`. Blocking IO runs in a worker thread.

## Consequences

- **Pros**: A write can only run after a second operator approves the exact bytes that were requested; the fingerprint check defeats argument swaps; the row lock makes retries safe; approvals survive Redis outages and worker restarts; the gateway never executes mutating tools; one implementation and one audit vocabulary cover both processes.
- **Cons**: Execution is at-least-once, so mutating tools must be idempotent or tolerate retries; a slow tool holds its row lock for the duration; tickets add a round trip through Redis in the normal path; the workspace root is a single shared directory rather than per-actor isolation.
