# ADR-005: Cryptographic Audit Trail & Hash Chaining

**Status:** Accepted  
**Date:** 2026-11-09  
**Last modified:** 2026-11-12

## Context

Bastion-Agent must produce an audit trail that is tamper-evident and suitable for compliance (SOC 2, ISO 27001, internal investigations). The audit log must record every security-relevant event with immutable, verifiable links.

The ledger lives in PostgreSQL 16 alongside the approval queue, so it inherits the database's transactional guarantees but also its failure modes: a compromised application credential must not be able to rewrite history, and verification must work from a plain table dump without trusting the application. The cost is an extra row-level trigger on writes and a table that grows forever unless retention is added.

## Decision

1. **PostgreSQL `audit_logs` table** (append-only, enforced by a trigger):

   ```sql
   CREATE TABLE audit_logs (
       id            BIGINT PRIMARY KEY,        -- from audit_logs_id_seq, allocated in the append txn
       timestamp     TIMESTAMPTZ NOT NULL,
       session_id    VARCHAR(128),              -- nullable: process-level events have no session
       tenant_id     VARCHAR(64) NOT NULL,      -- access scope, from the authenticated identity (ADR-015)
       actor_id      VARCHAR(128) NOT NULL,
       event_type    VARCHAR(32) NOT NULL,      -- INPUT_RECEIVED, DLP_REDACTION, ...
       payload_hash  CHAR(64) NOT NULL,         -- SHA-256, lowercase hex
       metadata_json JSONB NOT NULL DEFAULT '{}',
       previous_hash CHAR(64) NOT NULL,
       record_hash   CHAR(64) NOT NULL UNIQUE
   );
   ```

   The identifier is allocated from a sequence **inside** the append transaction because the hash covers it; hashes are stored as lowercase hex text so the `CHECK` constraints and equality comparisons stay exact. `tenant_id` is an access scope added by ADR-015, not an input to `record_hash`; the append-only trigger still prevents reassigning it.

2. **`record_hash` computation** at insertion time, in Python (`db.models.compute_record_hash`):

   ```
   record_hash = SHA256(
       id || '|' ||
       timestamp_iso8601_utc_microseconds || '|' ||
       actor_id || '|' || event_type || '|' ||
       payload_hash || '|' || previous_hash
   )
   ```

   Fields are joined with `|` so boundaries are unambiguous. The timestamp is rendered as ISO-8601 UTC with microsecond precision, which is exactly what PostgreSQL `timestamptz` preserves — the hash recomputed from a row read back always matches. The first record uses `GENESIS_HASH = "0" * 64`.

3. **Append-only enforcement**: a `BEFORE UPDATE OR DELETE` row trigger (`trg_audit_logs_append_only`) raises `insufficient_privilege`, so immutability does not depend on application discipline. Integrity tests and break-glass maintenance opt out per transaction with `SELECT set_config('bastion.allow_audit_mutation', 'on', true);`. `TRUNCATE` remains possible only as an explicit DDL reset.

4. **Verification**: `db.audit.verify_audit_chain` walks the ledger in id order and checks every hash and link (full table or the most recent N rows). The `/api/audit/verify` endpoint that exposes it lands with the dashboard (ADR-007, phase 1).

5. **Retention**: Audit logs retained per compliance policy (e.g., 7 years). PostgreSQL partitioning by year; cold data moved to archival storage. Not implemented in v0.1 — scheduled for v0.3 (async audit export) / v0.5 (compliance mode).

6. **No plaintext PII in audit logs**: All entity values are tokenized before logging. If the raw prompt must be stored (e.g., for debugging), it is encrypted at rest with KMS-managed keys and access-limited to `admin` role.

7. **Pre-production payload escrow** (`payload_escrow`, IDEA-016): decision 6's "no plaintext PII in audit logs" still holds for `audit_logs`, which remains hash-only and append-only. This decision supersedes that posture only for a **separate** table, and only outside production:

   - Every chat turn's `INPUT_RECEIVED` record is the one event whose `payload_hash` is the digest of user text (`DLP_REDACTION`, `ROUTING_DECISION` and `EGRESS_FILTERED` pass machine metadata only). When `PAYLOAD_ESCROW_ENABLED=true`, the writer stores the **raw pre-DLP payload** — the exact bytes that were hashed — as AES-256-GCM ciphertext in `payload_escrow`, keyed by `audit_logs.id`. Nothing else is escrowed: the post-DLP text is reproducible offline from the raw input with the same DLP build, and the delivered model text would need its own event and decision.
   - The row carries a per-record 12-byte nonce, `audit_logs.payload_hash` (copied so a decrypt is verifiable alone), `tenant_id`, `kind = input_raw`, `created_at` and `expires_at`. The AEAD associated data is `escrow-v1|audit_log_id|payload_hash|tenant_id|kind`, so a ciphertext copied to another record, tenant or hash fails authentication. The writer refuses a payload whose digest differs from the ledger's.
   - The master key is `PAYLOAD_ESCROW_MASTER_KEY` when set, otherwise an HKDF-SHA256 subkey of `VAULT_MASTER_KEY` under the fixed label `bastion-payload-escrow-v1`. No key material is committed, and the escrow never reuses the vault key itself.
   - Retention is `PAYLOAD_ESCROW_TTL_SECONDS` (24 h by default), deliberately far shorter than the ledger's retention in decision 5. Expiry **deletes** the row; no tombstone is kept, because the surviving evidence is the ledger record (id, actor, event, `payload_hash`, `record_hash`). The worker purges every 15 minutes and `scripts/purge_payload_escrow.py` does it on demand.
   - Read access is `admin` only, requires an explicit `POST /api/audit/{record_id}/escrow`, is tenant-scoped, and appends `ESCROW_ACCESSED` with the record id, actor and outcome. The plaintext is never logged. A `readonly` or `analyst` principal is refused before the handler, so no audit row can claim a read that did not happen.
   - The flag defaults off and `ENVIRONMENT=production` with `PAYLOAD_ESCROW_ENABLED=true` **refuses to start**. Enabling it is a deliberate pre-production debugging decision, not a production control.

   Trust boundary: an operator who can set the flag and reach the database can, for the retention window, recover the plaintext that the ledger deliberately hashed. The key lives in the process environment; the database alone is not enough. The table is a PII store and its access (role membership, backups, replicas) must be reviewed on the same cadence as the vault key. `payload_hash`, `record_hash`, the previous-hash links and `verify_audit_chain` are byte-identical with the flag on and off; the escrow writer never touches `audit_logs`.

8. **Delivered-answer persistence** (`RESPONSE_SENT`, IDEA-029): decision 7 recovered what the model *saw*; this decision records what the caller *received*.

   - After egress inspection and token restore, and only when `egress.blocked` is false, the turn appends one `RESPONSE_SENT` row whose `payload` is the sanitized delivered text (or its configured prefix). Its `payload_hash` therefore covers exactly what the caller saw. A canary-blocked or injection-refused turn returns before this point and writes no answer row.
   - Metadata carries `model`, `route`, `chars`, `stored_chars` and `truncated`; never the text. `RESPONSE_STORE_MAX_CHARS` (32,768 by default) bounds both the hash and the escrow copy. An answer over the cap is stored as its prefix with `truncated: true`, so the digest never silently covers less than the metadata claims.
   - With `PAYLOAD_ESCROW_ENABLED=true`, the same row gets an `egress_delivered` escrow copy: AES-256-GCM, per-record nonce, AAD bound to `audit_log_id|payload_hash|tenant_id|kind`, the same key derivation, the same 24-hour TTL and purge, and the same admin-only `POST /api/audit/{id}/escrow` read with an `ESCROW_ACCESSED` row. The kind is part of the AAD, so an input ciphertext cannot be relabelled as an answer or vice versa.
   - The row is written in its own committed transaction after `inspect()` and before the response is returned. It proves a delivery happened even when the answer is empty; without escrow it remains hash-only and proves delivery without content.

   Trust boundary: when escrow is on, the answer is a second PII store, because `egress.text` already contains the markers restored by the vault. When it is off, the row adds no recoverable plaintext. The delivered text is the model's own output, not a verified statement; its presence in the ledger is evidence of what the caller was shown, not of truth.

## Consequences

- **Pros**: Tamper-evident by construction; cryptographic verification is fast; the trigger prevents accidental or malicious mutation, not just application bugs; the chain can be verified over years without the original DB dump; integrates with compliance reporting.
- **Cons**: Slight write overhead (negligible vs request latency); verification requires scanning the table; storing metadata_json can bloat the table (use JSONB cautiously). The optional pre-production escrow is a PII store with a recoverable key: anyone with the process environment and the database could recover prompt text for the retention window, which is exactly why production refuses to enable it and why the window is 24 hours rather than the ledger's years.
