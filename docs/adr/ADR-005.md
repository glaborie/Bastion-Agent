# ADR-005: Cryptographic Audit Trail & Hash Chaining

**Status:** Accepted  
**Date:** 2026-11-09  
**Last modified:** 2026-11-11

## Context

Bastion-Agent must produce an audit trail that is tamper-evident and suitable for compliance (SOC 2, ISO 27001, internal investigations). The audit log must record every security-relevant event with immutable, verifiable links.

The ledger lives in PostgreSQL 16 alongside the approval queue, so it inherits the database's transactional guarantees but also its failure modes: a compromised application credential must not be able to rewrite history, and verification must work from a plain table dump without trusting the application. The cost is an extra row-level trigger on writes and a table that grows forever unless retention is added.

## Decision

1. **PostgreSQL `audit_logs` table** (append-only, enforced by a trigger):

   ```sql
   CREATE TABLE audit_logs (
       id            BIGINT PRIMARY KEY,        -- from audit_logs_id_seq, allocated in the append txn
       timestamp     TIMESTAMPTZ NOT NULL,
       session_id    VARCHAR(128),              -- nullable: process-level events have no session
       tenant_id     VARCHAR(64) NOT NULL,      -- access scope, from the authenticated identity (ADR-015)
       actor_id      VARCHAR(128) NOT NULL,
       event_type    VARCHAR(32) NOT NULL,      -- INPUT_RECEIVED, DLP_REDACTION, ...
       payload_hash  CHAR(64) NOT NULL,         -- SHA-256, lowercase hex
       metadata_json JSONB NOT NULL DEFAULT '{}',
       previous_hash CHAR(64) NOT NULL,
       record_hash   CHAR(64) NOT NULL UNIQUE
   );
   ```

   The identifier is allocated from a sequence **inside** the append transaction because the hash covers it; hashes are stored as lowercase hex text so the `CHECK` constraints and equality comparisons stay exact. `tenant_id` is an access scope added by ADR-015, not an input to `record_hash`; the append-only trigger still prevents reassigning it.

2. **`record_hash` computation** at insertion time, in Python (`db.models.compute_record_hash`):

   ```
   record_hash = SHA256(
       id || '|' ||
       timestamp_iso8601_utc_microseconds || '|' ||
       actor_id || '|' || event_type || '|' ||
       payload_hash || '|' || previous_hash
   )
   ```

   Fields are joined with `|` so boundaries are unambiguous. The timestamp is rendered as ISO-8601 UTC with microsecond precision, which is exactly what PostgreSQL `timestamptz` preserves — the hash recomputed from a row read back always matches. The first record uses `GENESIS_HASH = "0" * 64`.

3. **Append-only enforcement**: a `BEFORE UPDATE OR DELETE` row trigger (`trg_audit_logs_append_only`) raises `insufficient_privilege`, so immutability does not depend on application discipline. Integrity tests and break-glass maintenance opt out per transaction with `SELECT set_config('bastion.allow_audit_mutation', 'on', true);`. `TRUNCATE` remains possible only as an explicit DDL reset.

4. **Verification**: `db.audit.verify_audit_chain` walks the ledger in id order and checks every hash and link (full table or the most recent N rows). The `/api/audit/verify` endpoint that exposes it lands with the dashboard (ADR-007, phase 1).

5. **Retention**: Audit logs retained per compliance policy (e.g., 7 years). PostgreSQL partitioning by year; cold data moved to archival storage. Not implemented in v0.1 — scheduled for v0.3 (async audit export) / v0.5 (compliance mode).

6. **No plaintext PII in audit logs**: All entity values are tokenized before logging. If the raw prompt must be stored (e.g., for debugging), it is encrypted at rest with KMS-managed keys and access-limited to `admin` role.

## Consequences

- **Pros**: Tamper-evident by construction; cryptographic verification is fast; the trigger prevents accidental or malicious mutation, not just application bugs; the chain can be verified over years without the original DB dump; integrates with compliance reporting.
- **Cons**: Slight write overhead (negligible vs request latency); verification requires scanning the table; storing metadata_json can bloat the table (use JSONB cautiously).
