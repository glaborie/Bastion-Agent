# ADR-020: Per-Principal Inference Token Budget

**Status:** Proposed
**Date:** 2026-11-14
**Last modified:** 2026-11-14

## Context

ADR-013 bounded request rate and ended decision 7 with "per-principal token and
cost budgets remain future work; this ADR bounds request rate, not spend per
window". `THREAT_MODEL.md` T12 still says the same thing, and its roadmap entry
3 is "Add per-principal token and cost budgets (T12)". The gap is not cosmetic:
`POST /v1/chat` accepts up to 64 messages and 65,536 characters of prompt
(`MAX_MESSAGES`, `MAX_TOTAL_CHARS`) with `max_tokens` up to 8,192, so one turn
may spend orders of magnitude more than another while both cost one of the
chat bucket's 120 requests per minute. The existing bucket prices a three-word
question and a maximum-size turn identically, so a principal inside its request
budget has no spending bound at all.

Three constraints shape the answer. The gateway is horizontally scaled, so the
budget has to live in Redis beside the existing bucket rather than in process
state (ADR-013 decision 1). Spend is only known *after* the call: `ChatCompletion`
carries `prompt_tokens`, `completion_tokens` and `total_tokens`, each optional,
and `usage.cost` is optional too — so the unit cannot be dollars without a price
table no component owns. And the request-count dependency cannot enforce it,
because it runs before DLP, before the injection gate and before the router
applies `max_tokens`; a second control has to sit inside the handler, at the
point where the upstream payload is final.

This record is **Proposed, not implemented**: `gateway/rate_limit.py` still
charges exactly one token per request and ADR-013 remains the only enforced
budget. Building it is backlog work at the v0.3 phase; when it lands,
`THREAT_MODEL.md` T12 must be re-scored with `scripts/recalculate_dread.py` and
the rate-limiting line in `CONTROL.md` updated with it, in the same change.

## Decision

1. **A third limiter scope, `chat_tokens`, on the same store and script.** The
   key is `ratelimit:chat_tokens:<jwt-sub>`, so it inherits Redis `TIME`, the
   continuous refill, and the expiry-on-full behaviour of `_BUCKET_SCRIPT`.
   Capacity is the new setting `rate_limit_chat_tokens_per_window`, default
   **100,000 tokens per `rate_limit_window_seconds`** (60 s), validated positive
   with the other `rate_limit_*` fields. `RateLimiter.consume` takes a `cost`
   argument instead of the hardcoded `"1"`; the `dashboard` and `chat` request
   scopes keep passing 1.

2. **Reserve the worst case before dispatch, settle the actual after.** The
   reservation is the estimated prompt tokens — conservative `ceil(chars / 4)`
   plus 4 tokens per message, computed over the post-DLP, canary-fenced
   `upstream` list, which is the text actually sent — plus `max_tokens`. It is
   taken in `gateway/routers/chat.py` after the injection gate and after
   `sanitizer.canary_for`, immediately before `model_router.complete`, so a
   prompt refused by the injection gate or the egress circuit breaker spends
   nothing. If the reservation does not fit, the turn fails with `429`, the
   token bucket's `RateLimit-*` fields, `Retry-After`, and detail
   `token budget exhausted`; the model is not called.

3. **`max_tokens` always has a value.** `ChatRequest.max_tokens` becomes
   `int = Field(default=1024, ge=1, le=8192)` and is always sent upstream. A
   reservation computed against a provider-side default could not be
   reconstructed, and that default can change under the gate.

4. **Settlement may leave the bucket in debt.** A settlement path adds
   `actual - reserved` where `actual` is `total_tokens`, else
   `prompt_tokens + completion_tokens`, and it must accept a negative result.
   `_BUCKET_SCRIPT` refuses any `cost` above the balance, which is correct for
   admission and wrong for reconciling a completed call. Debt is cleared by
   refill, so the next turn is refused until the window repays it. The balance
   floors at `-capacity`, so a provider reporting a bogus usage figure cannot
   empty many windows at once.

5. **Unknown usage is charged at the reservation.** If `usage` is absent, there
   is no refund. Under-billing silently rewards omitting the field, and the
   gateway cannot distinguish omission from a zero-cost turn.

6. **A settle failure does not fail the turn.** If Redis is unreachable after
   the model answered, the answer is delivered, the failure is logged and
   flagged as `bastion.rate_limit.settle_failed` on the model span. Failing the
   response would not recover the spend and would cost the operator a completed
   turn; the following request fails closed at the request dependency with
   `503` (ADR-013 decision 6).

7. **The unit is tokens; cost stays telemetry.** `usage.cost` continues to reach
   the model span as `gen_ai.usage.cost` and does not gate. Tokens are the unit
   both backends report, and a dollar budget would need a maintained price table
   plus handling for routes that omit cost.

8. **Observability, not evidence.** Reservation, settlement and the resulting
   balance are span attributes (`bastion.rate_limit.tokens_requested`,
   `bastion.rate_limit.tokens_consumed`, `bastion.rate_limit.remaining`) —
   counts only, never prompt text (ADR-014). A refusal logs subject, request id,
   reservation and remaining balance; it writes no audit row, matching the
   existing 429 path.

9. **The algorithm is tested where the script runs.** Reserve, settle, debt,
   floor and refill cases extend `tests/test_rate_limit_redis.py` against live
   Redis 7 (`REDIS_TEST_URL`); the estimator arithmetic and the 429 contract
   extend `tests/test_rate_limit.py` with the existing stub limiter; and
   `tests/test_chat.py` covers the reserve-then-settle order and that a blocked
   or refused turn never reaches `model_router.complete`.

## Consequences

- **Pros**: a turn is charged to the principal that caused it, in the unit the
  router already reports, so a chat-heavy principal can no longer buy unlimited
  inference with 120 cheap requests; the worst-case reservation means a
  principal cannot overspend inside a single turn; the control reuses the Redis
  bucket, the settings surface, the refusal contract and the fail-closed
  dependency already established by ADR-013, so it adds no store and no new
  failure mode on the dashboard path; bursts after idle periods stay possible.
- **Cons**: the reservation is an estimate, so a prompt whose token density
  beats `chars / 4` (CJK, base64, minified JSON) settles as debt rather than
  being refused up front, and `chars / 4` over-reserves English, refusing a turn
  that would have fitted; a refused turn still spends one token of the `chat`
  request bucket because that dependency runs first; a settle blip under-books
  one turn by up to its reservation and leaves only a log line; the chat path
  gains a second Redis round trip; and the budget is still per principal in
  tokens, so a principal pinned to an expensive model gets the same allowance as
  one on the local model — dollar exposure narrows but is not closed, and there
  is still no per-tenant aggregate.
