# ADR-025: An Opt-In Availability Monitor Behind the `infra` Profile

**Status:** Accepted  
**Date:** 2026-11-18  
**Last modified:** 2026-11-18

## Context

Every service in `docker-compose.yml` that can be probed declares a healthcheck: `gateway`, `db`, `redis`, `keycloak`, `omniroute` and `llama-cpp`. Those checks do two things and stop: they gate a `depends_on` condition during startup and they colour a row in `docker compose ps`. A container that dies at 03:00 therefore produces no record and no signal. The state is discoverable only by a human typing `docker compose ps` the next morning, and the interval between the death and that command is invisible by construction — `ps` cannot show what it did not see. The OTel pipeline (ADR-014) is the only runtime telemetry in the stack, and it deliberately carries payload-free request spans: no availability, no restarts, no history.

Two obvious designs were rejected. Reading Docker engine health would report exactly what Compose already knows, but it requires the Docker socket, which is host-root-equivalent; this stack runs its app tier with `cap_drop: ALL` and `no-new-privileges`, and ADR-017 already spends the one socket exception on Falco to make its alerts carry container names. A Prometheus/Grafana pair would need a metrics endpoint the gateway does not serve (the `/metrics` claim in `wiki/API-Reference.md` is stale) and would turn "is redis reachable" into "is the metric fresh", which is a different question. What is missing is a history of reachability from a client's point of view, not a metrics store.

The repository also had no convention for a non-default profile. `pgadmin`, `redis-ui`, `compliance` and `security` each appeared one at a time, and PKI is a separate overlay. A monitoring sidecar needs a name that says why it is off by default and what it observes, because the alternative — quietly folding it into a default service's profile — leaves the next operator guessing. ADR-001 decision 1 excludes sidecar proxies, so the record also has to say plainly that an observing sidecar is not a proxy and carries no request traffic.

## Decision

1. **Uptime Kuma runs as one digest-pinned sidecar behind the `infra` profile.** The service is `uptime-kuma` in `docker-compose.yml`, image `louislam/uptime-kuma:2.5.12` pinned by manifest-list digest, with a named `uptimekuma_data` volume at `/app/data`, a single `127.0.0.1:${UPTIME_KUMA_PORT:-3002}:3001` mapping, `cap_drop: ALL`, `no-new-privileges:true`, `restart: unless-stopped`, and no ports on any other interface. It runs as the image's `node` uid (`user: "${UPTIME_KUMA_UID:-1000}:..."`) because the image's data directory is owned by that uid: as root with every capability dropped, the first-run database copy fails with `EPERM`, and granting the chown capabilities back would be a wider carve-out than this sidecar needs. `UPTIME_KUMA_DB_TYPE=sqlite` is what makes the container non-interactive; without it the image serves its database chooser and never reaches the socket server. The default profile, the `bastion-net` topology and every existing healthcheck are untouched, and `docker compose config --services` without the profile lists the same ten services as before.

2. **It observes endpoints, never the engine.** The monitor set is `config/uptime-kuma/monitors.json`, applied by `scripts/seed_uptime_kuma.py`, and every entry is something a client could check over `bastion-net`: `gateway` `/health` and `/health/ready` over HTTP, `db:5432` and `redis:6379` as TCP connects, Keycloak's management `/health` on `:9000`, `omniroute` `/api/health`, and `llama-cpp:8080` as a TCP connect. `llama-cpp` gets `maxretries × retryInterval ≥ 300 s` so a model load is not reported as an outage on every restart, the mistake the 180-second Compose `start_period` already exists to avoid. The service mounts no Docker socket and is not privileged; a test pins that the only socket mount in the file is Falco's read-only one. The worker is recorded as deliberately unmonitored — it has no listener and no HTTP surface, and its liveness is the Redis queue the `redis` monitor already reports; engine-level state such as exited, restarting or unhealthy is the daemon's view and is the one thing this design gives up. `otel-collector` is monitored after all: the distroless image has no shell, but the collector config already serves its own `health_check` extension on `:13133`, which is a probe rather than a healthcheck added to the service.

3. **The seed is a committed file, not a sequence of clicks.** `scripts/seed_uptime_kuma.py` creates the first admin account on a fresh instance, logs in, reads the monitor list and creates only the monitors that are missing, so a second run converges and prints what it kept. It speaks the dashboard's own Socket.IO protocol over Engine.IO long-polling because Uptime Kuma has no endpoint that creates a monitor: its alpha `/api` is read-only, and its OpenAPI document is explicit about it. Existing monitors are left alone — retuning one is a dashboard edit — and the script says so rather than silently rewriting history. The same run creates one public status page (`slug: bastion`) that publishes every monitor under a single group, so the availability record has a shareable face as well as a dashboard; an existing page is kept, exactly like an existing monitor. The admin credential is `UPTIME_KUMA_ADMIN_PASSWORD` from `.env`, empty in `.env.example`, and required by the seed, so no committed literal exists and the run fails closed when the operator forgot it; a test asserts both. Notifications are optional and configured in the dashboard or from `.env`; the seed never needs a delivery credential.

4. **The profile name is `infra`.** Observability that is off by default joins `infra`, the name the request used and the one that reads as "the stack's plumbing, not the request path". `compliance` stays the audit/scan profile, `security` the runtime-detection one, `pgadmin` and `redis-ui` stay single-service conveniences, and PKI stays a separate overlay because it changes transport rather than adding a capability. A future monitoring service joins `infra` instead of inventing a fifth name. The component is not a proxy: ADR-001 decision 1 forbids a sidecar in the request path, and this one only observes it, which is why no request, guardrail or audit record passes through it.

## Consequences

- **Pros**: an availability transition now leaves a record and a history instead of vanishing between two `docker compose ps` runs; the probes are the same endpoints an operator or client would use, so a monitor is evidence a reachable service is reachable; the monitor set is reviewed like code and reseeded after a `down -v`; the sidecar holds no engine socket and no elevated capability, so a compromise of it yields monitoring data and a loopback UI, not the host; the default stack stays the same size.
- **Cons**: a monitor on the same host cannot report its own host, daemon, engine or monitor outage — the honest limit, and the reason an external dead-man's-switch prober remains a follow-up rather than an oversight; Uptime Kuma's monitoring types do not include Docker health state, so a service without a listener stays outside the set by design; the seed is written against one released protocol, and a major Uptime Kuma upgrade can break it, at which point the failure is loud (`seed: ... failed`) rather than silent; re-tuning a monitor is a dashboard edit the seed will not overwrite, so drift between the file and the instance is possible and is reported as `kept` rather than reconciled; and the monitor's own SQLite volume is not backed up by anything in this repository.
