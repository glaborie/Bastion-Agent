# ADR-016: Container Image Scanning & SBOM Publication

**Status:** Accepted  
**Date:** 2026-11-11  
**Last modified:** 2026-11-19

## Context

The stack ships nine container images in `docker-compose.yml`: eight pulled from registries and one built from this repository's `Dockerfile`. The opt-in overlays add two more — the internal CA (`docker-compose.pki.yml`) and the dev Vault base the `docker-compose.vault.yml` services build on — which the inventory did not see until 2026-11-16 (IDEA-055). Until now the only supply-chain gate audited `uv.lock` against OSV, which sees Python wheels and nothing else. Base-image packages, the CUDA toolchain in the local inference image, the Keycloak distribution, `pgadmin` and the two Redis side cars were invisible. There was no SBOM, so a reviewer could not answer "what is in this release" without running `docker inspect` nine times, and `COMPLIANCE.md` claimed SOC 2 CC7.2 as implemented with no artifact behind the claim.

Two constraints shape the design. First, the scanner must not receive a Docker engine socket: a socket is equivalent to host root, and mounting one inside a stack whose app containers run with `cap_drop: ALL` and `no-new-privileges` would contradict the posture the rest of `docker-compose.yml` establishes. Second, the scan set must be derived from the compose file rather than a hand-written list, because a list is exactly the thing that goes stale when someone adds a service. Compliance wants the opposite of a manual step: a control that fails when it is not applied.

Trivy is chosen because one tool produces both artifacts the control needs — a vulnerability report and a CycloneDX SBOM — and can read a `docker save` archive without a daemon. The scanner itself is pinned by digest and runs only behind the `compliance` profile, so the default stack is unchanged. The policy is deliberately split from Trivy's own filter: Trivy reports every finding and Bastion's gate decides what fails, so a suppression cannot be hidden inside scanner configuration.

## Decision

1. **Inventory is derived from the compose files.** `scripts/image_inventory.py` reads `docker-compose.yml` plus every `docker-compose.*.yml` overlay, and the result is their additive union: the overlays a developer starts the stack with are the stack, so `docker-compose.pki.yml`'s CA image and `docker-compose.vault.yml`'s Vault base are scanned too (2026-11-16). Each file is parsed on its own, so a per-file `${VAR:?}` still fails closed. The parser expands `${VAR}` and `${VAR:-default}` the way Compose does, resolves `<<: *anchor` merges to the anchor's `image:` (the PKI overlay declares its CA image that way), and gives a build-only service the final `FROM` of the Dockerfile its `build:` stanza names — a stanza without a Dockerfile builds an image another file already declares and contributes nothing. `--compose` is repeatable and replaces the default set. It reads the project `.env` the way Compose does — the process environment wins over the file, and the file wins over the default — so a developer override such as `LLAMA_CPP_IMAGE` changes the scan set instead of being silently ignored; `--no-env-file` makes the file's defaults reproducible in a test. A service whose only profile is `compliance` is excluded: the scanner is tooling, not a shipped image. The script fails closed on an unset `${VAR:?}` rather than scanning a half-rendered stack. `docker compose config --images` is not used because rendering the files requires every secret-shaped variable and CI has no `.env`; parsing the same files yields the same set without secrets in the environment.

2. **Transport is a tarball, not a socket.** `scripts/scan_images.sh` saves one image at a time with `docker save` into `artifacts/compliance/work/images/<slug>.tar` and runs the `trivy-scan` service from the `compliance` profile against that archive, then deletes the tarball before moving to the next image. The service mounts the directory read-only and reads the archive with `trivy image --input`. It declares `cap_drop: ALL`, `no-new-privileges:true`, no ports, no added capabilities, `restart: "no"`, and no Docker engine socket. The image is `ghcr.io/aquasecurity/trivy:0.76.1` pinned by manifest-list digest. The alternative — scanning registry references directly — was rejected because it needs egress to five registries and the SBOM would describe a manifest rather than the bytes on the host. Scanning one archive at a time bounds peak disk to the largest image; the CUDA archive alone is multi-gigabyte and a hosted runner cannot hold twelve of them at once.

3. **One command, two artifacts, one gate.** The documented command is `scripts/scan_images.sh`; `--build-missing` builds the local `bastion-agent` image and pulls the rest, and is what CI uses. The scanner writes one CycloneDX document and one Trivy JSON report per image; `scripts/aggregate_trivy_reports.py` unions them into `artifacts/compliance/<UTC date>/sbom.cdx.json` and `cve.json`, each result tagged with `BastionImage`, plus a `manifest.json` that lists every reference scanned. `scripts/check_trivy_report.py` then applies the policy and returns the command's exit code: `0` clean, `1` an unsuppressed CRITICAL or a policy violation, `2` unreadable input or no images.

4. **Only CRITICAL fails, and only through `trivy.yaml`.** `trivy.yaml` is Bastion's policy file, not Trivy's configuration; Trivy is invoked with explicit flags and no `--ignorefile`, so a finding cannot be suppressed before the gate sees it. Each ignore entry must carry the Trivy id, a non-empty list of image slugs (or `*`), a statement of at least ten characters and an `expires` date. Entries are matched by id and `fnmatch` on the image slug. An expired entry fails the gate even when no finding matches it, so a stale acceptance cannot outlive its review. Missing, extra or malformed keys are a gate failure, not a warning.

5. **CI runs the same command.** The `supply-chain` job in `.github/workflows/ci.yml` runs the OSV audit and image scan when their respective filters require them. The OSV audit runs on master, weekly and manual runs, and on pull requests changing its inputs or CI gate; skipping it means a PR does not get a fresh advisory verdict. The image scan runs `./scripts/scan_images.sh --build-missing`, which renders the base file and every overlay with no arguments, uploads `artifacts/compliance/` as `compliance-reports`, and fails on the same exit code as a developer run. `ci-ok` requires `supply-chain` whenever it runs. The job's timeout is 45 minutes because a full scan pulls the CUDA image.

   **Cadence and cost (2026-11-12, development mode).** The control was merge-blocking on `master` until 2026-11-20 and is no longer run on every pull request. A scan costs about 6.5 minutes of billed runner time, and during development the same verdict is recomputed dozens of times a day: the job now scans on the weekly schedule, on manual runs, and on a pull request only when that PR edits the scanning machinery itself (`trivy.yaml`, the scan scripts, or the workflow). Image pins and lockfile bumps are therefore verified after merging rather than before merge — an accepted, reversible dev-mode trade-off recorded here rather than left to memory; restore the wider path filter before a release audit. When a scan does run, registry pulls are concurrent (`SCAN_JOBS`, default 4) and overlap the gateway build; stage and per-image timings are logged to guide further optimization. The Trivy database is restored from `actions/cache` instead of downloaded, and report artifacts are retained for 7 days instead of the repository default. The scanner still has no Docker socket and still reads only `docker save` archives. The CycloneDX and JSON analyses stay sequential: two Trivy processes sharing one cache directory fail with "cache may be in use by another process", and separate caches would re-download the database per format.

   **No scan on a push to `master` (2026-11-20, development mode).** The push path is gone as well: every merge
re-ran a scan that had already been paid for, and the job dominated billed runner minutes. The image scan now
runs only on the weekly schedule, on `workflow_dispatch`, and on a pull request that edits the scanning
machinery. Consequences, recorded rather than implied: a green `ci-ok` on `master` no longer means the pinned
images were scanned; the evidence behind `COMPLIANCE.md` CC7.2 is the weekly run plus `scripts/scan_images.sh`
run by hand; and a pin bump merges unverified until the next weekly run or a manual dispatch. Restore the
per-push path before a release audit. The scanner's posture is unchanged — same digest-pinned image, same
`docker save` archives, no Docker socket, same `trivy.yaml` policy — so running it by hand gives the same
verdict CI would have.

6. **Artifacts are evidence, not source.** `artifacts/compliance/` is gitignored with a tracked `.gitkeep`, mirroring `artifacts/gate/` and `artifacts/threat-intel/`. The SBOM and CVE report are uploaded by CI and retained there; they are never committed. `COMPLIANCE.md` CC7.2, `SECURITY.md` §Vulnerability Management and `THREAT_MODEL.md` T11 name the job, the command and the artifact path as their evidence, and claims that no longer have a mechanism (weekly Snyk scans) are removed.

## Consequences

- **Pros**: Coverage follows the compose files — the base file and every overlay — so a new service, in either, is scanned or the run fails on an unset variable; the scanner never holds host root; one tool yields both a CVE report and a CycloneDX SBOM; every suppression is scoped to an image, justified and expiring; a CRITICAL fails the merge gate rather than appearing on a dashboard; the artifacts answer "what shipped" without running the stack.
- **Cons**: A full scan downloads and re-saves twelve images, including a multi-gigabyte CUDA image, so CI is slower and bandwidth-hungry; Trivy's vulnerability database needs network access at scan time, which the local stack otherwise does not require; the image slug in an ignore entry is a naming convention rather than a database relationship, so renaming an image invalidates an entry silently (the gate then fails on the finding, not on the rename); the two `.env`-overridable images (`omniroute`, `llama.cpp`) are digest-pinned by default but an operator override can be tag-only; and the SBOM is only as complete as Trivy's package discovery for the scanned base images; a build-only overlay service contributes the base its Dockerfile starts from, not the derivative image Compose builds from it (2026-11-16).
- **Residual risk**: no image signature or provenance verification (cosign), so a compromised registry or tag could deliver content that scans clean; no IaC or secret scanning in this gate; `OMNIROUTE_IMAGE` and `LLAMA_CPP_IMAGE` are digest-pinned by default but can be overridden with a tag-only reference from `.env`; the scanner itself is trusted by digest but not independently verified. Accepted findings are image-scoped and expiring in `trivy.yaml`, not silent. These are named in `THREAT_MODEL.md` T11 and are follow-up items, not silently accepted.
