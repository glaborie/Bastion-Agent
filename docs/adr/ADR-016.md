# ADR-016: Container Image Scanning & SBOM Publication

**Status:** Accepted  
**Date:** 2026-11-11  
**Last modified:** 2026-11-11

## Context

The stack ships nine container images: eight pulled from registries and one built from this repository's `Dockerfile`. Until now the only supply-chain gate audited `uv.lock` against OSV, which sees Python wheels and nothing else. Base-image packages, the CUDA toolchain in the local inference image, the Keycloak distribution, `pgadmin` and the two Redis side cars were invisible. There was no SBOM, so a reviewer could not answer "what is in this release" without running `docker inspect` nine times, and `COMPLIANCE.md` claimed SOC 2 CC7.2 as implemented with no artifact behind the claim.

Two constraints shape the design. First, the scanner must not receive a Docker engine socket: a socket is equivalent to host root, and mounting one inside a stack whose app containers run with `cap_drop: ALL` and `no-new-privileges` would contradict the posture the rest of `docker-compose.yml` establishes. Second, the scan set must be derived from the compose file rather than a hand-written list, because a list is exactly the thing that goes stale when someone adds a service. Compliance wants the opposite of a manual step: a control that fails when it is not applied.

Trivy is chosen because one tool produces both artifacts the control needs — a vulnerability report and a CycloneDX SBOM — and can read a `docker save` archive without a daemon. The scanner itself is pinned by digest and runs only behind the `compliance` profile, so the default stack is unchanged. The policy is deliberately split from Trivy's own filter: Trivy reports every finding and Bastion's gate decides what fails, so a suppression cannot be hidden inside scanner configuration.

## Decision

1. **Inventory is derived from `docker-compose.yml`.** `scripts/image_inventory.py` parses every `image:` reference, expands `${VAR}` and `${VAR:-default}` the way Compose does, and de-duplicates while preserving file order. It reads the project `.env` the way Compose does — the process environment wins over the file, and the file wins over the default — so a developer override such as `LLAMA_CPP_IMAGE` changes the scan set instead of being silently ignored; `--no-env-file` makes the file's defaults reproducible in a test. A service whose only profile is `compliance` is excluded: the scanner is tooling, not a shipped image. The script fails closed on an unset `${VAR:?}` rather than scanning a half-rendered stack. `docker compose config --images` is not used because rendering the file requires nine secret-shaped variables and CI has no `.env`; parsing the same file yields the same set without secrets in the environment.

2. **Transport is a tarball, not a socket.** `scripts/scan_images.sh` saves one image at a time with `docker save` into `artifacts/compliance/work/images/<slug>.tar` and runs the `trivy-scan` service from the `compliance` profile against that archive, then deletes the tarball before moving to the next image. The service mounts the directory read-only and reads the archive with `trivy image --input`. It declares `cap_drop: ALL`, `no-new-privileges:true`, no ports, no added capabilities, `restart: "no"`, and no Docker engine socket. The image is `ghcr.io/aquasecurity/trivy:0.76.1` pinned by manifest-list digest. The alternative — scanning registry references directly — was rejected because it needs egress to five registries and the SBOM would describe a manifest rather than the bytes on the host. Scanning one archive at a time bounds peak disk to the largest image; the CUDA archive alone is multi-gigabyte and a hosted runner cannot hold nine of them at once.

3. **One command, two artifacts, one gate.** The documented command is `scripts/scan_images.sh`; `--build-missing` builds the local `bastion-agent` image and pulls the rest, and is what CI uses. The scanner writes one CycloneDX document and one Trivy JSON report per image; `scripts/aggregate_trivy_reports.py` unions them into `artifacts/compliance/<UTC date>/sbom.cdx.json` and `cve.json`, each result tagged with `BastionImage`, plus a `manifest.json` that lists every reference scanned. `scripts/check_trivy_report.py` then applies the policy and returns the command's exit code: `0` clean, `1` an unsuppressed CRITICAL or a policy violation, `2` unreadable input or no images.

4. **Only CRITICAL fails, and only through `trivy.yaml`.** `trivy.yaml` is Bastion's policy file, not Trivy's configuration; Trivy is invoked with explicit flags and no `--ignorefile`, so a finding cannot be suppressed before the gate sees it. Each ignore entry must carry the Trivy id, a non-empty list of image slugs (or `*`), a statement of at least ten characters and an `expires` date. Entries are matched by id and `fnmatch` on the image slug. An expired entry fails the gate even when no finding matches it, so a stale acceptance cannot outlive its review. Missing, extra or malformed keys are a gate failure, not a warning.

5. **CI runs the same command.** The `supply-chain` job in `.github/workflows/ci.yml` keeps the OSV audit, then runs `./scripts/scan_images.sh --build-missing`, uploads `artifacts/compliance/` as `compliance-reports`, and fails on the same exit code as a developer run. `ci-ok` still requires `supply-chain`, so the control is merge-blocking. All nine images are pulled from a registry or built in CI, so no exception is needed. The job's timeout is 45 minutes because a full scan pulls the CUDA image.

6. **Artifacts are evidence, not source.** `artifacts/compliance/` is gitignored with a tracked `.gitkeep`, mirroring `artifacts/gate/` and `artifacts/threat-intel/`. The SBOM and CVE report are uploaded by CI and retained there; they are never committed. `COMPLIANCE.md` CC7.2, `SECURITY.md` §Vulnerability Management and `THREAT_MODEL.md` T11 name the job, the command and the artifact path as their evidence, and claims that no longer have a mechanism (weekly Snyk scans) are removed.

## Consequences

- **Pros**: Coverage follows the compose file, so a new service is scanned or the run fails on an unset variable; the scanner never holds host root; one tool yields both a CVE report and a CycloneDX SBOM; every suppression is scoped to an image, justified and expiring; a CRITICAL fails the merge gate rather than appearing on a dashboard; the artifacts answer "what shipped" without running the stack.
- **Cons**: A full scan downloads and re-saves nine images, including a multi-gigabyte CUDA image, so CI is slower and bandwidth-hungry; Trivy's vulnerability database needs network access at scan time, which the local stack otherwise does not require; the image slug in an ignore entry is a naming convention rather than a database relationship, so renaming an image invalidates an entry silently (the gate then fails on the finding, not on the rename); the two `.env`-overridable images (`omniroute`, `llama.cpp`) are digest-pinned by default but an operator override can be tag-only; and the SBOM is only as complete as Trivy's package discovery for the scanned base images.
- **Residual risk**: no image signature or provenance verification (cosign), so a compromised registry or tag could deliver content that scans clean; no IaC or secret scanning in this gate; `OMNIROUTE_IMAGE` and `LLAMA_CPP_IMAGE` are digest-pinned by default but can be overridden with a tag-only reference from `.env`; the scanner itself is trusted by digest but not independently verified. The accepted findings for Postgres and RedisInsight are image-scoped and expiring in `trivy.yaml`, not silent. These are named in `THREAT_MODEL.md` T11 and are follow-up items, not silently accepted.
