# ADR-007: Command Control Dashboard & HTMX Integration

**Status:** Accepted  
**Date:** 2026-11-09  
**Last modified:** 2026-11-11

## Context

Operators need a lightweight, always-available dashboard to monitor approvals, evaluate health, and intervene when HITL gates trigger. The dashboard must not impose a heavy frontend build step or require a separate deployment.

The dashboard is served by the same FastAPI process as the API, so it must not add a Node toolchain, a bundler, or a second deployment. Operators use it during incidents, often on the same workstation, which sets the constraints: same JWT dependency as the API, strict CSP, no PII by default, and a bounded polling interval that stays cheap when nobody is looking.

## Decision

1. **FastAPI + Jinja2 + HTMX + Pico.css**: The dashboard is a regular FastAPI route (`/dashboard`) serving Jinja2 templates. No React, no Vue, no build step. Pico.css provides minimal styling (light/dark via `prefers-color-scheme`). HTMX 2.0.4 and Pico 2.0.6 are vendored under `gateway/dashboard/static/vendor/` with recorded SHA-256 digests — no CDN is contacted at runtime.

2. **Routes and API endpoints** (implemented in Milestone 2):
   - `GET /dashboard` → approvals and eval-health cards, polling every 3s/30s
   - `GET /dashboard/audit` → filterable, cursor-paginated audit ledger
   - `GET /dashboard/sessions/{id}` → session timeline from `audit_logs`
   - `GET /dashboard/demo` → allow-listed demo scenarios, each with the control it exercises and the evidence it should produce
   - `POST /dashboard/demo/runs` → start one registered scenario (operator/admin + CSRF; form field `scenario_id` only)
   - `GET /api/dashboard/demo/runs/{run_id}` → HTML run panel, polled until the run is terminal
   - `GET /api/approvals` → pending approvals; JSON normally, HTML partial for htmx
   - `POST /api/approvals/{ticket_id}/action` → approve/reject with four-eyes checks
   - `GET /api/audit` / `POST /api/audit/verify` → paging and hash-chain verification
   - `GET /api/sessions/{id}/timeline` → Session Inspector data
   - `GET /api/evals/latest` → latest DeepEval run summary

   **Demo console execution model (2026-11-11).** The demo page is a registry, not a shell: `agent/demo/scenarios.py` maps a fixed scenario id to a server-side callable, and no endpoint accepts a command string, a script path or argv. A run request carries the id and nothing else; an unknown id is `404`, and the CLI-only traffic scenario has no callable and is rejected with `422` before anything executes. The actor is the signed-in principal — the gateway captures `sub` and roles from the authenticated session, never from the request, so the `--actor-sub` flag of `scripts/demo_tool_request.py` cannot become an impersonation path. Execution is asynchronous: the gateway writes a `queued` run record to Redis under `demo:run:<id>` and enqueues `run_demo_scenario_job`; the worker resolves the id, runs the scenario and updates the record; the page polls the record. Results expire after an hour. Runs write structured logs and a `demo.scenario` span only — no new audit event type, because ADR-007 decision 7 keeps the ledger vocabulary frozen; the canonical rows still come from the scenario's own effects (the guarded tool ticket, the chat turn). Four-eyes is untouched: a ticket created by a scenario names the signed-in principal as initiator and still needs a different principal to approve. The CLI scripts remain the documented fallback.

3. **Real-time via WebSocket** (Phase 2): `hx-ext="ws"` upgrades the polling to full-duplex WebSocket for approval queue, worker health, and routing metrics. Fallback to 3s polling if the WS connection fails. Milestone 2 ships polling only.

4. **Browser auth is OIDC code + PKCE, not a token in the page**: `/auth/login` redirects to Keycloak with single-use `state`/`nonce`/PKCE values held in Redis; `/auth/callback` validates the ID token nonce and creates an opaque server-side session. The browser holds only an `HttpOnly`, `SameSite=Lax` cookie; access and refresh tokens stay in Redis. `/auth/logout` deletes the session, hands off to a one-time same-origin `/auth/logged-out` page (so the dashboard and its polling are unloaded before leaving for the IdP), then ends the Keycloak SSO session; a short-lived logout marker forces `prompt=login` if a login races the logout. Dashboard routes require `require_roles("operator", "admin")`; API clients may use a Bearer token. CSRF tokens are issued per session and required for cookie-authenticated mutations.

5. **Template and asset structure**:
   - `base.html` → shell, vendored assets, operator bar, CSP-friendly markup (no inline script)
   - `dashboard.html` → approval queue, eval health, chain verification
   - `demo.html` → demo scenarios, run buttons and per-scenario run slots
   - `audit.html` / `session.html` → ledger explorer and timeline
   - Partial templates: `partials/approval_table.html`, `partials/eval_status.html`, `partials/audit_table.html`, `partials/demo_run.html`

   Security headers (CSP, `X-Frame-Options: DENY`, `nosniff`, `no-referrer`, `no-store` on authenticated paths) are applied by middleware in `gateway/main.py`.

6. **Eval health is evidence, not a default**: `/api/evals/latest` reads the JSON artifact written by the Milestone 6 harness. A missing, malformed or stale (>24h) report renders as "not run yet"/stale; the dashboard never assumes a green run.

7. **Rate limiting is implemented; audit-view recording is still deferred.** Per-user dashboard rate limiting (60 req/min) was deferred by Milestone 2 and is now enforced by ADR-013: a Redis token bucket keyed on the JWT subject covers the dashboard pages, the HTMX partials and the APIs they poll, and refuses with `429` plus `Retry-After`. The `AUDIT_LOG_VIEW` record for every view still requires an event-vocabulary/schema change and remains scheduled with the Phase 1 dashboard features in ADR-008. Milestone 2 protects views with operator/admin RBAC, CSRF, `no-store` and a strict CSP.

## Consequences

- **Pros**: Zero frontend build dependency; instant refresh via HTMX; familiar HTML/CSS/JS for operators; same auth as API reduces surface area; WebSocket upgrade path.
- **Cons**: HTMX learning curve for developers adding new features; WebSocket requires connection management; Pico.css limits customizability (but that's a feature, not a bug, for security UI).
