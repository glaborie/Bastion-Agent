# ADR-015: Tenant Isolation for Keys, Rows and Queries

**Status:** Accepted  
**Date:** 2026-11-11  
**Last modified:** 2026-11-11

## Context

Every data path in v0.2 assumed one organisation per deployment. The DLP vault, canary registry, quarantine store and approval queue were keyed only by a session hash or a ticket id, and neither `audit_logs` nor `pending_approvals` carried a tenant. Two customers on one stack would therefore share one Redis namespace and one PostgreSQL schema: an operator in one tenant could reach another tenant's tokens or tickets by presenting a guessed conversation id or ticket id, and an audit query returned every customer's rows. `THREAT_MODEL.md` stated that boundary explicitly, so it could not be changed by a code comment alone.

The tenant has to come from the authenticated identity, not from a request field. A caller-supplied tenant header or conversation attribute would make isolation opt-in and would let an attacker choose which namespace to read. Keycloak already issues the identity; the realm can map a user attribute into a token claim, and the gateway already validates that token before any route executes. The same validated tenant must then be carried through the worker job, the tool context, the approval ticket and every ledger query.

Two properties are required. First, a forgotten query filter must not fall back to "all tenants": the read helpers take a tenant argument and there is no unscoped variant on the request path. Second, a copied Redis value must not decrypt under another tenant even if its token name is known; the AEAD associated data therefore binds the tenant as well as the session and token.

## Decision

1. **Tenant is an OIDC claim, and a missing claim fails closed.** `Principal.tenant_id` is resolved from the `TENANT_CLAIM` setting (default `tenant_id`) on every access-token validation. The value is normalised to `[A-Za-z0-9][A-Za-z0-9._-]{0,63}` before it reaches a key or a row; an absent claim raises `TokenValidationError("missing_tenant")` and an unusable value raises `invalid_tenant`. The Keycloak realm maps the `tenant` user attribute to that claim for both the browser and CLI clients, and the seeded users carry a tenant attribute. The server-side session record persists the tenant with the principal; a record that predates this ADR is discarded and the operator signs in again rather than being silently assigned a tenant.

2. **Redis keys carry an explicit tenant segment.** The vault uses `vault:<tenant>:<sha256(session)>`, `:rev` and `:seq`; the egress controls use `egress:<tenant>:canary:<sha256(session)>` and `egress:<tenant>:trip:<sha256(session)>`. Vault AEAD associated data is `tenant|session|token`, so a ciphertext copied to another tenant fails authentication even when the session id and token are identical. The chat vault session is derived as `chat:<sha256(tenant + "\x00" + actor_id + "\x00" + conversation_id)>`, which keeps the two independent controls aligned. Pre-ADR un-prefixed keys are never read: they expire through the existing vault (30 min) and quarantine (15 min) TTLs, and an upgrade does not migrate them.

3. **PostgreSQL rows carry a tenant and every request-path query filters on it.** `audit_logs.tenant_id` and `pending_approvals.tenant_id` are `VARCHAR(64) NOT NULL`, indexed with the columns their read paths already use. `append_audit_event` requires a tenant, `PendingApproval` creation requires a tenant, and the approval/audit read helpers require one as well. `list_pending`, `list_recently_decided`, `decide_ticket`, `list_records`, `session_timeline` and `recent_security_incidents` have no unscoped request-path variant. A decision against a ticket in another tenant is indistinguishable from a missing ticket (`404`), so the endpoint cannot be used to confirm that another tenant's ticket exists. The bootstrap DDL in `db/models.py` adds the columns with a `default` backfill for rows created before this ADR; new rows always receive an explicit tenant.

4. **The approval hand-off is tenant-qualified.** `AgentContext` carries the tenant, the worker job requires it, and the resume job id is `resume:<tenant>:<ticket_id>`. The cron sweeps remain system-wide by design: they execute approved tickets across tenants, and each resumed ticket re-derives its tenant from the stored row rather than from the job payload. The four-eyes HMAC token continues to bind ticket id, request fingerprint and expiry; the ticket itself is tenant-scoped, so the token cannot be replayed in another tenant.

5. **The audit chain formula is unchanged.** Tenant is an access-scope attribute, not part of `record_hash`: ADR-005's hash still covers id, timestamp, actor, event type, payload hash and the previous hash, so existing records and existing verification keep working. Reassigning a row's tenant requires an `UPDATE`, which the append-only trigger rejects; a database superuser able to disable that trigger is already outside the threat model (`THREAT_MODEL.md` T10). Chain verification remains global because the chain is global; it returns counters and the first bad id, not row contents.

6. **Operator escalation is explicit.** A tenant cannot opt into another tenant through an API parameter, and there is no break-glass endpoint that lists all tenants. Cross-tenant inspection remains a database-operator action outside the application. PostgreSQL row-level security is not replaced by this ADR; it remains the defence-in-depth step named in ADR-008 for the rest of v0.3.

## Consequences

- **Pros**: A guessed conversation id or ticket id no longer crosses a tenant boundary; Redis values are cryptographically bound to their tenant; the tenant is carried from the validated token through the worker and the ledger; approval and audit reads have a single mandatory scope parameter, so a new route cannot accidentally default to "all"; legacy single-tenant deployments continue to verify because the audit hash is untouched.
- **Cons**: Every token must now carry a tenant claim, so a misconfigured Keycloak mapper locks operators out (fail closed); existing sessions and un-prefixed Redis entries are abandoned at upgrade; the columns and indexes consume space and the backfill marks pre-ADR rows as `default`; application-level scoping still depends on each read helper being used, and PostgreSQL RLS is deferred to the rest of v0.3; the cron sweeps intentionally read across tenants, so their compromise is a system-level event rather than a tenant-level one.
