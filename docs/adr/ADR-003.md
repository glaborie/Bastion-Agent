# ADR-003: Declarative RBAC & Four-Eyes HITL

**Status:** Accepted  
**Date:** 2026-11-09  
**Last modified:** 2026-11-09

## Context

The agent must enforce role-based access control without requiring developers to remember to check roles at every tool call. Write actions must require independent human confirmation (four-eyes principle), and no single user should be able to escalate privileges through the agent.

Roles are the `realm_access.roles` claim issued by Keycloak; the gateway cannot invent roles locally, and tool definitions must remain readable so that adding a tool cannot silently widen access. Approval happens in a browser session that is separate from the API caller, and the initiator identity in the ticket must be trustworthy even if a caller fabricates headers, so the check is duplicated at the storage layer.

## Decision

1. **`@tool` decorator with `required_role`**: Every tool declares `read_only`, `required_role`, and `description`. Example:
   ```python
   @tool(
       name="execute_file_write",
       description="Writes data to storage",
       read_only=False,
       required_role="operator",
   )
   async def execute_file_write(path: str, content: str, context: AgentContext): ...
   ```

2. **Role extraction from validated JWT**: FastAPI dependency `require_roles(["operator", "admin"])` extracts `realm_access.roles` from the Keycloak JWT. Tools requiring roles the caller lacks are silently filtered from the model prompt schema.

3. **Four-eyes suspension & approval**:
   - On a write tool request: the ARQ worker suspends and writes a `PendingApproval` row with an HMAC-SHA256 ticket bound to the ticket id, a fingerprint of the exact tool arguments (prevents TOCTOU swaps) and the expiry. Only the token hash is stored.
   - Returns `status: "approval_pending"` + `ticket_id` to the caller.
   - The Command Control Center (`/dashboard`) polls `GET /api/approvals` every 3s and lists ticket id, tool name, arguments diff, initiator, and expiry.
   - Approval: `POST /api/approvals/{ticket_id}/action` with `{"action": "approve" | "reject"}`. `approver_id != initiator_id` is checked in the application **and** by a database `CHECK` constraint.

4. **Read-only allow list**: Tools with `read_only=True` execute immediately if the caller has any non-`readonly` role that permits read access. No approval needed.

## Consequences

- **Pros**: Role errors are caught at declaration time, not runtime; four-eyes prevents accidental/malicious writes; declarative pattern means new tools automatically inherit policy; RBAC matrix visualizer in dashboard.
- **Cons**: Slightly more verbose tool definitions; approval workflow adds ~30s latency for write actions; requires operator availability.
