# ADR-003: Declarative RBAC & Four-Eyes HITL

**Status:** Accepted  
**Date:** 2026-11-09  
**Last modified:** 2026-11-09

## Context

The agent must enforce role-based access control without requiring developers to remember to check roles at every tool call. Write actions must require independent human confirmation (four-eyes principle), and no single user should be able to escalate privileges through the agent.

Roles are the `realm_access.roles` claim issued by Keycloak; the gateway cannot invent roles locally, and tool definitions must remain readable so that adding a tool cannot silently widen access. Approval happens in a browser session that is separate from the API caller, and the initiator identity in the ticket must be trustworthy even if a caller fabricates headers, so the check is duplicated at the storage layer.

## Decision

1. **`@tool` decorator with `required_role`**: Every tool declares `read_only`, `required_role`, and `description`. Example:
   ```python
   @tool(
       name="execute_file_write",
       description="Writes data to storage",
       read_only=False,
       required_role="operator",
   )
   async def execute_file_write(path: str, content: str, context: AgentContext): ...
   ```

2. **Role extraction and satisfiability**: `require_roles(["operator", "admin"])` extracts `realm_access.roles` from the validated Keycloak token and applies **any-of** semantics. `admin` is a break-glass superset that satisfies every requirement; `operator`, `analyst` and `readonly` are independent grants, so `operator` does not implicitly grant `analyst`. Unknown roles are dropped. Protected routes accept either a Bearer token or a server-side session; cookie-authenticated mutations additionally require `X-CSRF-Token` and an `Origin`/`Referer` host check (loopback aliases are equivalent, and `Origin: null` from an opaque/sandboxed view is accepted only after the CSRF token matches). Tools requiring roles the caller lacks are silently filtered from the model prompt schema.

3. **Four-eyes suspension & approval**:
   - On a write tool request: the ARQ worker suspends and writes a `PendingApproval` row with an HMAC-SHA256 ticket bound to the ticket id, a fingerprint of the exact tool arguments (prevents TOCTOU swaps) and the expiry. Only the token hash is stored. (Milestone 4 implements suspension; Milestone 2 implements the decision side.)
   - Returns `status: "approval_pending"` + `ticket_id` to the caller.
   - The Command Control Center (`/dashboard`) polls `GET /api/approvals` every 3s and lists ticket id, tool name, arguments diff, initiator, and expiry. The initiator's row has no action buttons.
   - Approval: `POST /api/approvals/{ticket_id}/action` with `action=approve|reject` and an optional reason. Decisions take a row lock, reject expired/already-decided tickets, require the approver to satisfy the ticket's `required_role`, and enforce `approver_id != initiator_id` in the application **and** by a database `CHECK` constraint. The decision and its `APPROVAL_GRANTED`/`APPROVAL_REJECTED` audit record commit in one transaction; the audit ledger stores a SHA-256 of the free-text reason, never the text.

4. **Read-only allow list**: Tools with `read_only=True` execute immediately if the caller has any non-`readonly` role that permits read access. No approval needed.

## Consequences

- **Pros**: Role errors are caught at declaration time, not runtime; four-eyes prevents accidental/malicious writes; declarative pattern means new tools automatically inherit policy; API and dashboard share one authorization primitive.
- **Cons**: Slightly more verbose tool definitions; approval workflow adds ~30s latency for write actions; requires operator availability.
