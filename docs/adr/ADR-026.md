# ADR-026: An OpenAI-Compatible Facade Over One Guarded Pipeline

**Status:** Accepted  
**Date:** 2026-11-18  
**Last modified:** 2026-11-18

## Context

`POST /v1/chat` is the only route that reaches a model, and it speaks a body only this repository understands: `ChatRequest` with `extra="forbid"`, a `conversation_id` field, a response carrying `route`, `classification` and `blocked`. A client that already speaks the OpenAI dialect cannot point at the gateway. The pressure to add the surface is concrete: a local client polls `/v1/models` every 30 seconds and had logged roughly 11,500 not-found spans a day, and the first real integration would otherwise be written as an external proxy — the one shape that bypasses DLP, the canary, the injection gate and the ledger.

The structural constraint is that those guards live in one ordered pipeline. IDEA-036 already split the handler into one function per stage (`_ingress`, `_dlp_stage`, `_routing_stage`, `_preflight`, `_injection_gate`, `_complete`, `_egress_stage`, `_delivery_stage`) and that is done; what was missing was a single coordinator both surfaces could call. An adapter that re-ordered the stages, or called the endpoint over HTTP, would create the second guardrail implementation that "must not have two implementations". The conversation identity is the other hard part: the marker vault is scoped per session, while the canary and the quarantine must survive a client that sends no conversation id and resends its history on the next turn.

This record is **Accepted and implemented on 2026-11-18** (IDEA-060). It says what the surface is, what it deliberately refuses, and why the streaming is buffered rather than incremental.

## Decision

1. **Two routes, one guard set.** `POST /v1/chat/completions` and `GET /v1/models` live in `gateway/routers/openai_compat.py`, require the same `CHAT_ROLES`, the same CSRF check, the same rate limiter and the same DLP/egress dependencies as the native endpoint. The native routes and their response shape are unchanged; the compat routes are additive.

2. **One pipeline function.** The orchestration that used to sit in `chat()` moved to `chat.run_turn(...)`, and both `POST /v1/chat` and the compat route call it. A second adapter multiplies call sites, never stage order: DLP, routing, the injection gate, the canary, egress inspection and the audit rows run exactly once per turn.

3. **`model` is a hint; the route decision is authoritative.** `bastion-auto` forces nothing, `bastion-local` narrows the turn to the local alias (recorded as `client_alias_local` on the routing row, applied before the row is written so the ledger never disagrees with the answer), the two internal aliases are accepted as hints, and anything else is a `404` `model_not_found` envelope. Forcing local can only reduce where a prompt goes, so no additional role is required beyond the right to chat; the ADR records that reading rather than inventing a model-to-role table. The response reports the model that actually answered, not the one the caller asked for.

4. **A blocked turn is a normal completion with `finish_reason: "content_filter"`.** The injection gate returns `200`, an empty `content` and a `bastion` extension object carrying `blocked`, `block_reason`, `conversation_id`, `route`, `classification` and `confidence`. The gateway notice the native endpoint returns is not model text and must not be mistaken for it by an OpenAI client.

5. **Every error is the OpenAI envelope on these paths only.** `{"error": {"message", "type", "code"}}` with the existing status codes: `422` for a refused body, `404` for an unknown model, `429` with `rate_limit_exceeded` or `token_budget_exhausted` and the `RateLimit-*`/`Retry-After` headers, `403` `session_quarantined` for a trip, `502`/`503` for upstream and store failures. Body-validation errors are enveloped by a handler registered by the facade; HTTP errors are translated by a branch inside the handler `gateway.main` already owns, so login redirects, htmx reloads, the 429 page and every non-compat route keep their current shape.

6. **Conversation identity is a header, and the trip is keyed on the actor.** `X-Bastion-Conversation-Id` (validated against the native conversation pattern) drives the vault session and is echoed on the response. Without it the vault session is per request — markers must not outlive the turn that minted them — while the canary and the quarantine are keyed on `ephemeral:<tenant>:<actor>`, so a canary leak quarantines the principal instead of a throwaway session the caller abandons by not sending the header. That is one optional argument (`egress_session`) on `EgressSanitizer.inspect`, defaulting to the old behaviour, so the native endpoint's keying is unchanged.

7. **Client-supplied `tools`, `tool_choice`, `system` and `assistant` turns are refused with `422`.** Tool execution stays server-side behind the catalog and four-eyes, and ADR-012 keeps exactly one gateway-written system message while only the model writes assistant turns. A facade that accepted them would let a caller rewrite the guard by sending a `system` turn.

8. **`stream: true` is buffered, scanned and replayed as synthetic SSE.** The turn completes through the normal egress inspection and the already-sanitized text is emitted as `chat.completion.chunk` deltas followed by `[DONE]`. No unscanned byte can reach the caller, at the cost of the client seeing no token until the turn is done. True incremental streaming is a separate slice: it needs a holdback at least the length of the configured canary and the longest vault marker, a truncation record with `truncated: true`, and a property test that any chunking releases the same bytes as the non-streaming path.

9. **The Responses API is out of scope, and adding it later is stateless-only.** `store: false` would be forced and `previous_response_id` rejected, because server-side response state conflicts with the per-request vault session and with ledger semantics that record a turn rather than a thread the gateway silently rewrites.

10. **No new threat-model control.** The new ingress adds no unguarded path: it reuses the same identity, DLP, routing, egress and audit controls, and the only new surface is a route that refuses by default. `THREAT_MODEL.md` therefore keeps its control rows; the compat limits are recorded here and in `README.md`.

## Consequences

- **Pros**: an existing OpenAI client integrates by changing a base URL, so the alternative — an external proxy in front of the gateway — never gets built; the guardrail path stays single because both surfaces call one function; a canary trip on an ephemeral turn quarantines the principal rather than a session the caller can drop; error shapes match what SDKs already parse; tool execution stays catalog-bound and four-eyes, not caller-schema-bound.
- **Cons**: buffered SSE gives up time-to-first-token, so a streaming client sees the same latency as a non-streaming one; a caller that wants assistant history echoed must keep it locally, because the gateway refuses to accept it as input; `bastion-local` is available to anyone who may chat, which narrows egress but means the local model can be pinned by an analyst; the error-envelope translation is path-scoped, so a future route added under `/v1/` must be added to `_COMPAT_PATHS` or it answers with `detail`.
- **Residual risk**: the compat surface is another caller of the same controls, not a second control, so it inherits every limit ADR-012 records — the canary is best-effort against a model that paraphrases, the disclosure-claim detector is heuristic, and the token budget settles from provider-reported usage. True streaming, the Responses API, and any per-caller model-to-role policy remain open and are named rather than implied.
