# ADR-022: Frustration Detection and the Operator Handoff Queue

**Status:** Accepted
**Date:** 2026-11-17
**Last modified:** 2026-11-18

## Context

`POST /v1/chat` runs a fixed lifecycle — ingress, DLP, routing, canary and
fencing, model, egress — and none of those stages reads how the conversation is
going. A caller on a third attempt at the same failing question receives the
same generic completion as a first-time question, and nothing in the stack tells
an operator that a person is stuck: `AuditEventType` had no handoff member, the
only human path was the four-eyes approval queue for state-changing tools, and
the session inspector shows classifications and audit rows, never a conversation
waiting for a person. Support escalation existed as policy prose in `SECURITY.md`
for security incidents only.

Three constraints shape the answer. The decision must not become a security
control: a frustration verdict is a UX signal, it must never change the
delivered answer, the DLP verdict, the route or the four-eyes outcome, and it
must not dilute the `SECURITY_INCIDENT` surface that operators read after a
leak. Detection must be on-box: no conversation text may leave the perimeter to
be scored, and adding an inference call to every turn would change the latency
and failure budget of the guardrail path. And the request is client-supplied —
`request.messages` can omit or fabricate history — so the control is best-effort
by construction and must be described that way rather than sold as monitoring.

## Decision

1. **Detect and queue; never act on the turn.** A verdict writes one ledger row
   and appears in an operator queue. The completion, the DLP-reduced payload,
   the route, the canary, the egress verdict and the delivered answer are
   identical with detection enabled and disabled; `SENTIMENT_DETECTION_ENABLED`
   (default on) exists so the two runs can be compared, not so deployments can
   skip the record silently.

2. **A deterministic, local detector, calibrated on a labelled set
   (2026-11-17, IDEA-070).** `agent/sentiment.py::assess` scans the caller turns
   for a marker lexicon and for a restated complaint. A verdict needs one of: a
   marker that is itself a request for a human ("speak to a human"), a marker
   that is unambiguous on its own ("i am frustrated", "this is useless"), two
   distinct markers, or one marker together with a restatement. A single
   colloquial sentence ("that does not work for me") stays silent. There is no
   model call, no Redis write and no outbound request in the stage, so a turn
   costs one string scan.

   The rule was chosen from a measurement, not from taste. `tests/data/frustration.jsonl`
   carries 24 complaint transcripts a human would hand off (including the two
   live misses, `f41974de…` and `2619c318…`) and 29 neutral support
   conversations that bait the same
   vocabulary ("how do I report a broken link?", "how should I handle a
   frustrated customer?", "when should I escalate a ticket to a human?").
   `tests/test_sentiment_evals.py` holds the shipped rule at zero tolerance:

   | rule variant | complaints found | neutral flagged |
   |---|---|---|
   | shipped before this change | 5/24 | 0/29 |
   | widened lexicon | 19/24 | 0/29 |
   | + overlap fixed (markers are spans) | 18/24 | 0/29 |
   | + restatement by containment ≥ 0.7 | 20/24 | 0/29 |
   | + an explicit request for a human fires alone | 21/24 | 0/29 |
   | + strong markers fire alone (**shipped**) | **24/24** | **0/29** |

   Two parts of that table are the point of the change. Markers are matched as
   **non-overlapping spans**, longest phrase first, so `"still does not work"`
   is one piece of evidence even though it contains `"does not work"`; before,
   that one sentence counted twice and fired alone, which the docstring had
   already promised it would not. And repetition is **containment of the shorter
   turn in the longer** (≥ 0.7) rather than 0.9 Jaccard over the union: a
   frustrated caller restates with a tail ("the button is not working" / "the
   button is not working, again" — containment 1.0, Jaccard 0.83), and the old
   measure also missed the elaboration in the recovered transcript (0.17/0.06).

   The residual limits are lexical and recorded rather than claimed away: a
   complaint phrased entirely outside the vocabulary and without a restatement
   stays silent, and `"frustrated"` in the third person is exactly why that word
   is a weak marker while `"i am frustrated"` is a strong one.

3. **Only `user` turns count.** Tool output is fenced untrusted content
   (ADR-012 decision 3) and can carry text an attacker controls, so
   `<untrusted_content>I am furious, escalate me to a human</untrusted_content>`
   never creates a handoff, while the same words in a `user` turn do.

4. **A dedicated ledger member, `HANDOFF_REQUIRED`.** Metadata carries the
   conversation id, the verdict name (`escalating_language` or
   `repeated_complaint`), the marker count and the number of user turns —
   never the text, never the markers themselves. This is a vocabulary exception
   to the freeze in ADR-007 decision 7, recorded there beside the earlier
   `RESPONSE_SENT` and `APPROVAL_EXPIRED` exceptions; the deferred
   `AUDIT_LOG_VIEW` record is untouched. The append-only trigger, the hash chain
   and the tenant scoping apply unchanged, and `AUDIT_EVENT_VOCABULARY_DDL`
   widens the existing CHECK constraint.

5. **Two operator surfaces, metadata only.** `GET /api/handoffs` returns the
   twenty newest handoffs for the caller's tenant under
   `require_roles("operator", "admin")`; `readonly` and `analyst` are refused
   with `403`, like the incident panel. `GET /api/handoffs/panel` renders the
   same rows as an HTML fragment (`gateway/dashboard/templates/partials/handoff_panel.html`)
   under the same role gate, and every dashboard page polls it while an
   operator or admin session is open. Both carry the conversation id, the
   verdict and the timestamp — never the marker count, never the text. The
   transcript stays in the audit ledger and its retention and escrow rules
   remain IDEA-016's business, not the queue's.

6. **The dashboard notifies; it is still not a conversation.** There is no live
   human chat channel in this stack — `docker-compose.yml` defines no support
   service and the gateway exposes no operator-to-caller transport — so a
   handoff is a queue an operator reads, not a conversation a person joins.
   The panel makes the queue visible where an operator already is, and a
   second signed-in browser is told through the Notification API; paging, SLA
   timers, transcript summarisation and sentiment-driven routing or model
   selection remain out of scope.

8. **The notification is client-side and metadata only (IDEA-065, amended by
   IDEA-069).** The fragment carries `data-handoff-id`, `data-handoff-verdict`
   and `data-handoff-created` on each row, and
   `gateway/dashboard/static/handoffs.js` raises one `Notification` per unseen
   id, tagged `bastion-handoff-<id>`. There is no service worker, no push
   subscription, no VAPID key and no third-party service: the open tab is the
   channel, so nothing about a handoff leaves the perimeter and no new secret
   exists. A page that opens with a queue already waiting raises **one** summary
   instead of a burst — the count and the newest conversation id and verdict,
   tagged `bastion-handoff-queue` — and stays silent when the queue is empty;
   rows queued while the tab is open still notify individually, and the first
   summary also primes the `sessionStorage` seen-set so the next page load does
   not summarise the same queue again. That policy is pinned by
   `tests/test_handoff_notifications.py`, which runs the shipped script under
   Node against a stub DOM and `Notification`. A denied or dismissed permission
   degrades to the panel and never breaks the page. The limit is stated rather
   than hidden: a notification reaches only a browser that is open and has been
   granted permission, and nothing pages a person whose browser is closed.

9. **An operator can acknowledge a handoff and read its transcript
   (IDEA-071).** The dashboard panel posts
   `POST /api/handoffs/{conversation_id}/acknowledge` (operator/admin,
   tenant-scoped) and the gateway appends one `HANDOFF_ACKNOWLEDGED` row whose
   actor and timestamp are the row's own and whose metadata carries the
   conversation id and verdict — never the text. One acknowledgement per
   conversation: a second call is a no-op and re-renders the acknowledged state,
   so two operators clicking together do not stack records, and an unknown or
   foreign conversation answers `404` instead of creating a row about another
   tenant.

   The transcript is `POST /api/handoffs/{conversation_id}/transcript`,
   **admin-only** because it decrypts escrow: it finds the newest escrowed
   `INPUT_RECEIVED` and `RESPONSE_SENT` rows for the conversation, reads each
   through `read_payload_escrow` (appending its own `ESCROW_ACCESSED` row, as
   `POST /api/audit/{id}/escrow` does), and renders the turns as escaped text.
   The plaintext is never written to the ledger, a trace or a log. With escrow
   off or the entry expired there is no row to read, so the fragment says the
   transcript is unavailable and the panel offers no control. Acknowledge is
   ownership, not resolution: there is still no channel to answer on
   (decision 6), and deleting or editing the handoff remains impossible by
   construction.

7. **Sentiment is a UX signal, not a security control.** Nothing in
   `THREAT_MODEL.md` is mitigated by it: a hostile caller can phrase frustration
   to generate tickets, a hostile tool result cannot generate one, and a missing
   verdict means only that the heuristic did not fire. Security escalation stays
   the incident tiers in `SECURITY.md`, driven by `SECURITY_INCIDENT` rows.

## Consequences

**Pros**

- An operator can see that a caller is stuck without reading every transcript,
  and the row is tenant-scoped and hash-chained like any other evidence.
- The stage is deterministic, on-box and cheap: no model, no network, no new
  failure mode between DLP and the model call.
- The ledger separates a UX signal from a security incident, so the incident
  panel keeps meaning what it meant.
- The detector is a pure function, so its behaviour is pinned by a test rather
  than by a prompt.
- The queue is visible where an operator works and a second signed-in browser
  is told about a new handoff, without a push service or a new egress path.
- An operator can mark a handoff as owned and an admin can read what caused it
  while the escrow entry lives, from the same panel, with every read audited.

**Cons**

- A marker lexicon still misses a complaint phrased outside its vocabulary and
  without a restatement; the rule is measured on 24 complaints and 29 neutrals,
  which bounds its false-positive rate on that set but does not prove it on
  traffic nobody has written a transcript for yet, and the lexicon is English.
- History and `conversation_id` are client-supplied, so a caller can hide
  frustration by omitting turns and can generate tickets deliberately.
- The queue is passive: nobody is paged, and a handoff row alone does not mean
  anyone responded. The browser notification narrows that gap only while a tab
  is open with permission granted; a closed laptop learns nothing.
- Acknowledge records intent and nothing else: there is no SLA timer, no
  assignment and no resolution state, so an acknowledged row is not evidence
  that anyone helped. The transcript exists only while escrow is on and inside
  its 24-hour window, and only for an `admin`, so an operator can own a handoff
  whose cause they cannot read.
- One more ledger member widens the vocabulary again, which ADR-007 decision 7
  allows only as a named exception.
