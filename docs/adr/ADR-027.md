# ADR-027: Registered Non-Human Principals and the Four-Eyes Owner Rule

**Status:** Accepted  
**Date:** 2026-11-19  
**Last modified:** 2026-11-19

## Context

Every identity the control plane accepted was a human OIDC subject. An automated
caller had two bad options: borrow a human's token, so its requests shared that
human's budgets and were attributed to them, or log in as a human through the
public `bastion-cli` client. Neither answer satisfies the first question an
auditor asks — "which agent did this, and for whom?" — and neither lets one
human's agent be suspended without suspending the human or their other agents.
The four-eyes rule had the same edge: `can_be_decided_by` compared the approver
with the initiator's subject only, so a human could approve their own agent's
mutating call.

The ledger was the constraint that made this more than a feature. Its v2
preimage hashes the six original fields plus the version and the metadata
digest, and `verify_audit_chain` recomputes that preimage for every historical
row. Adding attribution fields to the preimage without versioning them would
have made every pre-existing record fail verification, and rewriting the chain
is exactly what the ledger exists to prevent.

## Decision

1. **An agent is a confidential Keycloak client with a service account.** Each
   registered agent is a `client_credentials` client with
   `serviceAccountsEnabled: true` and no interactive flows. A hardcoded-claim
   protocol mapper sets `bastion_actor_type=agent` on its access token; that
   marker — not a client-id naming convention and not a realm role — is what
   `TokenValidator` reads. The token's `azp` is the registry key; its `sub`
   (the service-account user id) stays the ledger's `actor_id`. A human token
   from the dashboard client cannot carry the marker, because the mapper exists
   only on agent clients.

2. **The registry row is the single allow switch.** `agent_registry` holds
   `agent_id`, `owner_sub`, `tenant_id`, `status`, `expires_at`,
   `allowed_tools`, `allowed_route_aliases` and `budget_key`. `authorize_agent`
   checks row presence, status, expiry, tenant and path in one place at ingress.
   There is deliberately no second quarantine table: suspension is the row's
   `status`, so there is one switch to audit and one value to flip. A refusal
   commits its `SECURITY_INCIDENT` row before the `403` is raised, so the denial
   is visible even though the request's own transaction rolls back, and the
   request never reaches the handler that could enqueue work.

3. **An agent token is not a session credential.** Agents may call the `/v1/`
   API prefixes only. `get_auth_context` refuses any agent request outside them,
   and the login and callback routes carry `refuse_agent_principal`, which
   rejects an agent bearer before login state or an `auth:session:*` key could
   be written. The dashboard, approval queue and audit reads are unreachable.

4. **The ledger is versioned, not rewritten.** v3 appends the actor triple
   (`actor_type`, `agent_id`, `owner_sub`) to the v2 preimage, with
   `actor_type` constrained to `human`/`agent`; v1 and v2 rows keep their
   original preimage and still verify. An agent row must name its `agent_id`;
   `owner_sub` is carried whenever the registry row is known, including a denial
   for a suspended agent, and stays NULL for an unregistered client, whose owner
   is by definition unknown. Editing any of the three breaks verification.

5. **Budgets and route aliases are per agent.** `rate_limit_subject` is the
   registry row's `budget_key` (default the agent id), so two agents of one owner
   have independent request and token buckets; one can be exhausted while the
   other still reserves. `allowed_route_aliases` bounds the aliases the router
   may choose for an agent; a route outside the list is refused after the
   decision, because the decision — not a client hint — is authoritative.

6. **Tool access is the catalog intersected with the role and the allowlist.**
   `docs/tools/v1.json` remains the outer gate: an allowlisted tool the catalog
   never approved is refused as `not_in_catalog`, and the allowlist can only
   narrow. An empty `allowed_tools` means no tools. The refusal is recorded as a
   `TOOL_REQUESTED` row with outcome `not_allowlisted`.

7. **The four-eyes rule also excludes the owner.** A mutating ticket carries
   `initiator_owner_sub` when its initiator is an agent, and both the
   application check (`can_be_decided_by`) and a database `CHECK` refuse the
   agent's subject or its owner as approver. An owner may originate an agent's
   call or review it in the dashboard, but cannot be the second pair of eyes for
   it; another human in the tenant with a satisfying role must decide. This is
   the conservative reading the backlog deliberately left to the ADR.

8. **`config/agents/registry.json` is the reviewable mirror, the database row is
   the truth.** `validate_rbac.py --strict` proves the three sources agree: every
   agent-marked client has a row, no row allowlists a tool the catalog lacks, and
   every allowlisted tool's `required_role` is satisfied by that client's
   service-account roles. The one-shot `migrate` service seeds missing rows from
   the file; it never deletes or overwrites an operator's row.

## Consequences

- **Pros**: every ledger row names the agent and (when known) the human it acts
  for; an agent is suspended or expired without touching its owner; per-agent
  request and token budgets are independent; a stolen agent secret cannot open a
  dashboard session; Sonar-style "who approved my robot?" questions have a
  data-model answer; the ledger upgrade is additive, so existing evidence keeps
  verifying.
- **Cons**: a new agent needs a Keycloak client, a registry row and a realm
  mapper, so onboarding is not self-service; the ingress now reads the registry
  on every agent request; `agent_registry` is another table an operator can get
  wrong, which is why `validate_rbac.py --strict` is the merge-blocking check;
  the conservative owner rule means one-person teams need a second human to
  approve any mutating agent call.
- **Residual risk**: `owner_sub` is trusted from the registry row — a wrong
  owner misattributes the ledger and misapplies the four-eyes exclusion, so the
  row is an owner-only write; the marker claim is only as strong as the realm
  export that defines it; and the agent bearer still travels as a shared secret
  (the `pki` overlay's X.509 client authentication is the documented upgrade).
  Route-alias enforcement happens after classification, so a refused turn has
  already been classified but never sent upstream.
