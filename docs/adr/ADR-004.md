# ADR-004: OmniRoute Model Routing & Failover

**Status:** Accepted  
**Date:** 2026-11-09  
**Last modified:** 2026-11-09

## Context

The agent needs to route prompts to the correct model backend depending on sensitivity, cost, and availability. There must be a local fallback (RTX 3060 Ti) for confidential prompts, and cloud providers for general use. Provider failover must be transparent to the agent code.

The local backend is a single RTX 3060 Ti with 8 GB of VRAM: Qwen 2.5 7B at Q4_K_M plus an 8k context fits, but only one request can be in flight, so local capacity is scarce. OmniRoute keeps its routing state in SQLite rather than a declarative file, and every service is bound to loopback on this host. The trade-offs are an extra network hop on every completion and one more stateful component to back up.

## Decision

1. **OmniRoute as the single upstream endpoint**: The FastAPI gateway and ARQ worker send all chat completions to `http://omniroute:20128/v1/chat/completions` (OmniRoute listens on 20128; the gateway owns 8000). No direct `openai` or `anthropic` SDK calls from agent code. The `/v1` plane requires the bearer credential in `OMNIROUTE_API_KEY` (`REQUIRE_API_KEY=true`).

2. **Model alias routing**: The agent sets the `model` field in the chat completion payload:
   - `model: "local-llama"` → OmniRoute dispatches to `llama.cpp` (RTX 3060 Ti, Qwen 2.5 7B Q4_K_M, served under the alias `qwen2.5-7b-instruct-q4_k_m`). Single target, **no fallback**.
   - `model: "cloud-primary"` → OpenRouter, as a `priority` combo: `openai/gpt-4o-mini` first, `anthropic/claude-haiku-4.5` on failure. There is no separate `cloud-fallback` alias; failover is internal to the combo.

3. **Routing policy via classifier**: The ONNX sensitivity classifier tags each prompt. If `CONFIDENTIAL`: set `model: "local-llama"`. If `PUBLIC`: set `model: "cloud-primary"`. Prompts below the confidence threshold are treated as **confidential (fail-closed)**: the cost of a false negative is an exfiltration, the cost of a false positive is local GPU time.

4. **Health checks & circuit breaking**: OmniRoute monitors upstream health and exposes `/api/health` (used by the container healthcheck). Cloud models fail over within `cloud-primary`; `local-llama` has no cloud target, so a `llama.cpp` outage fails closed with an error rather than silently sending confidential prompts to a third party. Availability is recovered by restoring the local backend.

5. **OmniRoute config externalized**: OmniRoute persists its state in SQLite, so `config/omniroute/config.yaml` is the declarative contract (provider node, connections, combos) applied idempotently by `scripts/omniroute_bootstrap.py`:
   - provider node `openai-compatible-chat-local`: `http://llama-cpp:8080/v1`, prefix `llama`, credential from `LLAMA_API_KEY`;
   - connection `openrouter`: `https://openrouter.ai/api/v1`, credential from `OPENROUTER_API_KEY`;
   - combos `local-llama` (priority, one local target) and `cloud-primary` (priority, two cloud targets);
   - gateway API key stored in `OMNIROUTE_API_KEY`.

   Re-running the bootstrap after `docker compose down -v` restores the whole routing plane and smoke-tests both aliases.

## Consequences

- **Pros**: Agent code is completely provider-agnostic; switching models is a config change, not a code change; local fallback ensures availability without cloud costs for sensitive prompts.
- **Cons**: One more moving part (OmniRoute); requires managing API keys for cloud providers; latency added by the extra routing hop.
