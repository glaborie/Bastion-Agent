# ADR-028: Stateless MCP on the Official Python SDK

**Status:** Proposed
**Date:** 2026-11-20
**Last modified:** 2026-11-20

## Context

ADR-009's four gates exist and are tested, but they are reachable only from the
gateway routes and the ARQ worker: there is no `/mcp` route and no MCP client in
the tree, so an external agent tool client has nothing to speak to. IDEA-061
opens the northbound side and, before any code, made the transport a decision:
either the official Python MCP SDK supports the 2026-07-28 revision, or the
stateless wire is built in-tree.

The revision matters because it changed the shape of the protocol. A
2026-07-28 request is self-describing — `params._meta` carries the protocol
version and the client's capabilities — there is no `initialize` handshake, no
`Mcp-Session-Id`, and the routing headers `Mcp-Method`/`Mcp-Name` are validated
against the body before dispatch. A hand-rolled layer would therefore have to
reimplement an envelope, a header ladder, `server/discover` and the revision's
error codes, and keep them in sync with a moving specification.

The deployment constraint is the existing gateway: one FastAPI process per
container, Python 3.11, `uv`-locked dependencies, Keycloak access tokens
validated by `gateway/auth/oidc.py`, agents admitted as registered non-human
principals (ADR-027). Whatever serves `/mcp` must fit that, and it must not add
state a restart would lose.

## Decision

1. **Use the official Python SDK, pinned `mcp==2.3.0`** (released 2026-10-02).
   It declares 2026-07-28 as its modern revision (`server/discover` answers
   `supportedVersions: ["2026-07-28"]`) and serves every earlier revision on the
   legacy leg. The in-tree wire layer is rejected: it would be a second
   implementation of semantics the SDK already carries.

2. **Serve the low-level `Server`** with `on_list_tools` / `on_call_tool`
   handlers, mounted at `/mcp`, built with
   `streamable_http_app(stateless_http=True)`. The host app's lifespan enters
   `server.session_manager.run()`; mounting disables the SDK app's own lifespan,
   and without that entry the first request fails. The endpoint is a `Mount`,
   which redirects `/mcp` to `/mcp/` (307) unless the mount and
   `streamable_http_path` are arranged so the exact path answers.

3. **Authentication stays ours.** The SDK's `AuthSettings`/`TokenVerifier`
   OAuth resource-server machinery is not used: the tokens are Keycloak access
   tokens and their validation, audience and agent-registry checks already live
   in `gateway/auth/`. A Bearer wall wraps the mount and refuses an
   unauthenticated request with `401` before the MCP app sees it.

4. **The modern envelope is required.** The spike showed that a request without
   `params._meta` is accepted on the pre-2026 leg, where the `Mcp-Method`
   header/body comparison is skipped: with `Mcp-Method: tools/list` on a
   `tools/call` body the legacy path still executed the tool, while the same
   request carrying the modern envelope was refused `-32020` before dispatch.
   The route therefore refuses the legacy leg; otherwise the header check the
   revision promises is silently absent.

5. **Tools only.** No resources and no prompts are registered, so their methods
   answer `-32601 Method not found`; `stateless_http=True` removes the
   server-to-client channel, so server-initiated sampling, elicitation and roots
   cannot be issued at all. That is the "refused by default" stance IDEA-061
   asks for, enforced by the transport rather than by a filter.

6. **This ADR stays `Proposed` until phase 1 lands.** The upstream MCP client,
   the catalog's `server`/`description_hash`/`input_schema_hash` fields, the
   per-surface audience and the tool-poisoning controls are recorded in
   IDEA-061, not decided here; this record covers the transport that phase 1 is
   built on.

## Consequences

- **Pros**: the revision's envelope, header ladder, `server/discover` and error
  codes come from the SDK instead of being reimplemented; the surface is
  stateless by construction, so a restart loses nothing and no session store is
  needed; the handlers reuse `agent.tools.execution.request_tool_execution`, so
  the gates stay in one place; the spike's four behaviours (no handshake, no
  session header, `-32020` before dispatch, `-32601` for resources) are
  reproduced with the pinned version, not inferred from release notes.
- **Cons**: a new dependency and its transitive tree in the gateway image; the
  SDK's v2 API is young (2.x since 2026-07-28, 2.3.0 at the time of writing), so
  a pin bump is a review, not a routine update; the legacy fallback has to be
  closed explicitly or the modern validation can be bypassed; because our auth
  is a wall outside the SDK, per-method scopes are ours to enforce in the
  handler; and the mount's trailing-slash behaviour needs one explicit test so a
  client is not asked to follow a redirect.
