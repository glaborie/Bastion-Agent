# ADR-018: Signed Job Envelopes for Worker Identity

**Status:** Accepted  
**Date:** 2026-11-12  
**Last modified:** 2026-11-12

## Context

The ARQ queue is a Redis list. `agent/runtime.py::execute_tool_job` rebuilt `AgentContext` from the job payload, so `actor_id`, `tenant_id` and `roles` were whatever the enqueuer wrote, and the worker verified none of them. `THREAT_MODEL.md` T8 recorded the consequence: anyone who can write the queue can assert any principal, a forged `initiator_id` weakens the four-eyes comparison that ADR-010 decision 3 rests on, and a forged `tenant_id` crosses the boundary ADR-015 decision 4 enforces everywhere except this path. The control table listed "signed or re-derived identity on queued jobs" as PLANNED with no implementation behind it.

Two shapes were available. The first is an opaque reference: the enqueuer writes a server-side record and the job carries only its id. That needs a new store, a durable write before every enqueue, and expiry and cleanup rules — and the demo CLI, which is the only enqueuer of `execute_tool_job` today, would need database access it does not otherwise use. The second is a signed envelope: the enqueuer mints an HMAC over the exact fields, the worker verifies it with a key it never discloses. The second reuses the approval-token idiom already in `db/models.py`, adds no table, and works for a CLI that already reads the process environment. It is the shape this ADR records.

The choice is not "trust the queue" versus "trust nothing". It moves the threshold from *write access to Redis* to *write access plus the signing key*. That is a real boundary — a leaked Redis port, an SSRF, or a compromised container without the key no longer buys administrator-equivalent tool execution — but it is not a boundary against a host attacker, who has the `.env` the gateway signs with.

## Decision

1. **Every identity-bearing job travels in an envelope.** `agent/job_auth.py` defines the wire format `v1|<job kind>|<sha256 of the canonical field map>|<nonce>|<expires_at>`, signed HMAC-SHA256 and rendered as the three kwargs `job_nonce`, `job_expires_at`, `job_signature`. The field map is fixed per kind by `tool_job_fields`, `demo_job_fields` and `resume_job_fields`, sorted and canonicalised through `hash_payload`, so the worker can rebuild exactly the bytes the enqueuer signed. Signing a dict and sending a different one is therefore not possible: the helper returns the payload keys and the envelope together.

2. **The worker verifies before the guard, not after.** `execute_tool_job`, `run_demo_scenario_job` and `resume_tool_job` call `_reject_unsigned_job` first. A rejection returns `{"status": "unauthorized_job"}` with the reason (`unsigned_job`, `bad_signature`, `expired_job`, `replayed_job`, `malformed_envelope`, `signature_unverifiable`) before `request_tool_execution` runs, so no tool executes, no `PendingApproval` row is created and no `TOOL_EXECUTED` or `TOOL_REQUESTED` event is written.

3. **A dedicated key, refused at startup outside local development.** The key is `JOB_SIGNING_SECRET`, deliberately distinct from `APPROVAL_HMAC_SECRET`: a leaked job key must not mint approval capability tokens, and a leaked approval key must not forge identities. `Settings._reject_dev_secrets` refuses the documented development value in `staging` and `production`, alongside the vault, approval and Keycloak secrets. The gateway and the demo CLI mint; the worker only verifies.

4. **A nonce is burned exactly once.** Verification is followed by `SET job:nonce:<nonce> 1 NX EX <ttl>`, where the TTL is the configured window or the signature's remaining lifetime, whichever is longer; a second delivery of the same payload is `replayed_job`. Measuring from the deadline means a job that waited in the queue for most of its window cannot be replayed after it lapses. `JOB_SIGNATURE_TTL_SECONDS` defaults to 900, matching the approval window. A Redis failure while claiming the nonce is a rejection (`signature_unverifiable`), not a fall-through: a worker that cannot prove single use must not execute.

5. **`resume_tool_job` is signed even though it needs no identity.** Execution re-derives the initiator, tenant and role from the ticket row and re-checks four-eyes, so a guessed ticket id is already harmless. Signing it anyway keeps one mint/verify path for every enqueue site instead of a rule that future jobs must remember. The two cron sweeps are in-process calls and carry no payload, so they are unchanged.

6. **A forged job writes no ledger row.** The only identity in a forged payload is the attacker's, and a hash-chained `SECURITY_INCIDENT` naming an attacker-chosen principal would poison the ledger it is supposed to protect. The refusal is a structured worker log line and a `bastion.job.rejected` span attribute; the gateway's own authentication remains the place where a real principal's rejection is recorded.

7. **Rotation is a settings-cache reset, and the queue must drain.** `reset_settings_cache()` is the supported hook. Rotation is not rolling: a worker holding the old key rejects jobs minted with the new one until it reloads, so rotate while the queue is idle or accept a bounded window of `bad_signature` refusals that the operator retries. The residual is recorded here rather than hidden behind a dual-key verification path that nothing yet needs.

## Consequences

- **Pros**: Forged `actor_id`, `roles` and `tenant_id` no longer produce tickets, executions or ledger rows; the boundary no longer depends on "only trusted code can reach Redis"; the failure is fail-closed and observable in logs and traces; the envelope reuses a canonicalisation and HMAC idiom already reviewed for approval tickets; a captured payload is worth one execution inside a 15-minute window at most.
- **Cons**: Every enqueue site now holds a secret — including the demo CLI, which means the CLI is administrator-equivalent by design and must stay documented as such; a rotated key needs a coordinated restart; the nonce table is another Redis namespace whose keys live as long as the signature window; and the envelope signs a field map, so adding a field to a job without adding it to the matching `*_fields` helper silently weakens the binding for that field (the worker would still verify, but the field would be unsigned).
- **Residual risk**: whoever holds `JOB_SIGNING_SECRET` — the host, the `.env`, or anything that can read the gateway's environment — can mint any identity, which is why T8 keeps a residual note rather than claiming T8 is closed. Transport-level protection for the queue (TLS, per-service Redis ACLs, no host port) remains IDEA-023. There is no key rotation schedule and no key version tag in the envelope: a rotation is a full switch, and an old key remains valid until every process reloads. These are follow-ups, not silent acceptances.
