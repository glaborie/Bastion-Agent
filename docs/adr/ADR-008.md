# ADR-008: Evolution Roadmap & Version Policy

**Status:** Accepted  
**Date:** 2026-11-09  
**Last modified:** 2026-11-11

## Context

Bastion-Agent must evolve systematically from a minimal viable product to a production-hardened system without breaking changes, undocumented upgrades, or technical debt accumulation. Each version must have a clear purpose and upgrade path.

The project is delivered as a Docker Compose stack, so every phase must remain deployable with the same operational model. Changing the control plane's security invariants between phases is acceptable only when an ADR records why.

## Decision

1. **Six-phase version plan** (v0.1 → v0.6):
   - **v0.1**: MVP — core gateway, DLP, routing, audit, basic dashboard. "It runs, it blocks, it logs."
   - **v0.2**: Hardening — multi-model DLP (ADR-011: ONNX classifier selection), eval-driven routing, canary hardening, audit verification, WebSocket dashboard.
   - **v0.3**: Multi-tenancy — tenant isolation, Redis namespaces, multi-region routing, approval SLA, async audit export, Presidio GPU. (Tenant isolation of Redis keys, approval rows and audit rows was delivered early in v0.2 under IDEA-001; see ADR-015. PostgreSQL row-level security remains here as the defence-in-depth step.)
   - **v0.4**: Adaptive policy — adaptive DLP, LLM-as-judge egress, dynamic RBAC, multi-step HITL.
   - **v0.5**: Production readiness — PostgreSQL HA, Redis HA, multi-node ARQ, backup/restore, compliance mode, secrets management. (Per-principal request rate limiting, originally listed here, was delivered early in v0.2; see ADR-013. Token and cost budgets remain open.)
   - **v0.6**: Future-proofing — multi-provider OmniRoute, local model hot-swap, custom DLP adapters, A2A (MCP), continuous eval pipeline, edge deployment.

2. **Semantic versioning**: `MAJOR.MINOR.PATCH`:
   - `MAJOR`: Breaking API changes (e.g., v1.0.0 when the gateway schema changes).
   - `MINOR`: Feature additions that are backward-compatible (e.g., v0.2.0 adds eval-driven routing).
   - `PATCH`: Bug fixes, non-breaking internal changes.

3. **Upgrade compatibility**: Each phase is a drop-in Docker Compose upgrade (`docker compose down && docker compose pull && docker compose up -d`). No database schema migrations that require downtime (except v0.3 RLS, which uses `WITH (ENABLE ROW LEVEL SECURITY)` online).

4. **Roadmap document**: `docs/adr/ADR-Index.md` is the authoritative roadmap. No informal "we should..." — all evolution is tracked as ADRs or in `docs/backlog.md` for future consideration.

5. **Feature freeze per phase**: No new features added phase-internal; only the phase's defined scope. New ideas go to `docs/backlog.md` and are scheduled for the next phase.

## Consequences

- **Pros**: Predictable upgrades; no surprise breaking changes; clear roadmap for stakeholders; each phase has a "done" definition; guards against scope creep.
- **Cons**: Requires discipline to not add "just one more thing" per phase; six versions may feel slow for users wanting all features immediately; roadmap document must be kept in sync.
