# ADR-013: Per-Principal Rate Limiting

**Status:** Accepted  
**Date:** 2026-11-10  
**Last modified:** 2026-11-14

## Context

ADR-007 deferred per-user dashboard rate limiting to Phase 1 and ADR-008 listed
rate limiting under v0.5 production readiness. Neither recorded a design, and
the gap was visible in two places: THREAT_MODEL T12 carried "per-principal rate
limits and token budgets" as PLANNED with "none found", while `CONTROL.md`
described a 60 req/min dashboard limit that no code enforced. A gateway that
can be driven at arbitrary request rate is an unbounded-consumption risk
(LLM06:2026) even when every individual request passes DLP and RBAC: the chat
path spends inference tokens, and a polling client can pin a database connection
and a worker slot without ever tripping another control.

The gateway is horizontally scalable — the dashboard, chat and approval routes
are replica-safe and carry no in-process state. A per-process counter would
therefore multiply the effective budget by the replica count and enforce
different limits after a restart. The limiter has to live in the one shared
store every replica already uses: Redis. That store is not optional on the chat
path — it holds the token vault, the session canary and the quarantine state —
so the rate limiter adds no new availability dependency.

## Decision

1. **One bucket per principal and scope.** The key is
   `ratelimit:<scope>:<jwt-sub>`. The principal is the validated JWT `subject`,
   never a username, session cookie value or client address. A caller presenting
   another principal's token is already rejected by ADR-001; a caller cannot
   reset a bucket by signing in again, because the subject survives the session.

2. **Token bucket, evaluated in one Lua script.** Capacity is the configured
   request budget and refill is continuous at `capacity / window`, so a client
   that has been idle may burst up to the capacity and then settles at the
   sustained rate. Consume, refill and expiry are one atomic script, which is
   what makes concurrent requests from several replicas safe: 25 simultaneous
   requests against a capacity of 10 yield exactly 10 permits. The script reads
   Redis `TIME` rather than the application clock, so replicas whose system
   clocks disagree still share one timeline. The key expires once the bucket
   would be full again; an idle principal leaves nothing behind.

3. **Two scopes with separate budgets.** `dashboard` covers the server-rendered
   pages, the HTMX partials and the JSON APIs they poll (approvals, audit, eval
   health) and defaults to **60 requests per 60 seconds** per principal. `chat`
   covers `POST /v1/chat` and defaults to **120 requests per 60 seconds**,
   because a turn is deliberate operator work that spends inference while a
   dashboard poll is background noise. Both the window and both budgets are
   settings (`RATE_LIMIT_*`), so a deployment can tighten them without a code
   change. The dashboard budget is the stricter one by design and is shared
   across the routers it covers: polling the approval queue and the audit page
   spends the same bucket.

4. **Authentication first, then the bucket.** Enforcement is a FastAPI
   dependency attached to the dashboard, approvals, audit, evaluation and chat
   routers. It depends on `get_auth_context`, so an unauthenticated request is
   rejected as 401 before a bucket is touched and no anonymous caller can
   consume a principal's budget. Health probes, the OIDC login/callback/logout
   routes and static assets are deliberately exempt: they either have no
   principal yet or must remain reachable while the rest of the stack is
   saturated.

5. **A refusal is actionable.** Every limited response carries the draft
   `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` fields; a
   refusal adds `Retry-After` in seconds. JSON callers receive `429` with a machine-readable detail; dashboard
   pages and HTMX partials render the same "too many requests" page as other
   dashboard errors, with the `Retry-After` header preserved, so a polling
   fragment never swaps raw JSON into the UI.

6. **Fail closed.** If Redis cannot answer, the dependency returns `503` and the
   route does not run. Silently degrading to unlimited would make the limiter
   the only control that disappears exactly when the system is under stress, and
   Redis is already a fail-closed dependency for DLP and egress. The trade-off
   is explicit: a Redis outage denies dashboard and chat traffic, which is the
   same outcome the vault and canary registry already impose on chat.

7. **Login throttling stays with Keycloak.** The gateway does not rate-limit
   `/auth/login` or `/auth/callback` by address: correct client-IP extraction
   needs proxy trust configuration that differs per deployment, and Keycloak's
   brute-force protection (`bruteForceProtected`, `failureFactor` 10,
   `maxFailureWaitSeconds` 900) already owns the credential check. Per-principal
   token and cost budgets remain future work; this ADR bounds request rate, not
   spend per window. That gap is designed in ADR-020 (Proposed), which is not
   yet enforced by the code described here.

8. **The algorithm is tested against a live Redis.** `fakeredis` cannot execute
   the Lua script without an optional dependency, so the suite does not mimic
   the bucket in Python. Exhaustion, refill, principal and scope isolation,
   concurrent overspend and key expiry run against Redis 7 in CI, where the
   service is provisioned; locally they skip unless `REDIS_TEST_URL` is set.

## Consequences

- **Pros**: One budget per principal across every replica; no new datastore or
  dependency; bursts stay possible after idle periods, which matches how an
  operator actually works; the refusal is self-describing and browser-friendly;
  the policy is configuration, not code; an outage cannot silently disable the
  control.
- **Cons**: Redis becomes a synchronous hop on dashboard requests as well as
  chat, so a Redis outage now denies the dashboard too — accepted because the
  same store already gates chat and egress; a token bucket permits a full-
  capacity burst, which is intentional but means the first second of a window
  can be much busier than the average; budgets are per principal, so one
  compromised token can still spend its full allowance, and there is no
  per-tenant aggregate or cost budget yet; login endpoints rely on Keycloak
  rather than the gateway, so a deployment that replaces Keycloak must supply
  its own brute-force protection; the Lua script is only exercised where a real
  Redis is available, so a local `pytest` run without `REDIS_TEST_URL` skips the
  algorithm tests (CI does not).
