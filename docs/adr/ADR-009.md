# ADR-009: Four-Gate Tool Governance Model

**Status:** Accepted  
**Date:** 2026-11-09  
**Last modified:** 2026-11-10

## Context

Bastion-Agent requires a defense-in-depth governance model that prevents prompt-injection bypasses and enforces data-leak prevention at every layer. Swiss regulatory environments (FINMA, GDPR, Swiss Banking Act) demand that security decisions cannot be overridden by model reasoning or prompt manipulation. Authorization must be enforced by deterministic platform controls, not by model instructions.

The occludra/gateway project demonstrates fail-closed DLP proxying, while Microsoft's Enterprise Agent Security and Tool Governance pattern provides a four-gate runtime model for tool calls. Bastion-Agent must adopt an equivalent model that maps to its existing Keycloak OIDC, OmniRoute, ARQ worker, and PostgreSQL audit infrastructure.

## Decision

1. **Four serial runtime gates** — every tool call must pass through four independent gates in series. Any gate can stop the call; no gate can grant what a later gate refuses.

   1. **Gate 1: Tool catalog allow-list** (`docs/tools/v1.json` / capability registry)
      - Tools are discovered via `@tool` decorators and registered on import.
      - The catalog is versioned and immutable. Agent sees only tools exposed in the current version.
      - `require_approval` is declared per tool in the catalog. It must be true
        for a mutating tool; a read-only tool that already declares a
        `required_role` may be tightened to require approval, but the catalog can
        never waive four-eyes or grant a different role.
      - Return code `-32003` for tools outside the catalog (unknown tool).
      - Runtime enforcement: `available_tools()` — the model-facing list — returns
        only catalog-approved definitions, and
        `agent.tools.execution.request_tool_execution()` re-checks the catalog
        before argument validation, RBAC or ticket creation. The gateway and the
        ARQ worker call `verify_registry()` at startup, so a registered but
        unapproved tool stops the process. An unreadable catalog exposes no
        tools (fail closed) and is audited as `catalog_unavailable`.
      - An approved ticket is re-checked against the catalog before execution: a
        tool removed from the allow-list (or whose required role changed) after
        approval is marked `FAILED` with a `SECURITY_INCIDENT`, not run.
      - The catalog is checked in at `docs/tools/v1.json` and compared with the
        registry by `scripts/validate_tool_catalog.py --check`; `--write` is the
        reviewable approval step. The image copies `docs/` so the container
        enforces the same file.

   2. **Gate 2: Connection identity and RBAC** (Keycloak OIDC JWT)
      - FastAPI dependency `require_roles` validates RS256/ES256 JWT via JWKS cache.
      - Identity derived from `sub` claim and `realm_access.roles`.
      - App roles: `admin`, `operator`, `analyst`, `readonly`.
      - Operator roles are time-bound and require sponsorship (four-eyes).

   3. **Gate 3: Human approval** (ARQ suspension + PendingApproval)
      - State-changing tools (`read_only=False`) pause execution in ARQ worker.
      - `PendingApproval` record created with HMAC-signed nonce, tool name, arguments hash, initiator_id, expiration.
      - Approval via `/api/approvals/{id}/action` with `approver_id != initiator_id`.
      - Approval is bound to exact action hash — one-time use, expires, single-use.

   4. **Gate 4: Source-side entitlement and egress filtering** (tool implementation + egress canary)
      - Tool implementation validates `AgentContext.user_roles` against `required_role`.
      - Tool output is framed as untrusted data; canary tokens are checked before return.
      - Egress filter screens for PII leaks, prompt injection, and canary presence.
      - Audit log entry written with hash chain linking to previous record.

2. **Four questions per tool call** — every call must answer:
   1. Who is calling? → JWT `sub`/client_id, identity kind (user/agent)
   2. Which tools exist and can run? → Catalog version, `allowed_tools` list
   3. What data/actions are permitted? → Token claims (`roles`/`scp`), data classification
   4. Who saw it and how do we stop it? → Audit trail, kill switch

3. **Request context is not authorization** — everything in agent request context is tainted:
   - Forwarded headers, payload tenant/user ids, metadata, tool arguments, retrieved content, memory, model output.
   - Authorization derived only from verified identity in a deny-by-default policy decision point.
   - Re-check authorization at every tool and resource boundary at call time.

4. **Bounded autonomy budgets** — server-enforced limits:
   - `MAX_TOOL_CALLS_PER_RUN` (default 4)
   - `MAX_TOKENS_PER_RUN`
   - `COST_BUDGET_CHF`
   - `TIME_BUDGET_SEC`
   - Autonomy profile selected from verified identity, never from prompt.

5. **Evidence ledger and run certificate** — append-only, hash-chained:
   - Every agent step recorded as digest, not raw content.
   - Run certificate signs ledger head + artifact digest + approvals.
   - Run is complete only with valid, non-withheld certificate.

## Consequences

- **Pros**
  - Defense-in-depth by design; model cannot bypass platform controls.
  - Swiss regulatory compliance: deterministic enforcement, auditability, four-eyes.
  - Tool governance owned by Platform/AI CoE, not agent developers.
  - Kill switch tiers allow immediate disable without code deploy.
  - Audit trail is non-repudiable with hash chain + signed certificate.

- **Cons**
  - Added latency from approval workflow (~30s for writes).
  - More moving parts to configure and test.
  - Operator availability required for HITL gates.
  - Requires disciplined tool declaration and version pinning.
