### IDEA-001: Tenant isolation for Redis keys and Postgres rows

- status: inbox
- priority: P2
- phase: v0.3
- area: agent
- tags: multi-tenancy, redis, postgres, rbac
- depends-on: -
- spec: ADR-008
- created: 2026-11-09
- updated: 2026-11-09
- source: ADR-008, phase v0.3 scope

**Problem**

Every subsystem assumes a single tenant: the vault key is
`vault:<sha256(session)>`, canaries are per session, quarantine is per session and
audit rows carry no tenant. Two customers on one stack would share a Redis
namespace and a Postgres schema, so one operator role could reach the other
tenant's data through a guessed identifier.

**Outcome**

Every derived key and every audit row is scoped by a tenant id that
comes from the authenticated identity, cross-tenant access is impossible by
construction, and a test proves it by attempting the access.

**Acceptance**

- [ ] Tenant id resolved from the OIDC claim and stored on `PendingApproval` and `AuditLog`
- [ ] Vault, canary, quarantine and approval keys include the tenant prefix
- [ ] A test shows a session from tenant A cannot read a token or ticket from tenant B
- [ ] ADR documents the isolation model before implementation

### IDEA-002: Push approval decisions over WebSocket instead of 3 s polling

- status: inbox
- priority: P1
- phase: v0.2
- area: gateway
- tags: dashboard, websocket, hitl, latency
- depends-on: -
- spec: ADR-007
- created: 2026-11-09
- updated: 2026-11-09
- source: ADR-008, phase v0.2 scope

**Problem**

The dashboard polls `/api/approvals` every 3 seconds, so a second
operator can wait up to 3 seconds to see a ticket and every open tab generates
traffic that had to be excluded from tracing.

**Outcome**

The dashboard receives `APPROVAL_REQUESTED` and decision events on a
WebSocket, polling becomes a fallback, and the tracing exclusion for the poll URL
can be removed.

**Acceptance**

- [ ] `/ws/approvals` authenticated by the same session cookie and CSRF rules
- [ ] Ticket creation and decision broadcast to every connected operator
- [ ] Polling remains as a degraded fallback when the socket cannot connect
- [ ] A test drives two clients and asserts both see the decision

### IDEA-003: Route the ONNX ensemble to GPU to meet the 50 ms classify budget

- status: ready
- priority: P1
- phase: v0.2
- area: agent
- tags: onnx, gpu, latency, classifier
- depends-on: -
- spec: ADR-011
- created: 2026-11-09
- updated: 2026-11-09
- source: ADR-011, measured 41-98 ms per classify on CPU

**Problem**

`SensitivityClassifier.classify()` measures 41-98 ms on the CPU-only
host, so the stated sub-50 ms budget is missed and every chat turn pays it.

**Outcome**

With `onnxruntime-gpu` and CUDA visible to `gateway` and `worker`,
the ensemble meets the budget on the golden corpus and still runs on CPU when no
GPU is present.

**Acceptance**

- [ ] `onnxruntime-gpu` installed in the image with a CPU fallback path
- [ ] A benchmark over `tests/data/goldens.jsonl` reports p95 under 50 ms on GPU
- [ ] CPU-only verification still passes `tests/test_classifier_evals.py`
- [ ] ADR-011 records the measured numbers and the provider chosen

### IDEA-004: Export the audit ledger asynchronously for retention

- status: blocked
- priority: P2
- phase: v0.3
- area: db
- tags: audit, export, compliance, retention
- depends-on: IDEA-001
- blocked-by: tenant scoping decides the partition key of the export
- spec: ADR-008
- created: 2026-11-09
- updated: 2026-11-09
- source: ADR-008, phase v0.3 scope

**Problem**

The hash-chained ledger only grows; compliance retention requires a
portable export, and an export without a tenant dimension would leak across
customers.

**Outcome**

A worker job writes signed, chain-verified segments to object storage
with a manifest, and verification can be rerun against an exported segment.

**Acceptance**

- [ ] Export job pages the ledger without breaking the hash chain
- [ ] Manifest records segment bounds and the terminal hash
- [ ] `scripts/verify_audit_chain.py` accepts an exported segment
- [ ] Retention and deletion policy documented in COMPLIANCE.md

### IDEA-005: Reject canary prefixes shorter than eight characters at startup

- status: ready
- priority: P1
- phase: v0.2
- area: security
- tags: canary, egress, validation, config
- depends-on: -
- spec: ADR-012
- created: 2026-11-10
- updated: 2026-11-10
- source: review of EGRESS_CANARY_PREFIX handling

**Problem**

`EGRESS_CANARY_PREFIX` is read from the environment and used as the
match token for `inspect()`. An empty or one-character prefix either blocks every
response or matches arbitrary text, and nothing rejects it at startup.

**Outcome**

Settings refuse a prefix shorter than eight characters, the failure is
explicit at boot rather than at the first request, and a test pins the minimum.

**Acceptance**

- [ ] Settings validation rejects prefixes shorter than 8 characters
- [ ] Startup failure names the variable and the minimum length
- [ ] A test covers empty, one-character and valid prefixes
- [ ] `.env.example` documents the constraint

### IDEA-006: Add a deterministic egress canary demo

- status: done
- priority: P3
- phase: v0.2
- area: docs
- tags: demo, canary, egress
- depends-on: -
- spec: ADR-012
- created: 2026-11-09
- updated: 2026-11-10
- source: review of DEMO.md, Act 6

**Problem**

Asking a model to leak its system marker is not a demo: it may refuse,
comply or paraphrase, so the evidence changed every run.

**Outcome**

`scripts/demo_egress.py` runs the real sanitizer, real Redis keys and
real vault against the exact completion text the egress stage would inspect.

**Acceptance**

- [x] One `CANARY-<uuid4>` per session, stable across turns
- [x] Leak blocked with empty delivered text and the session quarantined
- [x] Next turn rejected before inference
- [x] Vault marker restored only for its own session
- [x] Tool payload cannot close `</untrusted_content>`
- [x] Demo passes on the host and inside the gateway container
