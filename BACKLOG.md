### IDEA-001: Tenant isolation for Redis keys and Postgres rows

- status: inbox
- priority: P2
- phase: v0.3
- area: agent
- tags: multi-tenancy, redis, postgres, rbac
- depends-on: -
- spec: ADR-008
- created: 2026-11-09
- updated: 2026-11-09
- source: ADR-008, phase v0.3 scope

**Problem**

Every subsystem assumes a single tenant: the vault key is
`vault:<sha256(session)>`, canaries are per session, quarantine is per session and
audit rows carry no tenant. Two customers on one stack would share a Redis
namespace and a Postgres schema, so one operator role could reach the other
tenant's data through a guessed identifier.

**Outcome**

Every derived key and every audit row is scoped by a tenant id that
comes from the authenticated identity, cross-tenant access is impossible by
construction, and a test proves it by attempting the access.

**Acceptance**

- [ ] Tenant id resolved from the OIDC claim and stored on `PendingApproval` and `AuditLog`
- [ ] Vault, canary, quarantine and approval keys include the tenant prefix
- [ ] A test shows a session from tenant A cannot read a token or ticket from tenant B
- [ ] ADR documents the isolation model before implementation

### IDEA-002: Push approval decisions over WebSocket instead of 3 s polling

- status: inbox
- priority: P1
- phase: v0.2
- area: gateway
- tags: dashboard, websocket, hitl, latency
- depends-on: -
- spec: ADR-007
- created: 2026-11-09
- updated: 2026-11-09
- source: ADR-008, phase v0.2 scope

**Problem**

The dashboard polls `/api/approvals` every 3 seconds, so a second
operator can wait up to 3 seconds to see a ticket and every open tab generates
traffic that had to be excluded from tracing.

**Outcome**

The dashboard receives `APPROVAL_REQUESTED` and decision events on a
WebSocket, polling becomes a fallback, and the tracing exclusion for the poll URL
can be removed.

**Acceptance**

- [ ] `/ws/approvals` authenticated by the same session cookie and CSRF rules
- [ ] Ticket creation and decision broadcast to every connected operator
- [ ] Polling remains as a degraded fallback when the socket cannot connect
- [ ] A test drives two clients and asserts both see the decision

### IDEA-003: Route the ONNX ensemble to GPU to meet the 50 ms classify budget

- status: ready
- priority: P1
- phase: v0.2
- area: agent
- tags: onnx, gpu, latency, classifier
- depends-on: -
- spec: ADR-011
- created: 2026-11-09
- updated: 2026-11-09
- source: ADR-011, measured 41-98 ms per classify on CPU

**Problem**

`SensitivityClassifier.classify()` measures 41-98 ms on the CPU-only
host, so the stated sub-50 ms budget is missed and every chat turn pays it.

**Outcome**

With `onnxruntime-gpu` and CUDA visible to `gateway` and `worker`,
the ensemble meets the budget on the golden corpus and still runs on CPU when no
GPU is present.

**Acceptance**

- [ ] `onnxruntime-gpu` installed in the image with a CPU fallback path
- [ ] A benchmark over `tests/data/goldens.jsonl` reports p95 under 50 ms on GPU
- [ ] CPU-only verification still passes `tests/test_classifier_evals.py`
- [ ] ADR-011 records the measured numbers and the provider chosen

### IDEA-004: Export the audit ledger asynchronously for retention

- status: blocked
- priority: P2
- phase: v0.3
- area: db
- tags: audit, export, compliance, retention
- depends-on: IDEA-001

- spec: ADR-008
- created: 2026-11-09
- updated: 2026-11-09

**Problem**

The hash-chained ledger only grows; compliance retention requires a
portable export, and an export without a tenant dimension would leak across

- [ ] Manifest records segment bounds and the terminal hash
- [ ] `scripts/verify_audit_chain.py` accepts an exported segment
- [ ] Retention and deletion policy documented in COMPLIANCE.md

### IDEA-005: Reject canary prefixes shorter than eight characters at startup

- status: ready
- priority: P1
- phase: v0.2
- area: security
- tags: canary, egress, validation, config
- depends-on: -
- spec: ADR-012
- created: 2026-11-10
- updated: 2026-11-10
- source: review of EGRESS_CANARY_PREFIX handling

**Problem**

`EGRESS_CANARY_PREFIX` is read from the environment and used as the
match token for `inspect()`. An empty or one-character prefix either blocks every
response or matches arbitrary text, and nothing rejects it at startup.

**Outcome**

Settings refuse a prefix shorter than eight characters, the failure is
explicit at boot rather than at the first request, and a test pins the minimum.

**Acceptance**

- [ ] Settings validation rejects prefixes shorter than 8 characters
- [ ] Startup failure names the variable and the minimum length
- [ ] A test covers empty, one-character and valid prefixes
- [ ] `.env.example` documents the constraint

### IDEA-007: Route corporate-confidential documents without explicit markers to the local model

- status: inbox
- priority: P1
- phase: v0.2
- area: agent
- tags: classifier, calibration, dlp, routing
- depends-on: -
- spec: ADR-011
- created: 2026-11-10
- updated: 2026-11-10
- source: live traffic through POST /v1/chat on 2026-11-10

**Problem**

The classifier only routes to `local-llama` when it sees a marker. Measured on
the live stack today, "Q3 revenue forecast assumes a hiring freeze through
December" reached `cloud-primary` as PUBLIC with confidence 0.9875, and a
supplier indemnity clause reached it with 0.9804. The first matches only the
`commercial` rule at weight 2.0, which the deterministic floor scores
`2/(2+2)=0.50` against the 0.55 threshold (`agent/routing/classifier.py`,
`_classify_rules`); an indemnity clause of the same shape matches no rule at all
(measured: 0 markers). The ONNX ensemble cannot close the gap by design — it was
trained on harm, so secrecy that contains nothing harmful reads as safe
`public_content`. The documents a company most wants kept in-house —
forecasts, margin analysis, contracts — therefore leave for the cloud unless
someone happens to type "confidential".

**Outcome**

A prompt that is corporate-confidential by content, with no explicit marking,
routes to the local model or is refused, and the verdict with its evidence is
visible in the audit ledger and on the trace's server span. The documented
"single weight-2 marker stays borderline" policy is either revised with a
recorded rationale or replaced, and the evidence corpus is extended with this
class of text.

**Acceptance**

- [ ] `uv run pytest tests/test_classifier.py tests/test_classifier_evals.py -q` passes with a new assertion for an unmarked commercial prompt (a revenue forecast, a contract clause); no existing assertion is deleted to make the new one pass
- [ ] `uv run python scripts/demo_classifier.py "<sample>"` prints the new verdict and the rule or ensemble evidence that produced it, for both sample classes
- [ ] `docs/adr/ADR-011.md` records the choice (rule weight, new rule set, or a second model head), the re-measured benign false-positive and recall numbers, and the gap that remains
- [ ] The corpus gains rows of this class taken from measured live traffic, and ADR-011 still states it is calibration, not held-out evidence
- [ ] A live `POST /v1/chat` with such a prompt shows `bastion.classification=CONFIDENTIAL` and `bastion.route=local-llama` on the server span in the trace store

**Notes**

- This is documented policy, not a crash: the `_RULES` comment pins the 0.50 outcome deliberately and `test_a_single_codename_is_borderline_and_stays_public` enforces the same threshold for `codename`, so the fix is a decision with a false-positive budget attached, not an inline edit.
- Options seen so far: raise `commercial` to 3.0 (a lone forecast marker then scores 0.60), add a contract/legal rule set, or train a corporate-secrecy head. Weight tuning alone cannot cover the indemnity case, which matches nothing.
- Spotted while reviewing trace telemetry from a realistic traffic run: the misroute appeared as a PUBLIC `cloud-primary` turn in OpenLit. Related to IDEA-003 (classifier latency) through the same ADR-011 operating point.

### IDEA-008: Make the eval gate bit-reproducible across hosted runners

- status: inbox
- priority: P1
- phase: v0.2
- area: evals
- tags: ci, onnx, int8, calibration, golden-set
- depends-on: -
- spec: ADR-011
- created: 2026-11-10
- updated: 2026-11-10
- source: CI runs 42866889651 and 42870723135 on 2026-11-10

**Problem**

`Zero-tolerance eval gates (real ONNX models)` is red on `master` for two
consecutive commits even though one of them (`af91390`) only touches
`BACKLOG.md`. Both runs and a re-run land on an AMD EPYC 7763 runner and score
the benign golden rows `CONFIDENTIAL`/`unsafe_content` at 0.75–0.97
(`public-haiku-048` probe: 0.9243); the four documented misses flip to blocked
as well. This is the ADR-011 consequence "the gate's numbers are CPU-dispatch
dependent", now deterministic on that runner image rather than a one-off, so
the recorded mitigation (log the host, the AVX-512 flags and one probe) explains
the failure but does not unblock a merge: a re-run returns to the same image.

**Outcome**

The gate is green on every hosted runner for the same commit, or it fails with
an explicit environment verdict instead of a false "regression". A false
`CONFIDENTIAL` on a haiku stops blocking unrelated changes, and the golden
corpus keeps its zero-tolerance meaning on hosts where the graph is
reproducible.

**Acceptance**

- [ ] The eval job either pins a CPU class / container image where the int8 graphs reproduce, or gates the fp32 graph, or records the dispatch anomaly and skips the ratio assertions with a non-green-but-explicit verdict
- [ ] `docs/adr/ADR-011.md` records the choice and replaces the "not done" note in Consequences
- [ ] A run on the offending AMD EPYC image is reproducible evidence: the probe verdict, the host and the flags appear in the job summary, not only in a log line
- [ ] `uv run python scripts/run_evals.py` still exits non-zero on a genuine corpus regression, proven by a deliberately broken golden row in a test
- [ ] CI is green on `master` without a manual re-run

**Notes**

- The evidence needed for the fix is already collected by the "Record the
  inference environment" step; what is missing is a decision about what to do
  with it.
- Not caused by the telemetry or demo work in `bb02cf0` / `9bdb5bf`: the same
  failure appears on the docs-only commit that precedes them.
