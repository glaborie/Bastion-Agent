### IDEA-001: Tenant isolation for Redis keys and Postgres rows

- status: done
- priority: P2
- phase: v0.3
- area: agent
- tags: multi-tenancy, redis, postgres, rbac
- depends-on: -
- spec: ADR-008
- created: 2026-11-09
- updated: 2026-11-11
- source: ADR-008, phase v0.3 scope

**Problem**

Every subsystem assumes a single tenant: the vault key is
`vault:<sha256(session)>`, canaries are per session, quarantine is per session and
audit rows carry no tenant. Two customers on one stack would share a Redis
namespace and a Postgres schema, so one operator role could reach the other
tenant's data through a guessed identifier.

**Outcome**

Every derived key and every audit row is scoped by a tenant id that
comes from the authenticated identity, cross-tenant access is impossible by
construction, and a test proves it by attempting the access.

**Acceptance**

- [x] Tenant id resolved from the OIDC claim and stored on `PendingApproval` and `AuditLog`
- [x] Vault, canary, quarantine and approval keys include the tenant prefix
- [x] A test shows a session from tenant A cannot read a token or ticket from tenant B
- [x] ADR documents the isolation model before implementation

**Notes**

- PostgreSQL row-level security is not part of this change: it remains the v0.3 defence-in-depth step named in ADR-008 and ADR-015 decision 6. Request-path reads are tenant-scoped in the shared query helpers.

### IDEA-002: Push approval decisions over WebSocket instead of 3 s polling

- status: done
- priority: P1
- phase: v0.2
- area: gateway
- tags: dashboard, websocket, hitl, latency
- depends-on: -
- spec: ADR-007
- created: 2026-11-09
- updated: 2026-11-11
- source: ADR-008, phase v0.2 scope

**Problem**

The dashboard polls `/api/approvals` every 3 seconds, so a second
operator can wait up to 3 seconds to see a ticket and every open tab generates
traffic that had to be excluded from tracing.

**Outcome**

The dashboard receives `APPROVAL_REQUESTED` and decision events on a
WebSocket, polling becomes a fallback, and the tracing exclusion for the poll URL
can be removed.

**Acceptance**

- [x] `/ws/approvals` authenticated by the same session cookie and CSRF rules
- [x] Ticket creation and decision broadcast to every connected operator
- [x] Polling remains as a degraded fallback when the socket cannot connect
- [x] A test drives two clients and asserts both see the decision

**Notes**

- The bus is Redis pub/sub on `approvals:events:<tenant>`: the worker and demo scenarios publish ticket creation after the database commit, and the decision route publishes `APPROVAL_GRANTED`/`APPROVAL_REJECTED` after its commit. A publish failure is logged and swallowed; the dashboard's 3 s polling remains the recovery path.
- The browser sends the CSRF token in the `bastion.csrf.<token>` WebSocket subprotocol so it stays out of the URL and access logs; the query parameter and `X-CSRF-Token` are accepted for non-browser clients.
- Residual: `/ws/approvals` is authenticated and read-only but is not covered by ADR-013's HTTP request budget, and the JS polling fallback is covered by code inspection rather than a browser E2E harness. The socket protocol, tenant isolation, two-client fan-out and publish-after-commit paths are tested.

### IDEA-003: Route the ONNX ensemble to GPU to meet the 50 ms classify budget

- status: done
- priority: P1
- phase: v0.2
- area: agent
- tags: onnx, gpu, latency, classifier
- depends-on: -
- spec: ADR-011
- created: 2026-11-09
- updated: 2026-11-11
- source: ADR-011, measured 41-98 ms per classify on CPU

**Problem**

`SensitivityClassifier.classify()` measures 41-98 ms on the CPU-only
host, so the stated sub-50 ms budget is missed and every chat turn pays it.

**Outcome**

With `onnxruntime-gpu` and CUDA visible to `gateway` and `worker`,
the ensemble meets the budget on the golden corpus and still runs on CPU when no
GPU is present.

**Acceptance**

- [x] `onnxruntime-gpu` installed in the image with a CPU fallback path
- [x] A benchmark over `tests/data/goldens.jsonl` reports p95 under 50 ms on GPU
- [x] CPU-only verification still passes `tests/test_classifier_evals.py`
- [x] ADR-011 records the measured numbers and the provider chosen

**Notes**

- ADR-011 had already measured the shipped int8 graphs on CUDA and rejected them (1.4–2× slower; `MatMulInteger` has no CUDA kernel). This item re-opened that decision through the ADR's own condition — a graph with real CUDA kernels — by using the fp32 `onnx/model.onnx` that both pinned repositories ship. The int8 path stays the CPU default; a CUDA session selects the fp32 graphs when `CLASSIFIER_*_MODEL_GPU_PATH` is set.
- The fp32 graph is a second calibration, not a drop-in: on the golden corpus it scores the benign prompt-engineering explainer `unsafe` 0.570 against the int8 graph's 0.364, so the int8 `unsafe = 0.5` would add a benign false positive. The fp32 fp-free range is 0.580–0.900; `CLASSIFIER_SAFETY_UNSAFE_THRESHOLD_GPU=0.6` is the chosen point (model recall 14/22, 0/32 FP; joint gate still 28/32 with the same four documented gaps). Injection (`0.662`) and category (`0.3`) are unchanged because the fp32 sweep reproduces their fp-free ranges. With that operating point, a CUDA session reproduces every asserted label (83 rows, 0 mismatches).
- The GPU deployment is opt-in: `docker-compose.gpu.yml` builds the `runtime-gpu` target (onnxruntime-gpu with cudnn, CPU EP retained) and exposes the device with `gpus: all`; the base compose file and the default provider remain CPU. The GPU image was verified without a device: `CLASSIFIER_EXECUTION_PROVIDER=cpu` runs on the CPU EP, and `auto` logs the missing CUDA library and falls back to the CPU EP.
- Latency: `scripts/benchmark_classifier_goldens.py` over the 83-row corpus, five warm-up passes and 30 timed passes: p50 25.6 ms, p95 40.5 ms, p99 50.3 ms, both sessions `CUDAExecutionProvider`; across runs p95 stayed between 40 and 50 ms. Time to first answer after an idle period can exceed the budget while the GPU clocks ramp, which is why the script warms up before timing. The per-probe fp32 CUDA table is in ADR-011.
- VRAM: with the Q4_K_M model resident the card moved from 6,568 MiB to 7,814 MiB after loading the fp32 sessions and peaked at 7,834 MiB of 8,192 (~1.27 GiB delta, ~358 MiB left). Only one process may open the sessions; the gateway is the only classifier user and the worker only closes the router. Recorded in ADR-011.
- Verification: `uv run pytest -q tests/test_classifier_evals.py` 12 passed (int8 CPU gate); golden-label parity under the fp32 CUDA session 0/83 mismatches; benchmark p95 40.5 ms `within_budget`; full `pytest` 612 passed / 2 skipped (`model_integration`, no `LLAMA_CPP_BASE_URL`); ruff check and format clean, mypy clean (48 files), pylint 10.00/10, and `check_adrs.py`, `validate_tool_catalog.py --check`, `validate_rbac.py`, `recalculate_dread.py --check`, `check_backlog.py --check` all OK; `docker compose config` valid for both the base and the GPU override.
- Files changed: `agent/routing/classifier.py` (provider-aware graph selection, CUDA preload, fp32 operating point), `settings.py` (GPU paths/digests and threshold), `scripts/benchmark_classifier_goldens.py`, `Dockerfile` (`runtime-gpu` stage), `docker-compose.gpu.yml`, `docker-compose.yml`, `.env.example`, `docs/adr/ADR-011.md`, `README.md`, `tests/test_classifier.py`, `tests/test_settings.py`.

### IDEA-005: Reject canary prefixes shorter than eight characters at startup

- status: done
- priority: P1
- phase: v0.2
- area: security
- tags: canary, egress, validation, config
- depends-on: -
- spec: ADR-012
- created: 2026-11-10
- updated: 2026-11-11
- source: review of CANARY_PREFIX handling

**Problem**

`CANARY_PREFIX` is read from the environment and used as the
match token for `inspect()`. An empty or one-character prefix either blocks every
response or matches arbitrary text, and nothing rejected it at startup.

**Outcome**

Settings refuse a prefix shorter than eight characters, the failure is
explicit at boot rather than at the first request, and tests pin the minimum.

**Acceptance**

- [x] Settings validation rejects prefixes shorter than 8 characters
- [x] Startup failure names the variable and the minimum length
- [x] A test covers empty, one-character and valid prefixes
- [x] `.env.example` documents the constraint

**Notes**

- The acceptance floor of 8 exposed a conflict: the shipped default `CANARY-` is 7 characters, so enforcing it as written would have made the default configuration unstartable. The default is now `BASTION-CANARY-` (15 characters); the alternative of lowering the floor to 7 was rejected because it leaves the shipped marker one character above the dangerous range. Recorded in ADR-012 decision 1.
- The floor is enforced twice: `Settings._validate_canary_prefix` rejects it at startup with `CANARY_PREFIX must be at least 8 characters; got N`, and `EgressSanitizer` applies the same check to an explicit `canary_prefix=` override so a test fixture or script cannot bypass the boot check. `canary_prefix=""` now raises instead of silently falling back to the configured default.
- Upgrade note: canaries already in Redis keep the old `CANARY-` format until their 30-minute TTL lapses, and the new pattern does not match them. Restarting a deployment with the new default therefore leaves a TTL-bounded window in which a pre-upgrade marker would not trip the gate; drain sessions or accept the window. Recorded in ADR-012 decision 1.
- Files changed: `settings.py` (constant, default, validator), `agent/egress/sanitizer.py` (floor and override handling), `.env.example`, `docker-compose.yml`, the five test modules that pin the prefix, `scripts/demo_egress.py`, and the ADR/README/SECURITY/THREAT_MODEL/DEMO/HANDOVER_SPEC references to the marker format.
- Verification: `ruff check .` clean, `ruff format --check .` clean, `mypy` clean on the gate targets, `pylint` 10.00/10, full `pytest` 609 passed / 2 skipped (the two `model_integration` probes, no `LLAMA_CPP_BASE_URL`), and `check_adrs.py`, `validate_tool_catalog.py --check`, `validate_rbac.py`, `recalculate_dread.py --check` all pass.

### IDEA-007: Route corporate-confidential documents without explicit markers to the local model

- status: done
- priority: P1
- phase: v0.2
- area: agent
- tags: classifier, calibration, dlp, routing
- depends-on: -
- spec: ADR-011
- created: 2026-11-10
- updated: 2026-11-11
- source: live traffic through POST /v1/chat on 2026-11-10

**Problem**

The classifier only routes to `local-llama` when it sees a marker. Measured on
the live stack today, "Q3 revenue forecast assumes a hiring freeze through
December" reached `cloud-primary` as PUBLIC with confidence 0.9875, and a
supplier indemnity clause reached it with 0.9804. The first matches only the
`commercial` rule at weight 2.0, which the deterministic floor scores
`2/(2+2)=0.50` against the 0.55 threshold (`agent/routing/classifier.py`,
`_classify_rules`); an indemnity clause of the same shape matches no rule at all
(measured: 0 markers). The ONNX ensemble cannot close the gap by design — it was
trained on harm, so secrecy that contains nothing harmful reads as safe
`public_content`. The documents a company most wants kept in-house —
forecasts, margin analysis, contracts — therefore leave for the cloud unless
someone happens to type "confidential".

**Outcome**

A prompt that is corporate-confidential by content, with no explicit marking,
routes to the local model or is refused, and the verdict with its evidence is
visible in the audit ledger and on the trace's server span. The documented
"single weight-2 marker stays borderline" policy is either revised with a
recorded rationale or replaced, and the evidence corpus is extended with this
class of text.

**Acceptance**

- [x] `uv run pytest tests/test_classifier.py tests/test_classifier_evals.py -q` passes with a new assertion for an unmarked commercial prompt (a revenue forecast, a contract clause); no existing assertion is deleted to make the new one pass
- [x] `uv run python scripts/demo_classifier.py "<sample>"` prints the new verdict and the rule or ensemble evidence that produced it, for both sample classes
- [x] `docs/adr/ADR-011.md` records the choice (rule weight, new rule set, or a second model head), the re-measured benign false-positive and recall numbers, and the gap that remains
- [x] The corpus gains rows of this class taken from measured live traffic, and ADR-011 still states it is calibration, not held-out evidence
- [x] A live `POST /v1/chat` with such a prompt shows `bastion.classification=CONFIDENTIAL` and `bastion.route=local-llama` on the server span in the trace store

**Notes**

- Implemented at explicit request (the item was `inbox`, and the ready list was empty); the decision recorded here is the "revise the documented policy with a rationale" option, not weight tuning alone.
- Originally recorded as documented policy, not a crash: the `_RULES` comment pinned the 0.50 outcome deliberately and `test_a_single_codename_is_borderline_and_stays_public` enforced the same threshold for `codename`, so the fix had to be a decision with a false-positive budget attached, not an inline edit.
- Options seen at capture: raise `commercial` to 3.0 (a lone forecast marker then scores 0.60), add a contract/legal rule set, or train a corporate-secrecy head. Weight tuning alone could not cover the indemnity case, which matched nothing — hence both the weight raise and the new rule set.
- The misroute was spotted while reviewing trace telemetry from a realistic traffic run: it appeared as a PUBLIC `cloud-primary` turn in OpenLit. Related to IDEA-003 (classifier latency) through the same ADR-011 operating point.
- Policy now: every domain marker weighs 3.0, so one marker of confidential substance crosses the 0.55 threshold on its own. `commercial` moved 2.0 → 3.0 and `contract_legal` is new at 3.0 (`indemnif*`, `indemnit(y|ies)`, `force majeure`, `governing law`, `limitation of liability`, `unlimited liability`, `liability cap`, `master services agreement`, `warranty clause`, `warranty period`). `codename` is the only remaining weight-2 marker, so "a single weight-2 marker stays borderline" is now true of a project name alone — an identifier with no confidential content around it, unlike a forecast or an indemnity clause, which *is* the content. The `_RULES` comment and `test_a_single_codename_is_borderline_and_stays_public` keep enforcing that.
- Measured over the 85-row corpus with the pinned int8 graphs: the rules floor blocks 18 of 42 asserted must-block positives (0.429, was 16/40 = 0.400) and flags none of the 26 rows the corpus expects to stay `PUBLIC` (0.000, unchanged); the end-to-end gate blocks 42/42. The five accepted over-routes (term sheet, board meeting, source-code review, salary benchmark, merger news) are unchanged. `tests/test_classifier_evals.py` pins the three counts so the FP budget cannot drift silently.
- Corpus 83 → 85 rows: `corporate-forecast-unmarked-084` (the verbatim live prompt, which the model alone still calls `public_content` at 0.999) and `corporate-indemnity-clause-085` (its model-only confidence reproduces the measured 0.9804). ADR-011 still labels the corpus calibration, not held-out evidence, and now records the expansion and the numbers.
- Live verification against the running stack (gateway and worker images rebuilt with the change): `POST /v1/chat` for the forecast returned CONFIDENTIAL / local-llama / 0.6 / reason `matched: commercial`, and for the indemnity clause CONFIDENTIAL / local-llama / 0.6 / `matched: contract_legal`; both spans are in the OpenLit trace store with `bastion.classification=CONFIDENTIAL`, `bastion.route=local-llama` and the matching `gen_ai.conversation.id`.
- Remaining gap (recorded in ADR-011 decision 4): the floor is a vocabulary gate, so corporate text phrased without any of these markers — the "client's account at the Zurich Kantonalbank" paraphrase already carried as a `known_gap` row — still reads as public. The learned graphs have no corporate-secrecy notion, so closing that needs a dedicated head or corpus retraining, which is a separate item.
- Gates: `tests/test_classifier.py` 63 passed and `tests/test_classifier_evals.py` 14 passed; full `pytest` 621 passed / 2 `model_integration` skips; ruff check and format clean; mypy clean (66 files); pylint 10.00/10; `check_adrs.py`, `validate_tool_catalog.py --check`, `validate_rbac.py`, `recalculate_dread.py --check` and `check_backlog.py --check` all OK.

### IDEA-008: Make the eval gate bit-reproducible across hosted runners

- status: done
- priority: P1
- phase: v0.2
- area: evals
- tags: ci, onnx, int8, calibration, golden-set
- depends-on: -
- spec: ADR-011
- created: 2026-11-10
- updated: 2026-11-10
- source: CI runs 42866889651, 42870723135 and 42882954274 on 2026-11-10

**Problem**

`Zero-tolerance eval gates (real ONNX models)` is red on `master` for two
consecutive commits even though one of them (`af91390`) only touches
`BACKLOG.md`. Both runs and a re-run land on an AMD EPYC 7763 runner and score
the benign golden rows `CONFIDENTIAL`/`unsafe_content` at 0.75–0.97
(`public-haiku-048` probe: 0.9243); the four documented misses flip to blocked
as well. This is the ADR-011 consequence "the gate's numbers are CPU-dispatch
dependent", now deterministic on that runner image rather than a one-off, so
the recorded mitigation (log the host, the AVX-512 flags and one probe) explains
the failure but does not unblock a merge: a re-run returns to the same image.

The signature is now narrowed to the host's instruction set. Every failing run
landed on an AMD EPYC machine that reports no AVX-512 at all, so `/proc/cpuinfo`
lists no `avx512*` flags and ONNX Runtime selects the AVX2 int8 kernels: EPYC

`Senapus Perillard`, street `Piazza Indipendenza 102`, city `6808 Torricella`,

`SenapusPerillard@teleworm.us` and `Born April 7, 1996`. `DLP_REDACTION`

`{"model":"openai/gpt-4o-mini","route":"cloud-primary","restored_tokens":2}`. So
the name, the postal address and the date of birth were sent to `gpt-4o-mini` in
plaintext, the assistant echoed them back, and the egress filter restored the two
tokens for the authorised client exactly as designed.

Reproduced directly against `get_analyzer()` on 2026-11-11: `"Senapus
Perillard"` returns `[]` — `en_core_web_sm` tags no PERSON at all, even at
`score_threshold` 0.0 — while `"Alice Smith"`, `"Maria Keller"` and `"Müller
Beat"` are tagged PERSON 0.85, so the miss is name-shaped (out-of-vocabulary
surname), not a wiring bug. The full record at threshold 0.0 yields
`EMAIL_ADDRESS` 1.0, `LOCATION` 0.85 (only `Switzerland`; the street and city are
not parsed), `DATE_TIME` 0.85 (`April 7, 1996` plus a spurious `98 31` inside the
phone number), `PHONE_NUMBER` 0.75 and `URL` 0.5 (`teleworm.us`). `LOCATION` and
`DATE_TIME` are absent from the default `DLP_ENTITIES` in `settings.py`
(`PERSON,EMAIL_ADDRESS,PHONE_NUMBER,IBAN_CODE,IP_ADDRESS,CREDIT_CARD,US_SSN,API_KEY`),
so even the spans Presidio does find are dropped, and there is no address
recognizer at all. The language gate is not the cause: `detect_language()` read
the record as `it` at 0.571, below `DLP_LANGUAGE_MIN_CONFIDENCE` 0.80, so NER
still ran.

The root cause is two independent gaps that compose. (a) DLP recall is a fixed
entity list plus one English spaCy model, and it misses an unusual personal name
plus every entity type outside that list. (b) The two-model classifier has no
personal-data notion at all — the `sensitive_personal` rule is a keyword list
(`passport`, `social security`, `bank account`, `medical record`, `diagnos*`),
and the ensemble knows corporate confidentiality, injection and safety — so
`PUBLIC` is a correct answer to the question it is asked, and nothing forces
PII-bearing text to `local-llama` when redaction is incomplete. The golden corpus
encodes the second gap: PII rows carry `expected_label: null`.

**Outcome**

A prompt that is a structured personal record no longer reaches a cloud route
with an unredacted name, postal address or date of birth: it is either kept on
`local-llama`, refused, or sent only after every field the record contains has
been tokenised. Whichever route is chosen is recorded as a decision in ADR-002,
the ledger says why on the request's own rows, and the corpus and tests pin the
record so the behaviour cannot regress. No existing redaction, routing, canary
or four-eyes behaviour is weakened to achieve it.

**Problem**

Every credential the stack needs is a plain process environment variable, so "production secrets" today means a line in a gitignored `.env` that is readable by `docker inspect`, `docker compose config`, any process in the container and any crash dump. `settings.py` declares four of them as `SecretStr` — `keycloak_client_secret` (line 66), `vault_master_key` (line 114), `approval_hmac_secret` (line 212), `omniroute_api_key` (line 236, default `sk-local-dev`) — but two more are not even wrapped: `database_url` (line 49) and `redis_url` (line 59) are plain `str` with the Postgres and Redis passwords inline inside the connection URL, so no redacting type stands between them and any `repr`, log line or traceback that formats the settings object. `_reject_dev_secrets` (`settings.py:407-419`) is the only production guard and it is narrower than it looks: it runs only when `environment` is `staging` or `production`, compares exactly three values against their dev constants (`VAULT_MASTER_KEY` 411, `APPROVAL_HMAC_SECRET` 413, `KEYCLOAK_CLIENT_SECRET` 415), and never inspects `omniroute_api_key`, `database_url` or `redis_url`. **Outcome**

Each service logs in with its own AppRole and its own policy — gateway and worker get distinct roles, because the worker never mints or needs the vault key but does execute guarded tools. The audit device records every read with the AppRole identity and the path and never the value. `settings.py` resolves through a provider with an explicit env fallback for `ENVIRONMENT=local`, and `reset_settings_cache()` (`settings.py:495`) is the supported rotation hook, so a rotation without a restart is testable. When OpenBao is unreachable, secret-dependent paths fail closed at boot and `/v1/chat` refuses to serve rather than falling back to stale environment values. `SECURITY.md`, `COMPLIANCE.md` and `THREAT_MODEL.md` describe the control that actually exists and name the claims that are still aspirational.

### IDEA-021: Anchor the audit chain head in object storage with WORM retention (MinIO)

- status: inbox
- priority: P2
- phase: v0.3
- area: db
- tags: audit, worm, retention, minio, tamper-evidence
- depends-on: -
- spec: ADR-005
- created: 2026-11-11
- updated: 2026-11-11
- source: session request on 2026-11-11 ("capture MinIO WORM as a compliance improvement")

**Problem**

The ledger's tamper evidence stops at the database boundary. `verify_audit_chain` (`db/audit.py:121`) walks `audit_logs` and checks each `record_hash` against its `previous_hash`, but `ChainVerification` (`db/audit.py:46-53`) returns only `ok`, `checked`, `first_bad_id` and `reason` — no terminal hash — so `scripts/verify_audit_chain.py` (`:63` returns `2` when verification cannot run, `:79` returns `0`/`1` for intact/tampered) and `POST /api/audit/verify` (`gateway/routers/audit.py:107`) can only prove the rows agree with each other. `THREAT_MODEL.md:240` states the consequence: "A chain inside the same database detects partial edits. An attacker with write access can recompute the whole chain. Detecting that needs the head hash exported to a separate system or write-once store, plus an INSERT-only database role. Neither is implemented." Nothing stores a hash outside Postgres: `docker-compose.yml` defines eight services plus two profile UIs and four volumes (`pgdata`, `redisdata`, `keycloak_data`, `omniroute_data`; lines 497-501), and a search for `minio`, `object lock`, `write-once` or `archival` returns only prose claims.

Those claims are the second half of the gap. ADR-005 decision 5 (`docs/adr/ADR-005.md:50`) records retention as "7 years … partitioning by year; cold data moved to archival storage" and marks it "Not implemented in v0.1 — scheduled for v0.3 (async audit export) / v0.5 (compliance mode)". `SECURITY.md:132-133` nevertheless states "Retention: 7 years (partitioned by year)" and "Cold storage: Migrate to archival after 1 year", and `COMPLIANCE.md:117` (FINMA 2018/3 §4.5) and `COMPLIANCE.md:137` (Swiss Banking Act Art. 48) both cite "7-year retention" as ✅ Compliant. No partition exists, no archival path exists, and no export can be made deletion-proof because there is no store to write it to.

**Outcome**

A `compliance` compose profile supplies a digest-pinned MinIO with versioning and object lock, and a one-shot `mc` init job that creates `bastion-audit` with a 7-year default retention in `COMPLIANCE` mode. Whenever an export runs — or on a schedule, until IDEA-004 exists — the writer appends a small witness object containing only the tenant or global scope, the id range, the row count, the terminal `record_hash`, a timestamp and a signature; no prompt, completion, tool argument or plaintext PII, because the ledger itself is hash-only (`THREAT_MODEL.md:238`). `scripts/verify_audit_chain.py` gains a mode that recomputes the DB head and compares it to the stored witness, exits non-zero on any mismatch, and treats an unreachable store as "could not verify" (`2`) rather than a pass. The application credential may only put objects under the witness prefix: retention is server-enforced, and an overwrite creates a new version instead of replacing the witness. `ADR-005.md:50`, `SECURITY.md:132-133`, `COMPLIANCE.md:117`/`:137` and `THREAT_MODEL.md:240` claim retention and external anchoring only once they are real.

**Acceptance**

- [ ] `docker compose --profile compliance up -d` starts `minio` (pinned by digest, as `db` and `redis` are) and a one-shot `minio-init` job; `mc retention info` on `bastion-audit` reports `COMPLIANCE` with a 7-year default and `mc version info` reports versioning enabled, asserted by the scripted check rather than by reading the compose file
- [ ] Deleting or overwriting a retained witness with the application credentials fails (403 or an object-lock error) and `mc stat --versions` still lists the original version; `uv run pytest tests/test_audit_witness.py -q` asserts both the failure and the surviving version against the running MinIO
- [ ] `uv run python scripts/verify_audit_chain.py --witness` exits `0` on an intact ledger and non-zero after one audit row is edited or deleted — mutated through the documented opt-out `SELECT set_config('bastion.allow_audit_mutation', 'on', true)` (ADR-005:46), not by disabling the trigger — and an unreachable MinIO exits `2`
- [ ] The witness object carries only scope, range bounds, row count, terminal `record_hash`, timestamp and signature; a test reads the stored object and asserts no prompt, completion or tool-argument text and no plaintext PII is present
- [ ] `mc admin policy info` (or the bucket policy) shows the app credential holds `s3:PutObject` on the witness prefix only, and a test asserts `s3:DeleteObject` and `s3:PutBucketObjectLockConfiguration` are denied, so retention cannot be shortened from the application

### IDEA-022: Detect runtime container escapes and unexpected process behaviour with Falco

- status: done
- priority: P2
- phase: v0.4
- area: security
- tags: runtime, falco, detection, docker, monitoring
- depends-on: -
- spec: ADR-001
- created: 2026-11-11
- updated: 2026-11-11
- source: session request on 2026-11-11 ("capture Falco as a compliance improvement")

**Problem**

The stack is hardened at start and unobserved afterwards. The app tier carries
`init: true`, `no-new-privileges:true` and `cap_drop: ALL`
(`docker-compose.yml:112-117`, the `x-app-build` anchor) and every other
service repeats the pair (`db:217-220`, `redis:282-285`,
`keycloak:341-344`, `omniroute:388-391`, `llama-cpp:442-445`,
`otel-collector:490-493`), but there is no seccomp, AppArmor or `noexec`
profile anywhere in the tree, so that is prevention with no observation: nothing
records what a process does after the container starts. All eight services share
one bridge network and the host kernel (`docker-compose.yml:503-505`), and
`bastion-net` is not `internal: true`, so a compromised gateway can open a
connection to any destination; "OmniRoute as the only routing layer"
(`docs/adr/ADR-001.md:21`) is enforced in Python, not by the network. The
process runs as uid 10001 (`Dockerfile:21-22,45`) but owns its own source tree
(`Dockerfile:35-41`), so it can rewrite `/app/gateway/...`, and it can spawn
`/bin/sh` from the `python:3.11-slim` base (`Dockerfile:6`) without any tool
doing it: `docs/tools/v1.json` lists exactly three tools
(`execute_file_write`, `read_file`, `read_system_status`), none executes a
command, and `agent/tools/builtin.py:37-59,147-166` confines writes to
`TOOL_WORKSPACE_ROOT` (`/tmp/bastion-workspace`, `.env.example:117`). The
existing evidence cannot cover this: T10 (`THREAT_MODEL.md:231-241`) is post-hoc
chain verification and T11 (`:243-251`) is build-time supply chain; §4's control
table (`:85-95`) lists no control that observes syscalls, process trees or
sockets, and the only uses of "runtime" in that document are the status
definitions (`:18`) and a negation (`:183`). `COMPLIANCE.md` overstates what
exists: CC7.2 (`:103`) claims "detection and monitoring procedures" evidenced by
"Golden regression suite, CI/CD gates, vulnerability scanning, SBOM generation",
all build-time; FINMA §4.4 (`:116`) cites "real-time approvals"; EU AI Act
Art. 15 (`:146`) repeats the build-time list; and `:56`/`:104` claim
"24/7/365 monitoring", which no component performs.

**Outcome**

One documented, opt-in command starts a runtime detector that observes the
container syscalls the rest of the design assumes are well behaved, and a
reviewed rule set turns the behaviours that matter here into JSON alerts naming
the container and process: a shell or package manager in `gateway`/`worker`, a
worker write outside `TOOL_WORKSPACE_ROOT`, a gateway connection to anything
other than `db`, `redis`, `keycloak`, `omniroute`, `otel-collector` or the
container DNS resolver, `exec`/`nsenter` into `db` or `redis`, and a write to
`/etc/passwd`, `/etc/shadow` or the app's own tree. The default `docker compose
up -d`, the unprivileged CI job and the host test suite are unchanged; alerts
carry container and process metadata only, never prompt or completion text, tool
arguments, vault markers or process environment. `COMPLIANCE.md` and
`THREAT_MODEL.md` state what is observed, what is not, and which rows were
overstating monitoring before the control existed.

### IDEA-023: Replace internal plaintext and password-only links with short-lived mTLS via Step-CA

- status: inbox
- priority: P2
- phase: v0.4
- area: infra
- tags: mtls, step-ca, pki, zero-trust, docker
- depends-on: -
- spec: ADR-001
- created: 2026-11-11
- updated: 2026-11-11
- source: session request on 2026-11-11 ("capture Step-CA as a compliance improvement")

**Problem**

Every hop inside the stack is plaintext and authenticated by a shared password.
`DATABASE_URL` is `postgresql+asyncpg://…@db:5432/bastion` with no `sslmode`
(`docker-compose.yml:23`) and `create_async_engine` passes only `timeout` and
`server_settings`, so the client neither requests nor verifies TLS
(`db/session.py:34-50`). `REDIS_URL` is `redis://:${REDIS_PASSWORD}@redis:6379/0`
(`docker-compose.yml:27`) against a server started with `--requirepass` and no
`--tls-port` (`docker-compose.yml:259-270`), and `Redis.from_url` sets no `ssl`
argument (`db/redis.py:20-27`). Keycloak speaks `http://keycloak:8080` for both the
JWKS document and the back-channel token endpoint (`docker-compose.yml:34,37`;
`KC_HTTP_ENABLED: "true"` at line 321; `.env.example:62`), OmniRoute is reached at
`http://omniroute:20128` with `OMNIROUTE_API_KEY` defaulting to `sk-local-dev`
(`docker-compose.yml:91-92`), and traces post to `http://otel-collector:4318`
(`docker-compose.yml:99`). Every service in the file joins one user-defined bridge
(`docker-compose.yml:503-505`) — the eight default services plus the `pgadmin` and
`redis-ui` side cars — and the app tier additionally loads the whole `.env` into
its environment (`docker-compose.yml:109-111`).

The load-bearing exposure is credential replay, not passive sniffing. The compose
baseline drops `CAP_NET_RAW` (`docker-compose.yml:116-117`), which raises the bar
for ARP or DNS spoofing from a compromised container, but every app container
already holds `POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `OMNIROUTE_API_KEY` and
`KEYCLOAK_CLIENT_SECRET` (`docker-compose.yml:23,27,32,92`), so a compromised
workload — or anyone who reads a leaked `.env`, a host process, or the loopback
ports published at `docker-compose.yml:209,274,331,372` — can replay those
credentials from anywhere on the bridge, with no identity attached. `SECURITY.md`
claims TLS only at the edge ("Bound to `127.0.0.1` (use TLS reverse proxy for
external access)", lines 237-238) and quarterly rotation of `REDIS_PASSWORD`
(line 243), which is the same shared secret model. `settings.py` masks the DSN in
logs with `redacted_database_url` (`settings.py:478-486`, used at `db/session.py:53`
and `gateway/main.py:66`), which is presentation, not transport security: the
password still crosses the bridge in the clear.

The gap is already named and unowned. `THREAT_MODEL.md` T8 lists "separate Redis
ACL users for gateway and worker, TLS, and no host port exposure" as **PLANNED**
(line 216) and concludes "treat Redis write access as equivalent to administrator
access" (line 217), while §2 assigns "network segmentation" to the deployer
(line 38). No ADR decides how that is done. ADR-001 is the record this item
amends, and it does not authorise the change: its Context fixes the target as
"a single Docker Compose stack on one host … no service mesh or sidecar proxies"
(`docs/adr/ADR-001.md:11`), decision 1 repeats "no sidecar proxies"
(`ADR-001.md:15`), and decision 2 accepts that JWKS is "fetched over the internal
network" without saying over what (`ADR-001.md:17`). The zero-trust claim in that
ADR's Consequences (`ADR-001.md:29`) therefore holds at the gateway ingress only;
east-west, the stack is a flat trusted network. Whoever takes this item must say
outright that it contradicts those two ADR-001 sentences, and must change the ADR
rather than cite it as precedent.

**Outcome**

The default profile still starts for local development, and a `pki` profile (or a
`docker-compose.pki.yml` override, mirroring the existing `docker-compose.gpu.yml`
pattern from IDEA-003) switches the data plane to mutual TLS: PostgreSQL, Redis,
Keycloak, OmniRoute and the OTLP endpoint each present a certificate issued by a
local Step-CA, the app tier presents a client certificate, and a password alone is
no longer sufficient to reach Postgres or Redis. A short certificate lifetime
(default 24 h) renews from an agent without rebuilding images, an expired or
missing certificate fails the connection closed instead of silently falling back
to plaintext, and the CA's private key never enters the repository, `.env` or a
world-readable volume. ADR-001 is amended — or a successor ADR with ADR-001 marked
Superseded — to record the east-west trust model, the reversal of the "no sidecar
proxies" sentence (a renewal agent is not a proxy, but it is a sidecar and that

**Problem**

### IDEA-027: Cache semantically equivalent completions to avoid repeated model calls

- status: inbox
- priority: P2
- phase: v0.5
- area: agent
- tags: semantic, cache, redis, latency
- depends-on: -
- spec: -
- created: 2026-11-12
- updated: 2026-11-12
- source: session request on 2026-11-12 ("add a semantic cache component to avoid unnecessary LLM calls for similar queries")

**Problem**

Every chat turn ends in a model call that nothing can short-circuit:
`gateway/routers/chat.py` reaches `model_router.complete(...)` at line 446
unconditionally after DLP, classification and routing, and
`agent/routing/client.py::ModelRouter.complete` (line 261) always posts the
messages to OmniRoute. A search for an answer cache finds none — `agent/`,
`gateway/` and `settings.py` hold only `functools.lru_cache` singletons (the
Presidio analyzer, the tool catalog, the model router, the JWKS client, the
settings object) and `gateway/evals.py`'s mtime-keyed report cache, while Redis

duplicates queue behind the single RTX 3060 Ti that ADR-004 records, and every
`PUBLIC` duplicate is a billed cloud completion. The opposite gap matters too:
`gateway/routers/audit.py` states that PII payload responses are never cached,
so any completion cache has to be argued against an existing no-cache posture
rather than added casually.

**Outcome**

A cache in front of the completion call answers a repeated or semantically
equivalent question without a model request, and the saving is measurable in hit
rate and latency; a near-duplicate whose answer would differ misses and calls
the model. Lookup happens after DLP and classification, and the entry is keyed
by tenant, model alias and classification label, so a turn can never receive
another tenant's answer or a `cloud-primary` answer for a `CONFIDENTIAL` prompt.
Entity markers stay session-scoped: egress restores them for the requesting
session, and a hit never delivers an unresolved `{{ENTITY:...}}` token. The
similarity backend is injectable, the threshold and TTL are settings keys, and
the feature ships off by default until an ADR records the key, the scope, the
eviction and the audit shape.

- [ ] The same text routed two ways never shares an entry: a `pii_detected` turn on `local-llama` does not read a `cloud-primary` entry, and a tenant B turn does not read a tenant A entry, both asserted with identical prompt text
- [ ] A hit cannot deliver another session's marker: a test replays a cached answer whose markers were minted in a different session and asserts the caller gets either a fully restored answer or a miss, never a `{{ENTITY:...}}` token
- [ ] The turn is still audited: a cache hit is visible on the ledger (the existing rows' metadata, or the event shape the ADR decides) and the hit still writes the DLP and egress rows for that turn, asserted by comparing the hit and miss paths in `tests/test_semantic_cache.py`

- [ ] The ADR (a new one, or an amendment to ADR-004) records what the cache is not — not a confidentiality decision, not a substitute for DLP, canary or egress, and not a PII store — and `uv run python scripts/check_adrs.py` passes

The last answer has no later turn to carry it, and nothing in the server, logs or traces retains it: ADR-014 deliberately never exports completion text, and IDEA-016's acceptance fixed the escrow to the raw input because that was the only event whose `payload_hash` was the digest of user text. The same gap blocks incident triage: on 2026-11-12 that conversation produced `EGRESS_FILTERED` row 632 with `disclosure_claim: system_prompt` and `blocked: false`, so the ledger recorded the claim but not the answer; only the client's copy showed the text was a fabricated generic prompt, not the injected instruction. The server alone could neither confirm nor refute the claim.

**Outcome**

A conversation can be reconstructed from the ledger after the session-scoped vault and canary have expired. The turn that delivers an answer writes one new ledger row whose `payload` is the delivered text (so `payload_hash` covers it), written after egress sanitation and only when the response was not blocked, and — with the existing pre-production flag on — the same row gets an encrypted `egress_delivered` escrow copy in the same store, with the same key, AAD binding, admin-only decrypt, `ESCROW_ACCESSED` evidence and TTL purge. A blocked turn writes no answer row because it delivered no text. Existing rows, hashes and chain links are unchanged with the flag on and off, and the size of what is hashed and escrowed is bounded and recorded rather than silently truncated.

The same change closes the live incident that motivated it: when the injection guard fires, the turn is refused **before** the model is called, the caller gets a gateway-authored notice with `blocked: true` and `block_reason: "prompt_injection_detected"`, and the ledger records `EGRESS_FILTERED` (`blocked: true`) plus `SECURITY_INCIDENT`. No model answer exists to fabricate a system prompt, and the dashboard shows the block instead of an answer.

### IDEA-030: Make the worker reject tool jobs whose identity the gateway did not mint

- status: done
- priority: P1
- phase: v0.3
- area: security
- tags: rbac, redis, hitl, audit, identity
- depends-on: -
- spec: ADR-010
- created: 2026-11-12
- updated: 2026-11-12
- source: security posture review of THREAT_MODEL.md T8 against agent/runtime.py, 2026-11-12

**Problem**

`execute_tool_job` (`agent/runtime.py`) rebuilds `AgentContext` from the ARQ payload, so `actor_id`, `roles` and `tenant_id` are whatever the enqueuer wrote and the worker re-verifies none of them. Anyone who can write the queue can therefore assert any principal, which defeats the four-eyes comparison in ADR-010 decision 3 (a forged `initiator_id` is approved by the real operator) and the tenant boundary ADR-015 decision 4 relies on, because only the cron sweep re-derives the tenant from the stored row — the job path trusts the payload. `THREAT_MODEL.md:228` states the finding and `:100` lists "signed or re-derived identity on queued jobs" as PLANNED, but no backlog item owns it; IDEA-023 raises the cost of writing the queue with mTLS and leaves the payload itself trusted.

**Outcome**

The worker executes a tool job only when it can establish identity without trusting the caller: either the gateway mints a short-lived HMAC over `(job id, actor, roles, tenant, expiry)` that the worker verifies with a key the enqueuer holds and the worker only checks, or the job carries an opaque reference to a gateway-written record whose contents the worker reads. A hand-written job fails closed before any tool runs, before any approval row is written, and before any audit event claims an execution.

**Acceptance**

- [x] A test enqueues a well-formed `execute_tool_job` for a principal the gateway never issued and asserts no `TOOL_EXECUTED` row, no `PendingApproval` row, no tool call, and a rejected-job log or span
- [x] A forged `initiator_id` cannot produce a ticket another approver can satisfy, and a forged `tenant_id` cannot reach another tenant's rows (`tests/test_tool_execution.py`, `tests/test_tenant_isolation.py`)
- [x] Both enqueue sites — the tool-request path and `resume_tool_job` — use the same mint, and the legitimate gateway path still executes end to end
- [x] Expired or replayed payloads are rejected (single use or short TTL), proven by a test that resubmits a captured payload
- [x] `THREAT_MODEL.md` §4 flips the row to LIVE, T8 records the chosen shape and the residual (whoever holds the signing key is still admin), and ADR-010 or a successor records the decision
- [x] `uv run pytest -q`, `ruff check .`, `ruff format --check .`, mypy, pylint and `scripts/gate.sh` pass

**Notes**

- Deduplication: grepped `BACKLOG.md`, `docs/adr/` and `THREAT_MODEL.md` for `opaque`, `forged`, `impersonat`, `signed job`, `re-derive`, `unauthenticated trust boundary`. The only nearby item is IDEA-023 (short-lived mTLS for internal links), whose Notes cite `THREAT_MODEL.md:216` — the TLS half of T8 — and explicitly scope identity out; transport identity leaves any writer who holds a valid client certificate, or the gateway itself, able to forge a principal. ADR-007's demo-console decision relies on the gateway reading `sub` from the session, which is exactly the property the worker never checks. Not a duplicate of IDEA-001 (tenant keys and rows), IDEA-020 (secrets at rest) or IDEA-021 (chain anchoring).
- Classification: `P1`/`v0.3`/`security`. Not `P0`: no live leak, the residual is documented rather than hidden, and exploiting it needs write access the threat model already equates with administrator. `P1` because v0.3 is the multi-tenancy phase (ADR-008) and a payload that names its own tenant makes tenant isolation conditional on Redis ACLs. `area: security` because the deliverable is a trust-boundary invariant; `agent` is the fair alternative, since most lines land in `agent/runtime.py` and `gateway/queue.py`.
- The gap is a design residual, not a coding slip: the threat model already names the remedy. The decision to make is which shape to build (per-job HMAC vs opaque reference) and where the key lives, which needs an ADR line before code because the wrong choice couples four-eyes to a new shared secret.
- Decision taken at implementation (2026-11-12, ADR-018): a per-job HMAC envelope rather than an opaque reference. The reference shape needs a durable pre-enqueue write and would hand the demo CLI database access it does not otherwise use; the envelope reuses the approval-token canonicalisation (`hash_payload`, `canonical_timestamp`) and adds no table. Wire format `v1|<kind>|<sha256 of fields>|<nonce>|<expires_at>`, delivered as `job_nonce`, `job_expires_at`, `job_signature`. The key is `JOB_SIGNING_SECRET`, deliberately separate from `APPROVAL_HMAC_SECRET`, and `_reject_dev_secrets` refuses the documented development value in staging and production. Scope covers `execute_tool_job`, `run_demo_scenario_job` and `resume_tool_job`; the two cron sweeps are in-process calls with no payload.
- Replay is closed by burning the nonce once (`SET job:nonce:<nonce> 1 NX EX <remaining>`), with the TTL measured from the signature deadline rather than arrival. A Redis failure while claiming the nonce is a rejection, not a fall-through.
- A forged payload deliberately writes no audit row: the only identity available is the attacker's, and a hash-chained `SECURITY_INCIDENT` naming an attacker-chosen principal would poison the ledger. The refusal is a structured log line plus a `bastion.job.rejected` span attribute; T8's Verification line points at the tests.
