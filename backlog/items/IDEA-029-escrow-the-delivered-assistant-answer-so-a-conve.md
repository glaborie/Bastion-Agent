### IDEA-029: Escrow the delivered assistant answer so a conversation is reconstructable

- status: done
- priority: P2
- phase: v0.3
- area: db
- tags: escrow, audit, forensics, egress, pre-production
- depends-on: -
- spec: ADR-005
- created: 2026-11-12
- updated: 2026-11-12
- source: live local stack on 2026-11-12, conversation 98ccb1945eed4a97a7424c0b7c7ce814 (audit rows 566-632); the final answer beginning "Success is not the destination..." exists in no ledger row, escrow row, log or trace, and row 632 records `disclosure_claim: system_prompt` with `blocked: false` for an answer that the client's copy showed to be a fabricated prompt the server could not inspect

**Problem**

The payload escrow added by IDEA-016 recovers what the model *saw*, not what it *said*. A three-turn conversation on the live stack wrote twelve rows — four per turn, `INPUT_RECEIVED`, `DLP_REDACTION`, `ROUTING_DECISION`, `EGRESS_FILTERED` — and the final answer is absent from all of them. `EGRESS_FILTERED` is written from `egress.blocked`, `egress.reason`, the restored/unresolved marker counts, `egress.disclosure_claim`, the model and the route (`gateway/routers/chat.py:479`); the sanitized text lives only in the `ChatResponse`, and its `payload_hash` is the digest of `{}` (rows 567-569, 571-573, 577-579 all share `44136fa355b3…`). The two earlier answers were recoverable only by accident: the client resent the thread, so they appear inside the next turn's escrowed `INPUT_RECEIVED` payload (rows 570 and 576). The last answer has no later turn to carry it, and nothing in the server, logs or traces retains it: ADR-014 deliberately never exports completion text, and IDEA-016's acceptance fixed the escrow to the raw input because that was the only event whose `payload_hash` was the digest of user text. The same gap blocks incident triage: on 2026-11-12 that conversation produced `EGRESS_FILTERED` row 632 with `disclosure_claim: system_prompt` and `blocked: false`, so the ledger recorded the claim but not the answer; only the client's copy showed the text was a fabricated generic prompt, not the injected instruction. The server alone could neither confirm nor refute the claim.

**Outcome**

A conversation can be reconstructed from the ledger after the session-scoped vault and canary have expired. The turn that delivers an answer writes one new ledger row whose `payload` is the delivered text (so `payload_hash` covers it), written after egress sanitation and only when the response was not blocked, and — with the existing pre-production flag on — the same row gets an encrypted `egress_delivered` escrow copy in the same store, with the same key, AAD binding, admin-only decrypt, `ESCROW_ACCESSED` evidence and TTL purge. A blocked turn writes no answer row because it delivered no text. Existing rows, hashes and chain links are unchanged with the flag on and off, and the size of what is hashed and escrowed is bounded and recorded rather than silently truncated.

The same change closes the live incident that motivated it: when the injection guard fires, the turn is refused **before** the model is called, the caller gets a gateway-authored notice with `blocked: true` and `block_reason: "prompt_injection_detected"`, and the ledger records `EGRESS_FILTERED` (`blocked: true`) plus `SECURITY_INCIDENT`. No model answer exists to fabricate a system prompt, and the dashboard shows the block instead of an answer.

**Notes**

- Deduplication: grepped `BACKLOG.md`, `docs/adr/` and the code for `RESPONSE_SENT`, `delivered`, `assistant`, `output escrow` and `egress_delivered`. `CONTROL.md:22` already describes a `RESPONSE_SENT` timeline card, but no item or ADR builds it; `HANDOVER_SPEC.md:178` omits it from the event list. IDEA-016 is the input-only store and is done — this extends it to the output rather than duplicating it; IDEA-015 detects disclosure claims at egress, IDEA-009/ADR-014 keeps text out of traces, IDEA-004 exports the ledger, and IDEA-001 scopes keys and rows per tenant. Nothing else covers persisting the answer.
- Classification: `P2`/`v0.3`/`db`. This is a new capability, not a regression: no guardrail is broken and nothing leaked, the client still holds its own answer, so `P2` is honest. `v0.3` is the current phase and already owns audit retention/export (ADR-008); the alternative is `v0.2` only if triage treats "the ledger cannot explain a delivered answer" as a documented-control defect, which the IDEA-011 precedent could support. `area: db` because the work is a ledger event, an escrow kind and the purge/chain invariants; the chat call site is one line and the route is unchanged. `security` is the fair alternative because the answer is PII-bearing and the trust boundary moves, but the shipped code change is the store.
- Decisions taken at implementation (2026-11-12): the event is `RESPONSE_SENT` (matches `CONTROL.md` and the dashboard timeline), the escrow kind is `egress_delivered`, and the row is written for every **unblocked** turn, including an empty answer, so the ledger proves a delivery happened even when the text was empty. The cap is `RESPONSE_STORE_MAX_CHARS=32768`; an answer over it is stored and hashed as its prefix with `truncated: true` and the original length in metadata, so `payload_hash` covers exactly what was stored. "Delivered" means the sanitized text handed to the response after `inspect()` returned `blocked=false`; a canary block raises before that point and writes no answer row. An injection-detected turn is refused before the model call: the caller receives a 200 `ChatResponse` with `blocked=true`, `block_reason="prompt_injection_detected"` and a fixed gateway notice, the model is not invoked, and no answer row exists to fabricate a prompt from.
- Ordering: the answer row is written after `sanitizer.inspect(...)` and before the response is returned, in its own committed transaction like every other stage. The dashboard must not append the gateway notice to the history it resends, and clears that history after a block (the conversation id stays, so the blocked turn remains linked in the ledger), or the hostile turn would re-trigger on every later request.
- Honest limits to record in the ADR: the answer row is a second PII store whenever escrow is on (the vault has already restored markers into `egress.text`); without escrow the row is hash-only and still proves an answer was produced but not what it said; and an answer truncated at the cap is partially unrecoverable by design.
- Scope at implementation: the `RESPONSE_SENT` event, the `egress_delivered` kind, the cap, the injection block and its notice, the dashboard behavior, tests, ADRs 005/012 and the runbook. Not in scope: streaming responses, changing the classifier threshold, or blocking on a disclosure claim when no injection was detected (ADR-012 decision 9 stays in force).
- Gates: `scripts/gate.sh --integration --evals` → 11/11, pytest 720 passed / 12 skipped, evals 232/232 with all metrics 1.000, pylint 10.00/10, mypy clean (78 files), all five policy scripts OK. Live verification on the rebuilt stack: a PII turn wrote `INPUT_RECEIVED`/`DLP_REDACTION`/`ROUTING_DECISION`/`EGRESS_FILTERED`/`RESPONSE_SENT`, the answer decrypted as `egress_delivered` with a matching hash, an injection turn returned `blocked: true` with no answer row and a `SECURITY_INCIDENT`, and the chain verified. The event vocabulary and escrow-kind CHECK constraints are widened idempotently on boot (`AUDIT_EVENT_VOCABULARY_DDL`, `ESCROW_KIND_DDL`).
