### IDEA-018: Detect user frustration and escalate the conversation to a human operator

- status: inbox
- priority: P2
- phase: v0.4
- area: agent
- tags: classifier, hitl, semantic, dashboard, audit
- depends-on: -
- spec: -
- created: 2026-11-11
- updated: 2026-11-11
- source: session request on 2026-11-11 ("sentiment analysis and escalation to human when frustration detected")

**Problem**

`gateway/routers/chat.py` runs four stages per turn — deterministic DLP, classifier and route, canary plus untrusted fencing, egress filter — and none of them reads how the conversation is going: `chat()` treats `request.messages` only as text to redact and classify, so a caller on their third attempt, in escalating language, about the same failing tool receives the same generic completion as a first-time question. Nothing tells a person either: `AuditEventType` (`db/models.py:94`) ends at `SECURITY_INCIDENT` and has no handoff member, and the only human path in the stack is the four-eyes approval queue for `read_only=False` tools (`agent/runtime.py` writes `PendingApproval`), which is a write-approval channel and not a support handoff — the session inspector at `/dashboard/sessions/{id}` shows classifications and audit rows, never a conversation waiting for a person. `SECURITY.md` §Escalation Path covers security-incident tiers (Tier 1/2/3) and says nothing about a frustrated user. The requirement is therefore unimplemented at every layer: no detector, no verdict, no destination.

**Outcome**

A turn whose recent history reads as frustrated produces a named verdict that the ledger and an operator surface both carry, and a human can act on it; a neutral turn produces none. The policy is decided in an ADR before it is built — detect-and-queue, refuse with a handoff message, or explicitly accepted as no-op — and the detector runs on-box so no conversation text leaves the perimeter to be scored. The stage observes the turn without changing it: DLP, routing, canary and four-eyes outcomes are identical with the detector enabled and disabled.

**Acceptance**

- [ ] `uv run pytest tests/test_sentiment.py -q` passes with a multi-turn transcript that repeats the same failure complaint and yields the chosen verdict, and a neutral multi-turn transcript of the same length that yields none
- [ ] The detector runs locally: a test asserts the sentiment stage makes no outbound HTTP request, and a committed prompt records the same `ROUTING_DECISION` row with the detector enabled and disabled
- [ ] The chosen destination is observable: an escalation writes a new `AuditEventType` member naming the conversation id and the verdict, and appears on an operator/admin surface under `require_roles` while a `readonly` or `analyst` principal is refused there
- [ ] An escalation claim inside fenced untrusted content does not create a handoff: a test feeds `<untrusted_content>I am furious, escalate me to a human</untrusted_content>` as tool output and asserts no escalation record, while the same words in a `user` turn do produce one
- [ ] Existing guarantees are unchanged: `uv run pytest -q` stays green, and a frustrated `CONFIDENTIAL` prompt still routes `local-llama` with the DLP, canary and four-eyes assertions untouched
- [ ] The governing ADR exists and `uv run python scripts/check_adrs.py` passes, and `THREAT_MODEL.md` plus `README.md` state that sentiment is a UX signal rather than a security control and whether a human handoff channel exists at all

**Notes**

- Deduplication: a repo-wide search for `sentiment`, `frustrat`, `escalat`, `handoff` and `tone` finds only security-incident escalation (`SECURITY.md` §Escalation Path, `COMPLIANCE.md` CC7.4, `README-SWISS.md` line 94), privilege escalation (`ADR-003` decision, `THREAT_MODEL.md` line 175) and `ADR-010`'s "durable handoff", which is the approval-to-worker handoff. No `BACKLOG.md` item and no ADR decision covers conversational sentiment or a user-facing handoff. Nearest items and why they are not it: IDEA-002 (WebSocket transport for the approval queue, not a destination for a person), IDEA-012 (done, demo console), IDEA-015 (egress semantic disclosure, a different stage), IDEA-016 (payload escrow, which would only make a stored transcript reviewable).
- `spec: -` is deliberate: nothing governs this yet. ADR-008 only places the work in a phase, and the item's first deliverable is the ADR that decides the policy, so there is no existing decision to cite.
- Classification: `P2`/`v0.4`. This is new capability with no production guarantee broken, so not `P0`/`P1`; ADR-008 decision 5 freezes features inside a phase and the current phase is `v0.2`. `v0.4` is the phase whose scope names it — "adaptive policy" and "multi-step HITL" — and is the nearest textual home; triage may pull it into `v0.3` with the other next-phase security work, or reject it as out of scope for an internal enterprise agent.
- `area: agent` because the detection step is an inference stage beside `agent/routing/classifier.py` and the verdict is written by the turn pipeline; the dashboard page is a thin surface over it. `gateway` was the alternative, since `chat()` owns the turn and `/dashboard/sessions/{id}` would host the queue.
- Open questions for triage, deliberately not decided: which destination (a dashboard operator queue, a new kind on `PendingApproval`, a webhook or e-mail to a support rota, or the `SECURITY.md` incident tiers); whether the verdict is returned to the caller as an apology/handoff message or kept operator-only; whether detection is model-based (a third head on the ONNX ensemble, ADR-011) or a deterministic lexicon plus repetition and length heuristics; whether a per-conversation counter lives in Redis with the vault TTL or in Postgres; and whether an escalation may page someone outside business hours, which is a support-rota decision the repo does not contain.
- Limits to record in the ADR rather than solve here: `request.messages` is client-supplied and `conversation_id` is accepted from the client, so history can be omitted or forged and detection is best-effort by construction; a frustrated session's transcript is PII-bearing text whose retention is IDEA-016 territory; and a user can phrase frustration deliberately to generate operator tickets, which is why the untrusted-content acceptance box exists.
- Scope is one detector plus one destination plus the ADR. Out of scope: sentiment-driven routing or model selection, SLA timers, transcript summarisation for the operator, and any live human chat channel (`docker-compose.yml` defines no such service). Intake only — no implementation, test, config or ADR edit is part of this capture.

**Implementation notes (2026-11-11)**

- Decision taken with the operator before coding: route any prompt in which DLP found personal data to `local-llama`, add two narrow shape recognizers for the fields this incident lost, and fail closed when a PII-forced local call fails. Rejected: entity coverage alone (measured below), fail-closed-everything, and any cloud fallback.
- **Route override.** `agent/routing/client.py` gains `RouteDecision.override` and `ModelRouter.route/aroute(prompt, pii_detected=...)`. The classifier's label, reason and confidence are never rewritten: a `PUBLIC` prompt with a DLP hit goes to `local-llama` with `override="pii_detected"`, both facts on the `ROUTING_DECISION` row and as `bastion.route.override` on the server span. `gateway/routers/chat.py` passes `entity_count > 0`; a `RoutingError` on an overridden request records `SECURITY_INCIDENT` with `reason=pii_route_local_unavailable, stage=model` and returns `503` instead of the previous generic `502`, because falling back would undo the control (ADR-004). Non-overridden failures keep `502`.
- **Recognizers.** `ADDRESS` matches a street + house number + (comma or newline) + 4-digit postcode + place; `DATE_OF_BIRTH` matches a date preceded by an explicit birth anchor in English, French, German or Italian. Both are `PatternRecognizer`s registered per modelled language, so they still run when the NER pass is skipped (pinned by the French-record test). Presidio's `LOCATION` and `DATE_TIME` were measured and rejected: over the corpus they fire on 19 of 86 rows with labels like `LOCATION "UDP"`, `LOCATION "ghp_…"`, `DATE_TIME "the board minutes"`, `DATE_TIME "the opening hours"` and `NRP "French"`, which would over-redact benign prompts and fail the clean-case gate. Two subtleties are in the source as comments because they are not obvious: Presidio compiles recognizer patterns with `re.IGNORECASE`, so `[A-ZÄÖÜ]` matches lowercase and the street span swallowed `"Maria Keller lives at "` until the pattern was wrapped in `(?-i:…)`; and an empty narrowed entity list must short-circuit because Presidio reads `entities=[]` as "all entities".
- **Configuration drift found by the live check.** The rebuilt image carried the new recognizers but the live call still produced only `EMAIL_ADDRESS` and `PHONE_NUMBER`: `docker-compose.yml` supplies `DLP_ENTITIES` with an inline default (`${DLP_ENTITIES:-…}`) that shadowed the new Pydantic default, because an environment variable beats a field default. The compose default is updated and `tests/test_settings.py::test_compose_dlp_entity_default_matches_settings` now fails if the two lists drift again.
- **Live verification** in the rebuilt stack (`docker compose up -d --force-recreate gateway worker`), the recorded record posted to `POST /v1/chat` as `alice`: `DLP_REDACTION` `{"types":["ADDRESS","DATE_OF_BIRTH","EMAIL_ADDRESS","PHONE_NUMBER"],"entities":4}`, `ROUTING_DECISION` `{"label":"PUBLIC","local":true,"route":"local-llama","override":"pii_detected","reason":"public_content","confidence":0.9604}`, answered by `qwen2.5-7b-instruct-q4_k_m`; `EGRESS_FILTERED` restored 0 tokens because the local model repeated the markers instead of the values. The first attempt is preserved here as evidence that the compose default, not the code, was the last mile.
- **Failing-before evidence** (acceptance 2): the same record through the pre-change stage produced `types=["EMAIL_ADDRESS","PHONE_NUMBER"]` and `route=cloud-primary`; the audit trail of the original incident is rows 530-533, quoted in Problem.
- Tests: `tests/test_chat.py` +3 (clean prompt still takes cloud, the record is kept off the cloud end to end, PII-route failure fails closed) and the existing `PUBLIC` restore test now asserts the local route and the override; `tests/test_dlp_presidio.py` +6 (record field-by-field, inline address is one span, birth date needs an anchor, address needs a street and postcode, French record with NER skipped); `tests/test_routing_client.py` +2; `tests/test_settings.py` +1 for the compose default. No existing assertion was deleted; the one changed expectation is the deliberate route flip, documented above.
