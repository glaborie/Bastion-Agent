### IDEA-058: Fail the gate when certificate or key material becomes trackable

- status: inbox
- priority: P2
- phase: v0.3
- area: security
- tags: secrets, gitignore, supply-chain, ci
- depends-on: -
- spec: -
- created: 2026-11-14
- updated: 2026-11-14
- source: 2026-11-14, after `vault/certs/vault.key` sat unignored on master because the ignore rule only existed on a closed branch (PR #42); the same day the rule was restored (PR #44) with no gate behind it

**Problem**

`.gitignore` is the only control over generated certificate material: `pki/` and
`secrets/` (`.gitignore:11-14`, generated by `scripts/pki/bootstrap.sh`) and now
`vault/certs/` (`.gitignore:16-18`). Nothing fails when that control is absent
or bypassed. On 2026-11-14 the `vault/certs/` rule existed only on the unmerged
`vault-secrets-overlay` branch (#42, closed), so on `master` `git status` showed
`?? vault/` with a private key in it and a plain `git add -A` would have staged
it; the gap was found by reading status output, not by a check.

No gate step covers this. `scripts/gate.sh:213-221` adds ADRs, tool catalog,
RBAC, DREAD, threat model, backlog, the compose config and pytest, and
`.github/workflows/ci.yml` has no gitleaks, detect-secrets or equivalent step.
`git ls-files` filtered on `\.(crt|key|pem|p12|pfx|jks)$` is run nowhere, so a
committed leaf key or CA root is invisible to every automated control the repo
has. `IDEA-019`'s Notes deliberately left "secret scanning of the tree" as a
separate gate with its own false-positive budget, and IDEA-023/040 are about mTLS
and HTTPS, not about what may be committed, so the follow-up it named was never
captured.

**Outcome**

A committed repository check fails when certificate or key material becomes
trackable, in both directions: a tracked path matching the cert/key patterns,
and generated material present in the worktree whose directory is no longer
covered by an ignore rule. It runs as a `scripts/gate.sh` step and in the CI
quality job, so the 2026-11-14 incident — an ignore rule that lived only on a
branch — is a red check instead of a close call. The message names the path and
the missing rule and never prints file content, so a failure does not leak the
material it is protecting. Legitimate fixture material is allowed only through
an explicit, commented allowlist that the check itself reports.

**Acceptance**

- [ ] `uv run python scripts/check_secret_material.py` exits 0 on `master`, and its rule is what `git ls-files | grep -E '\.(crt|key|pem|p12|pfx|jks)$'` finds: nothing is tracked today, so an empty result must be an assertion inside the check rather than a command a reviewer has to remember
- [ ] A tracked key fails: `tests/test_secret_material.py` builds a git repository in a temporary directory (or calls the check with an explicit path list), commits `dummy.key` and `leaf.crt`, and asserts a non-zero exit whose output contains both paths and contains neither a byte nor a line of the file's content
- [ ] Unignored generated material fails, reproducing the incident: in a temporary copy of the tree with the `vault/certs/` line removed from `.gitignore` and a key placed in `vault/certs/`, the check exits non-zero and names `vault/certs/` and the missing ignore rule; restoring the line makes it pass
- [ ] `scripts/gate.sh` runs it through `add_step` beside `adrs` and `rbac` (`scripts/gate.sh:213-221`), `.github/workflows/ci.yml` runs the same command in the quality job, and `ci-ok` still requires that job, so the check is merge-blocking rather than advisory
- [ ] No false positive on material the repo keeps on purpose: an allowlisted fixture path (for example a future `tests/fixtures/` key needed to test TLS refusal) passes, the allowlist entry carries a justification comment, an unjustified entry fails, and `--verbose` prints the allowlist so a reviewer can see what is exempt
- [ ] The documents that describe the control point at it: the `.gitignore` headers for `pki/`, `secrets/` and `vault/certs/` name the check, and `docs/PKI.md` or `SECURITY.md` §Secrets Management states what the guard covers, how to add legitimate material, and that pattern matching does not catch a key renamed to a non-matching extension

**Notes**

- Deduplication: grepped `backlog/items/` and `docs/adr/` for `gitleaks`, `trufflehog`, `detect-secrets`, `secret scanning`, `gitignore`, `tracked key`, `certificate`. `IDEA-019` (done) added image scanning and explicitly left "secret scanning of the tree" as a separate gate with a separate false-positive budget, which is the gap this item fills for cert material; `IDEA-020` is secrets at rest and runtime, `IDEA-023` is internal mTLS, `IDEA-040` is HTTPS in the gateway profile, and none of them constrains what may be committed. Nothing was merged.
- `spec: -` is deliberate: no ADR governs repository hygiene. `ADR-019` covers east-west PKI material but not what may be committed; `ADR-016` is the nearest precedent for "a control is a gate step, not a dashboard", and it governs image scanning, not this.
- Scope boundary: this is not a full secret scanner. Gitleaks-style content matching over the whole tree has its own false-positive budget and its own capture; this item is the narrower invariant "no certificate or key material is trackable, and generated material stays ignored". Naming that boundary keeps the first slice small enough to land.
- Honest limit to state in the check's own docstring: extension and ignore-rule matching misses a key copied to `notes.txt` or pasted into a Markdown file, so the guard raises the floor and does not replace review.
- The id was allocated as IDEA-055 because this worktree's base predates the `backlog/vault-overlay-gaps` capture that already holds IDEA-055..057; renamed to the next free id so the two branches cannot merge as duplicate ids. `depends-on: -` remains literal.
